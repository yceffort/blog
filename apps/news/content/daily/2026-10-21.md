### Cargo의 의존성 쿨다운은 악성 릴리스가 내려가기 전의 두 시간을 버티는 장치입니다

`Socket` [원문](https://socket.dev/blog/rust-cargo-cooldowns)

8월에 crates.io를 오염시킨 악성 크레이트 세 개가 올라와 있던 시간은 86분, 90분, 107분이었고, 두 시간 안에 내려갔어도 그사이 CI와 개발자 머신에는 이미 들어갔을 수 있습니다.

- Rust 1.100(11월 12일 예정)이 Cargo에 최소 공개 경과 시간 설정을 안정화합니다. `.cargo/config.toml`에 `global-min-publish-age = "7 days"`처럼 적으면 공개된 지 7일이 안 된 버전은 의존성 해석에서 제외됩니다. 기본값은 0이라서 Cargo를 올리는 것만으로는 아무 보호도 생기지 않고 팀이 직접 켜야 합니다.
- 계기는 8월 사건입니다. arrayref, internment, append-only-vec이 탈취되어 악성 크레이트 proc-macro1을 의존성으로 끌어왔고, proc-macro1의 빌드 스크립트가 페이로드를 내려받았습니다. 세 릴리스는 각각 86분, 90분, 107분 만에 내려갔지만 의존성 갱신은 조사보다 빨리 퍼질 수 있습니다. 이 기능 자체는 사건 두 달 전인 6월 21일에 nightly Cargo에 들어와 있었습니다.
- 조건에 맞는 버전이 하나도 없으면 해석을 실패시키는 것이 의도입니다. 기능의 RFC는 공격자가 악성 업데이트를 올린 뒤 안전한 버전을 yank(레지스트리에서 특정 버전을 새 해석 대상에서 빼는 조치)하는 시나리오를 가정합니다. 오래된 버전을 "선호"만 하는 정책이면 안전한 버전이 사라졌을 때 악성 버전으로 되돌아가기 때문입니다. 8월 사건에서도 공격자는 정상 arrayref 버전들을 실제로 yank했습니다.
- Cargo.lock에 이미 기록된 버전은 나이가 어려도 유지됩니다. 긴급 패치가 필요하면 `CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow cargo update -p some-crate --precise 1.2.3`처럼 그 한 번만 검사를 끌 수 있고, 이후 빌드는 lockfile에 기록된 버전을 정상 정책으로 계속 씁니다.
- 한계도 분명합니다. `cargo install`에는 적용되지 않고, 공개 시각을 레지스트리 타임스탬프에 의존하므로 Git과 로컬 경로 의존성, 해당 메타데이터가 없는 레지스트리는 범위 밖입니다. 정상 수정도 같이 기다려야 하고, 탐지를 피한 악성 릴리스는 쿨다운보다 오래 살아남을 수 있습니다. 저자의 결론은 방어자에게 행동할 시간을 벌어 주는 것이 가치라는 것입니다.

npm의 `minimumReleaseAge`와 같은 계열의 방어를 다른 생태계가 어떤 실패 동작으로 설계했는지 보여 주므로, 의존성 정책을 설계하는 입장에서 비교해 볼 만합니다. 보안 업체 블로그라서 위협을 강조하는 톤이 있지만, 날짜와 시간, 설정 이름은 공개 기록에 기댄 내용입니다.

### CrUX가 SPA 라우트 전환을 별도 뷰로 세기 시작하면 같은 사이트의 지표가 좋아 보입니다

`Harry Roberts` [원문](https://csswizardry.com/2026/10/web-perf-wednesday-013-crux-adds-soft-navigation-core-web-vitals/)

코드를 한 줄도 바꾸지 않았는데 LCP가 좋은 오리진의 비율이 68.3%에서 72.1%로 올라갑니다. 세는 방식이 바뀌었기 때문입니다.

- 2026년 9월 CrUX(Chrome 사용자 실측 데이터) 릴리스가 소프트 내비게이션(SPA의 라우트 전환)을 포함한 실험 지표 세 개를 추가했습니다. `experimental_largest_contentful_paint_with_softnavs`, `experimental_interaction_to_next_paint_with_softnavs`, `experimental_cumulative_layout_shift_with_softnavs`이고 BigQuery, CrUX API, CrUX History API에서 볼 수 있습니다. 하드 내비게이션과 소프트 내비게이션을 합친 75퍼센타일이며 소프트 전용 값이 아닙니다.
- 이전에는 SPA 세션 전체를 긴 페이지 하나로 취급했습니다. 첫 로드를 기록하고, 세션 내내의 상호작용을 그 페이지에 귀속시키고, 레이아웃 이동도 문서 수명 동안 누적했습니다. 새 시리즈는 인식된 라우트 변경을 별도 뷰로 보기 때문에 INP는 뷰마다 평가되고 CLS는 내비게이션마다 초기화됩니다.
- 그래서 수치가 움직입니다. 좋은 LCP 오리진 비율은 68.3%에서 72.1%, 좋은 CLS는 81.7%에서 85.1%, 좋은 INP는 85.4%에서 87.4%, 세 지표를 모두 통과하는 비율은 55.9%에서 59.5%가 됩니다. 저자는 이것이 개선이 아니라 다른 모집단을 재는 것이라고 강조하며, 후속 뷰가 첫 로드의 코드와 자산을 재사용하는 점도 이유로 듭니다.
- 영향은 고르지 않습니다. Google은 오리진의 약 70%에는 소프트 내비게이션 트래픽이 거의 없고, 상위 1,000개 사이트의 35~42%는 페이지뷰의 절반 넘게를 소프트 내비게이션으로 처리한다고 밝혔습니다. 변화는 규모가 크고 SPA 비중이 높은 사이트에 몰립니다. 정식 Core Web Vitals는 그대로이고 2027년 5월 졸업을 목표로 하며, 졸업하면 Search Console도 새 데이터로 바뀝니다.
- 같은 글은 Firefox 158도 다룹니다. `PerformanceResourceTiming.deliveryType`이 캐시에서 온 리소스를 `cache`로 알려 주고, JPEG XL이 기본 활성화되며 Accept 헤더에 `image/jxl`이 붙습니다. Accept로 포맷을 협상하는 이미지 서비스는 앱 릴리스 없이 Firefox에 다른 파일을 주기 시작할 수 있으므로 캐시 키와 Vary를 확인하라고 권합니다.

SPA를 운영하는 팀이 대시보드와 목표치를 하드 내비게이션 기준으로 잡아 두었다면, 졸업 전에 두 시리즈를 나란히 두고 갈라지는 라우트를 찾아야 한다는 실무 순서를 줍니다. 글 끝에 컨설팅 안내가 붙어 있고 수치는 Google 릴리스 노트를 인용한 것입니다.

### Litestream을 Node 패키지로 옮기면 SQLite 백업의 사이드카 프로세스가 사라집니다

`Platformatic` [원문](https://blog.platformatic.dev/sqlite-js-stream-litestream-nodejs)

WAL이 4.1배 커지는 동안 최대 메모리는 1.22배만 늘었고, 이 포트의 코드는 로컬 모델을 돌리는 에이전트가 썼습니다.

- SQLite 파일을 쓰는 중에 `cp`로 복사하면 깨진 스냅샷이 나옵니다. 커밋된 쓰기가 본 파일이 아니라 `-wal` 파일에 있을 수 있고 체크포인트로 언제든 잘릴 수 있기 때문입니다. Litestream은 WAL을 트랜잭션 하나에서 바뀐 페이지를 담은 LTX 파일 열로 바꿔 S3나 로컬 폴더에 쌓고, 복원은 이 파일을 순서대로 재생합니다. 이 포트는 같은 LTX 포맷을 쓰므로 Litestream이 만든 파일을 읽고 그 반대도 됩니다.
- 핵심 주장은 성능이 아니라 배포 방식입니다. Go 바이너리인 Litestream은 앱 옆에서 별도 프로세스로 돌리고 설정 파일과 버전을 따로 관리해야 합니다. `npm install sqlite-js-stream`은 앱 프로세스 안에서 돌고, 내장 `node:sqlite`와 Node의 타입 스트리핑을 써서 빌드 단계도 없습니다. 저자는 이 운영 부담 때문에 팀들이 SQLite 대신 Postgres를 고른다고 봅니다.
- 측정은 작은 규모입니다. 10만 행, 100개 트랜잭션, WAL 3.76MB, localhost 파일 백엔드에서 sync는 약 180~250ms였습니다. 크기를 키운 실험에서 WAL이 1.87MB에서 7.72MB로 4.1배 커질 때 최대 RSS는 99.8MB에서 121.2MB로 1.22배 늘었습니다. 저자 스스로 Litestream과의 직접 비교가 아니며 순수 JS LZ4 코덱은 Go의 SIMD 구현에 질 것으로 예상한다고 밝힙니다.
- 여러 호스트 중 쓰기 호스트를 하나만 고르는 방식은 S3의 `If-None-Match`, `If-Match` 조건부 쓰기로 `lock.json` 임대를 잡는 것입니다. 이는 재해 복구용이지 분산 DB가 아닙니다. 두 호스트의 같은 행이 다른 값이면 기본 호스트의 값만 S3에 남고, 장애 전환 시 스탠바이는 마지막 백업 시점까지의 데이터만 가집니다. 코어 패키지는 아직 배포 전이고 S3 이외의 백엔드는 구현되지 않았습니다.
- 에이전트는 pi 하네스에 DeepSeek V4 Flash 비전 빌드를 vLLM으로 NVIDIA DGX Spark 두 대에서 돌려 썼고, 사람이 계획서를 쓰고 diff를 검토했습니다. 테스트 우선으로 121개 테스트를 유지했고, 에이전트가 "새 파일 포맷으로 올려라"를 오해해 구버전 복원 경로를 통째로 만들었을 때 사람이 잘라냈다고 적었습니다.

SQLite 위에서 서비스를 돌릴 때 백업을 어떻게 앱에 붙일지 고민한다면 WAL과 LTX의 동작 설명이 참고가 됩니다. 에이전트가 만든 포트를 사람이 어디서 막았는지 기록한 점도 검증 체계 관점에서 읽을 만하지만, 성능 비교가 없고 초기 단계라는 점이 한계입니다.

### 에이전트가 UI를 짜는 시대에 웹 컴포넌트의 재사용 논거가 약해졌다고 옹호자가 인정합니다

`Nolan Lawson` [원문](https://nolanlawson.com/2026/10/19/do-web-components-have-a-future-if-nobody-is-writing-them/)

웹 컴포넌트 기반 프레임워크(LWC)를 수년간 만들고 옹호해 온 저자가, Google이 에이전트에게 주는 최신 웹 지침에서 웹 컴포넌트를 쓰라는 권고를 거의 찾지 못했다고 씁니다.

- 출발점은 Google의 Modern Web Guidance입니다. 에이전트가 CSS scroll snap, 스크롤 구동 애니메이션 같은 최신 브라우저 기능을 쓰도록 유도하는 스킬 모음입니다. 저자가 저장소를 보니 처음 6개월 동안 웹 컴포넌트 언급이 거의 없었고, 3주 전에야 커밋 하나가 들어왔으며, 그마저 "커스텀 엘리먼트가 정말 필요한지 먼저 판단하라"는 절이 있습니다. 새 제품을 만드는 에이전트라면 웹 컴포넌트를 고르지 않을 가능성이 크다는 판단입니다.
- 논증의 핵심은 경제성입니다. 웹 컴포넌트는 사람이 HTML을 손으로 치고, 코드가 귀하고, 그래서 재사용이 경제적 필수이던 세계를 전제로 설계되었습니다. 에이전트가 UI를 처음부터 만들면 "공통 표준으로 만들면 재사용하기 쉽다"는 설득력이 약해집니다. 프레임워크를 "에이전트에게 더 낫다는 느낌"으로 갈아엎는 사례가 늘면 그 아래 계층의 가치도 같이 낮아지고, shadcn처럼 보일러플레이트가 장점이 되는 흐름도 같은 방향이라고 봅니다. 사용자 경험상 웹 컴포넌트만 줄 수 있는 것은 없다는 입장이며, 셰도 DOM의 CSS 성능 이점은 컴파일 타임 CSS 스코핑으로 같게 얻는다고 직접 벤치마크했다고 합니다.
- 방어 논거 두 가지를 스스로 "약하다"고 평가합니다. 하나는 마이크로 프런트엔드 격리입니다. 에이전트를 경계 안에 가두는 일과 맞지만 iframe이 더 단단한 경계를 줍니다. 다른 하나는 재사용입니다. 자신이 만든 `<emoji-picker>`처럼 프레임워크와 접점이 적은 독립 컴포넌트는 여전히 웹 컴포넌트가 맞고, 동료 André Staltz의 관찰대로 AI 코딩은 공유 코드를 줄이지 않고 늘리고 있다고 씁니다.
- "에이전트에게는 React가 이미 재사용 계층"이라는 반론에는 동의하지 않습니다. React가 마지막 프레임워크일 리 없고 가상 DOM은 벤치마크에서 여전히 오버헤드라고 보기 때문입니다. 다만 가장 강한 논거는 어떤 프레임워크도 결국 AGENTS.md의 각주일 뿐이라는 것입니다. 자신이 아내를 위해 바이브 코딩한 앱에서 에이전트가 Preact와 Svelte 사이에서 망설이다 Preact를 골랐는데 앱이 동작해서 신경 쓰지 않았다고 합니다.
- 사용자 경험에 직접 닿는 미해결 문제로 서버 사이드 렌더링, 스타일시트 공유, 접근성을 꼽습니다. 이것들은 AI 코딩과 무관하게 남기 때문에 풀어야 승산이 있다고 봅니다. 저자 본인도 자기 사이트의 웹 컴포넌트를 쓰려고 에이전트에게 명시적으로 지시해야 했다고 인정합니다.

공유 라이브러리와 디자인 시스템을 만드는 입장에서는 "이 라이브러리의 소비자가 사람인가 에이전트인가"가 API 설계의 전제를 바꾼다는 질문을 던집니다. 근거는 한 저장소의 지침 문서와 저자의 경험이어서 사용 데이터가 아닌 의견이라는 한계가 있습니다.

### AI 지출이 개발자당 월 수천 달러여도 PR 증가가 곧 생산성이라는 근거는 아직 없습니다

`The Pragmatic Engineer` [원문](https://newsletter.pragmaticengineer.com/p/whats-the-roi-of-software-engineers)

한 퀀트 회사의 AI 비용은 1월 월 50만 달러에서 9월 월 800만 달러로 16배가 됐고, 그 회사는 ROI를 트레이딩 데스크의 이익으로만 잰다고 합니다.

- 저자는 27개 회사의 엔지니어링 리더와 시니어 엔지니어를 취재하고 CodeRabbit과 Gitar의 집계 데이터를 더했습니다. 지표로는 PR 처리량(PR throughput)을 골랐습니다. 대부분의 회사가 이미 갖고 있고, 아직 개발자들이 조작하지 않았고, AI 도입 전후를 비교할 수 있기 때문입니다. CodeRabbit 사용자의 주간 PR은 1년 전보다 113%, 같은 개발자 2만 명을 1년간 추적하면 128% 늘었고, Gitar는 AI 중심 팀이 개발자당 주 60건 이상을 낸다고 봅니다.
- 지출은 회사 규모와 무관했습니다. 직원 2명의 .NET 에이전시는 개발자당 월 3,000달러를 쓰고 하루 PR이 1~2건에서 10건 이상으로, 주 60건 수준으로 늘었다고 합니다. 반면 엔지니어 1,500명의 상장사는 개발자당 월 150달러 한도를 둡니다. 지출은 6~7월에 정점이었고 API 요금제 회사들은 Opus 5.5 혼용과 오픈 모델 이전으로 비용이 대략 절반으로 줄었으며, 보조금이 붙은 구독이 끝나면 청구서가 5~10배가 될 수 있다는 회사도 있었습니다.
- 반례가 많습니다. 월 1,200달러 한도를 두고도 5% 미만만 그 한도에 닿는 한 회사는 PR 수는 늘었지만 머지 속도는 크게 달라지지 않았고, 사람 리뷰가 "아예 필요 없는 변경이나 10배 커진 변경"을 잡는다고 합니다. 다른 회사는 PR 빈도는 그대로인데 PR 크기가 코드 줄 수 기준 3배가 됐습니다. 또 다른 회사는 4건에서 8건으로 2배가 됐고, 한 엔지니어는 품질을 지키는 팀에서는 속도가 크게 늘지 않는다고 말합니다.
- 효과가 확실했다는 영역은 이슈 분류(하루 걸리던 일이 몇 분과 최대 1시간의 사람 검증으로), 코드 이력 조사(하루 이틀에서 몇 분으로), 복잡한 기능의 시제품(1~2주에서 몇 시간으로)이었습니다.

PR 수와 PR 크기가 갈라지고 머지 속도는 그대로라는 사례가 한 글 안에 함께 있어서, PR 수로 AI 도입 효과를 재는 방식이 무엇을 놓치는지 보여 줍니다. 수집된 본문이 중간까지라 글의 결론부는 확인하지 못했고, 27개 회사의 익명 자기 보고라는 한계가 있습니다.

### Uber의 AI 도구는 1년 만에 만든 것이 아니라 10년 치 개발자 도구 위에 얹은 것입니다

`The Pragmatic Engineer` [원문](https://newsletter.pragmaticengineer.com/p/ubers-ai-infra-from-the-inside)

Uber는 올해 CI 작업이 12개월 만에 두 배 넘게 늘어 내부적으로 CI에 "code red"를 선언했습니다.

- 2023년에 AI로 만드는 모든 것을 모델과 하네스에 종속되지 않게 하기로 하고 Model Gateway를 만들었습니다. Anthropic, OpenAI, 그 밖의 벤더 모델과 자체 운영 오픈 모델을 바꿔 끼울 수 있고, 그 위에 보안팀이 요청과 응답을 검사하고 지연을 재는 AI Guard, 사용자별 지출 추적, 감사 로그를 얹었습니다. AIFX는 Claude Code, Codex, OpenCode를 감싸서 엔지니어가 하네스를 바꿔도 설정, 스킬, 플러그인이 따라가게 합니다.
- 비용은 지출 등급제로 관리합니다. 한도에 닿으면 매니저가 그 달에 한해 승인하고, 비용 개선 팁을 주는 CostCheck 플러그인이 있으며, 최근 몇 달간 토큰 비용을 약 50% 줄였다고 합니다.
- 모든 PR은 여전히 사람이 리뷰하고, 코드 리뷰가 병목이라고 인정합니다. 그래서 리뷰어가 보는 시점에는 AI 리뷰가 이미 돌았고, 가능하면 기능 스크린샷과 영상이 붙고, 위험 점수가 매겨져 있습니다. CI 폭증에는 린트, 빌드, 템플릿 규칙 같은 가벼운 검사를 `afx validate` 명령으로 에이전트가 PR 열기 전에 돌리도록 안쪽 루프로 옮겼습니다.
- 생산성 지표도 바꿨습니다. PR이 프로덕션에 가기까지 걸리는 시간은 PR을 수십, 수백 개 만들 수 있게 되자 의미가 줄었습니다. 그래서 PR을 기능, 버그 수정, 유지보수, 테스트, 문서로 태깅하고, 기능 PR 비율이 오르고 유지보수 PR 비율이 내려가는지 봅니다.
- 도구가 빨리 나온 이유는 기반이 있었기 때문이라고 설명합니다. 2025년의 Minion은 2017년에 만든 DevPods 위에서 돌고, MCP 게이트웨이는 기존 Thrift와 Protobuf 레지스트리 덕에 빨리 만들었으며, 인터뷰이는 엔지니어를 편하게 한 것이 에이전트도 편하게 한다고 말합니다.

대규모 프런트엔드 인프라와 공통 도구를 만들어 온 입장에서 "개발자 경험 투자가 에이전트 시대의 기반"이라는 주장과, 리뷰 병목에 사전 검증을 앞당기는 해법이 참고가 됩니다. 한 임원의 회사 소개 인터뷰 요약이라 수치는 대부분 자체 보고이고, 후원사 안내가 본문 앞에 섞여 있습니다.
