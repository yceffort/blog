## 오늘 하나만 본다면

### 에이전트가 코드를 쓰는 시대에 웹 컴포넌트의 존재 이유는 약해졌다

`Nolan Lawson` [원문](https://nolanlawson.com/2026/10/19/do-web-components-have-a-future-if-nobody-is-writing-them/)

웹 컴포넌트 진영에서 수년을 일한 저자가 직접 "웹 컴포넌트의 핵심 가치 제안이 에이전트 코딩으로 심하게 약해졌다"고 인정합니다.

- 계기는 Chrome 팀이 만든 Modern Web Guidance입니다. 에이전트가 더 최신의 브라우저 기능을 쓰도록 유도하는 스킬 묶음인데, 저자가 코드를 열어 보니 첫 6개월 동안 웹 컴포넌트 언급이 거의 없었고 3주 전에야 커밋 하나가 들어왔습니다. 그마저 "커스텀 엘리먼트가 정말 필요한지부터 판단하라"는 절이 있어서, 새 제품을 만드는 에이전트가 웹 컴포넌트를 고를 가능성은 낮다고 봅니다.
- 핵심 논증은 경제성입니다. 웹 컴포넌트는 사람이 HTML을 손으로 치고 코드가 귀하던 시대에 재사용이 경제적 필수였기 때문에 설계됐습니다. 이제는 프레임워크 갈아엎기도 프롬프트 하나로 가능해서 "공통 표준으로 만들면 재사용이 쉽다"는 설득력이 떨어집니다. 프레임워크 층을 일회용으로 보기 시작하면 그 아래 층에 가치를 두기는 더 어렵다는 논리입니다.
- 최종 사용자 경험 측면의 이점도 약합니다. Shadow DOM의 CSS 성능 이득은 저자가 오래 벤치마크했지만 Svelte, Vue, Tailwind가 쓰는 빌드 타임 CSS 스코핑으로 같은 효과를 얻을 수 있다고 합니다. shadcn처럼 부품을 복사해 마음대로 고치는 방식이 이미 대세였고, LLM 시대에는 "긴 보일러플레이트"가 오히려 장점이 됩니다.
- 남는 근거는 약하다고 스스로 단서를 답니다. 하나는 마이크로 프론트엔드입니다. 에이전트 무리를 서로 간섭하지 않게 격리한다는 면에서는 쓸모가 있지만, 더 강한 경계인 iframe이 이미 있습니다. 다른 하나는 `<emoji-picker>`처럼 프레임워크와 접점이 적은 독립 컴포넌트의 배포 형식입니다.
- 사용자에게 직접 닿는 문제인 서버 사이드 렌더링, 스타일시트 공유, 접근성이 여전히 미해결이라고 지적합니다. 이것은 AI 코딩과 무관하게 남는 약점이라 고쳐지지 않으면 승산이 없다는 결론입니다. 저자는 에이전트가 Preact와 Svelte 사이에서 망설이다 Preact를 고른 앱을 만들었지만 동작만 하면 상관없었다고 덧붙입니다.

사내 디자인 시스템이나 공통 컴포넌트 라이브러리를 어떤 형식으로 배포할지 고민하는 팀이라면 "누가 이 코드를 읽고 쓰는가"라는 전제를 다시 점검할 근거가 됩니다. 다만 저자의 주장은 에이전트가 새 제품을 처음부터 짠다는 시나리오 중심이고, 대규모 기존 코드베이스나 조직 간 계약 문제는 거의 다루지 않습니다.

## 읽을 만한 것

### Cloudflare와 VoidZero가 Rust로 TypeScript를 다시 포팅했고, 시간 대부분은 AI가 아니라 호환성 유지에 든다

`Cloudflare` [원문](https://blog.cloudflare.com/typescript-rust-port/)

TypeScript 7.0(Go 포팅판) 대비 최대 8배 빠르고 메모리를 약 70% 덜 쓰는 Rust 포팅 tsrs가 나왔는데, 저자들은 "포크가 아니다"라고 강조합니다.

- Cloudflare와 VoidZero가 Owner.com의 Max Schwenk와 함께 만들고 Oxc 툴체인 안에서 키웁니다. 같은 수의 타입 체크 워커로 비교했을 때 TypeScript 7.0보다 최대 8배 빠르고 메모리는 약 70% 적게 쓴다고 합니다. 이 숫자는 TypeScript 팀과 설정을 맞춰 잰 것이지만 글쓴이 쪽이 낸 벤치마크입니다.
- 같은 시점의 TypeScript 7.1 베타는 7.0보다 최대 2.5배 빠르며, 그 최적화 일부는 tsrs에서 upstream으로 올라간 것이라고 합니다. tsrs는 npm의 `tsrs` 패키지로 실험판을 설치해 써 볼 수 있습니다.
- "왜 지금 Rust인가"에 대한 답은 두 가지입니다. 하나는 AI 모델이 대규모 포팅을 며칠 만에 거의 혼자 해내게 되어 slopfork부터 충실한 포팅까지 시도가 쏟아지고 있다는 점입니다. 다른 하나는 WebAssembly입니다. Go를 Wasm으로 컴파일하면 가비지 컬렉터까지 같이 들어가지만 Rust는 게스트와 호스트 사이 메모리 상호작용이 단순해서, 브라우저나 Workers 같은 샌드박스에서 개발 툴체인 전체를 돌리기에 유리하다는 주장입니다.
- 언어 설계는 전적으로 TypeScript 팀이 정하고 포팅은 원본 구현을 엄격히 따릅니다. 유지 방법은 Cloudflare가 Next.js를 따라가는 Vinext에서 쓰는 방식입니다. 매일 아침 에이전트가 upstream 변경을 검토해 이슈를 열고, 매일 밤 Next.js 테스트 스위트를 돌려 호환성 표를 다시 만듭니다. 진단 메시지 출력 순서 같은 차이는 아직 남아 있고 정식 릴리스 전에 줄이겠다고 합니다.

TypeScript 타입 체크가 CI와 에디터 대기 시간의 큰 몫인 팀에게 "다음 속도 향상이 어디서 오는가"를 보여 주는 글입니다. 한계는 벤치마크가 자체 보고이고 아직 실험판이며, 장기 유지가 에이전트 파이프라인에 기대고 있다는 점입니다.

### Chrome의 CrUX가 SPA 소프트 내비게이션을 포함한 Core Web Vitals를 실험 공개했고 합격률이 오른다

`Harry Roberts` [원문](https://csswizardry.com/2026/10/web-perf-wednesday-013-crux-adds-soft-navigation-core-web-vitals/)

같은 사이트인데 SPA의 소프트 내비게이션을 포함하면 세 가지 지표를 모두 통과하는 origin 비율이 55.9%에서 59.5%로 올라갑니다.

- 지금까지 CrUX(Chrome 사용자 실측 데이터)는 SPA 세션 전체를 긴 페이지 하나로 봤습니다. 첫 로드를 기록하고, 세션의 모든 상호작용을 그 페이지에 귀속하고, 레이아웃 이동을 문서 수명 동안 누적했습니다. 9월 CrUX 릴리스에 추가된 실험 지표 3종(`experimental_largest_contentful_paint_with_softnavs`, `..._interaction_to_next_paint_with_softnavs`, `..._cumulative_layout_shift_with_softnavs`)은 인식된 라우트 변경을 별도 뷰로 셉니다.
- 9월 릴리스 노트의 수치는 안정판 대비 좋은 LCP 비율이 68.3%에서 72.1%, CLS가 81.7%에서 85.1%, INP가 85.4%에서 87.4%입니다. 저자는 이 상승이 사이트가 빨라진 것이 아니라 측정 모집단이 달라진 결과라고 읽습니다. 후속 뷰는 첫 로드의 코드와 에셋을 재사용하고, INP는 세션 내 가장 느린 상호작용 하나를 끌고 가는 대신 뷰마다 평가되고, CLS는 내비게이션마다 초기화되기 때문입니다.
- 이 새 지표는 소프트 내비게이션만 본 값이 아니라 하드와 소프트를 합친 75번째 백분위수입니다. Google은 origin의 약 70%는 소프트 내비게이션 트래픽이 거의 없고, 상위 1,000개 사이트의 35~42%는 페이지뷰의 절반 넘게를 소프트 내비게이션으로 처리한다고 밝힙니다. 변화는 대규모 SPA에 집중됩니다.
- 안정판 Core Web Vitals는 그대로이고, 피드백을 반영해 2027년 5월에 정식화하는 것이 목표입니다. 정식화되면 Search Console도 새 데이터로 바뀝니다. 저자는 지금을 비교 기간으로 쓰라고 권합니다. 두 시리즈가 갈라지는 라우트와 기기를 찾고, 하드 내비게이션 전용 데이터를 쓰는 대시보드와 알림과 목표를 기록해 두라는 것입니다.
- 같은 글에서 Firefox 158이 `PerformanceResourceTiming.deliveryType`(`cache` 값)과 JPEG XL 기본 활성화(Accept 헤더에 `image/jxl` 추가)를 넣은 점도 다룹니다. 이미지를 Accept 헤더로 협상하는 CDN은 애플리케이션 릴리스 없이 Firefox에 다른 에셋을 내보낼 수 있어서, 캐시 키와 `Vary` 처리를 점검하라고 합니다.

SPA 기반 서비스의 성능 목표와 알림을 운영하는 팀이라면 내년 5월 전환 전에 어떤 지표가 어떻게 움직일지 미리 볼 수 있습니다. 마지막에 저자의 컨설팅 안내가 붙어 있고, 지표는 실험 단계라 변경될 수 있습니다.

### Cargo가 Rust 1.100에서 의존성 쿨다운을 넣는다, 실패하는 쪽을 기본으로 택한 이유가 있다

`Socket` [원문](https://socket.dev/blog/rust-cargo-cooldowns)

악성 crate 세 개가 crates.io에 올라와 있던 시간은 86분, 90분, 107분이었습니다.

- 8월에 공격자가 arrayref, internment, append-only-vec의 침해된 버전을 올렸습니다. 빌드 스크립트가 페이로드를 내려받는 악성 crate proc-macro1에 의존하게 만든 것입니다. Rust 보안 대응팀에 따르면 이 릴리스들은 각각 86분, 90분, 107분 만에 제거됐습니다. 두 시간도 안 되지만 그 사이 개발자 머신과 CI로 이미 들어올 수 있습니다.
- Rust 1.100(11월 12일 예정)은 `.cargo/config.toml`의 `[registry] global-min-publish-age = "7 days"` 같은 설정으로 게시된 지 일정 시간이 안 된 버전을 해석에서 제외합니다. 기본값은 0이라 업그레이드만으로는 보호가 생기지 않고 직접 켜야 합니다.
- 맞는 후보가 없으면 더 오래된 버전으로 조용히 넘어가지 않고 해석이 실패합니다. 이것은 의도입니다. 공격자가 악성 업데이트를 올리고 안전한 버전을 yank(철회)하면 "오래된 쪽 선호" 정책은 악성 쪽으로 밀려날 수 있고, 실제로 8월 공격에서 arrayref의 정상 버전이 yank됐습니다. 이미 `Cargo.lock`에 기록된 버전은 유지됩니다.
- 급한 수정은 `CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow cargo update -p some-crate --precise 1.2.3`처럼 한 번만 검사를 끌 수 있습니다. 한계도 분명합니다. `cargo install`에는 적용되지 않고, 게시 시각 메타데이터에 의존해서 Git이나 경로 의존성과 이를 제공하지 않는 레지스트리는 대상이 아닙니다. 탐지를 피한 악성 릴리스는 쿨다운보다 오래 버틸 수 있습니다.

npm에서 pnpm의 `minimumReleaseAge`로 같은 문제를 다뤄 본 팀이라면 같은 설계 논점(대기 시간, 실패 정책, 예외 경로)이 다른 생태계에서 어떻게 정해지는지 비교할 수 있습니다. 출처가 보안 업체 블로그라 위협 서술에 힘이 들어가 있고, 효과를 수치로 검증한 글은 아닙니다.

### 이틀 만에 AI가 만든 가짜 통계 5만 건이 7개월째 ChatGPT에 인용되고, 은행 리서치까지 흘러들었다

`peec.ai` (Hacker News 경유) [원문](https://peec.ai/blog/publish-stats-get-cited-the-tactic-that-put-my-data-all-over-the-web)

작성자는 GPT-4.1로 하루 만에 가짜 통계 5만 건짜리 사이트를 만들었고, Google은 색인에서 지웠지만 ChatGPT는 7개월째 계속 가져다 씁니다.

- 새 도메인 stateglobe.com에 SEO, 이커머스 등 주제와 200개 국가의 통계를 GPT-4.1로 생성했고 숫자는 하나도 검증하지 않았습니다. 프롬프트는 국가와 주제 목록에 두 문장이 전부였고 비용은 목록형 글 1만 5천 건을 합쳐 약 50달러입니다. 글쓴이는 GEO(생성형 AI 검색 노출 최적화) 리서치 회사 Peec AI 소속입니다.
- Google에서는 공개 직후 두 번의 업데이트로 노출이 무너졌습니다. 반면 최근 30일 Cloudflare 크롤 데이터에서 봇 요청이 60만 건이 넘고 그중 약 7만 2천 건이 `ChatGPT-User`입니다. 학습용 크롤이 아니라 사용자 질문에 답하는 도중 실시간으로 페이지를 여는 에이전트입니다. GA4로는 ChatGPT 유입이 1만 세션이 넘고, 이 사이트를 링크한 도메인이 330개 이상이며 Shopify, DHL, Bluehost도 있습니다.
- 가짜 숫자는 학술 논문, 카타르 최대 금융그룹의 투자 리서치, 인도 경제 매체, 캐나다 인플루언서 커뮤니티 보고서에 인용됐습니다. 숫자가 참이 된 것은 아니지만 인용이 쌓일수록 출처가 있는 통계처럼 보이는 "인용 세탁"이 일어난다고 설명합니다. 이 페이지가 웹 크롤을 거쳐 학습 데이터로 들어가면 다음 모델이 그 숫자를 "안다"고 여길 수 있다고 경고합니다.
- 메커니즘은 이렇습니다. LLM이 글을 쓰다가 근거가 빈 곳을 만나면 "통계, 데이터, 올해 연도"를 붙인 하위 질의로 검색합니다. 검색 근거를 붙여 답하는 단계는 지연과 비용 한도가 빡빡해서 숫자를 교차 검증하지 않고, 리랭커는 관련성을 점수화할 뿐 진실성을 보지 않습니다. 통계 페이지는 제목과 URL에 연도가 들어 있어 최신성 신호도 얻습니다.
- 글 후반은 진짜 데이터로 통계 페이지를 만드는 요령(문장 하나에 주장 하나, 숫자 옆에 출처와 연도 표기, 헤딩을 하위 질의 형태로 맞춤)이고 홍보 성격이 강합니다. 저자는 이것을 가짜 콘텐츠 매뉴얼이 아니라 연구로 공유한다고 말하며, 글쓰기와 리서치 워크플로에 출처 검증이 필수가 되어야 한다고 결론짓습니다.

LLM이 검색한 숫자를 신뢰하는 구조적 이유를 실측으로 보여 주므로, 사내 에이전트가 웹에서 가져온 수치를 PR이나 문서에 쓰는 흐름을 설계하는 사람에게 닿습니다. 단일 실험이고 ChatGPT 내부는 외부 관찰로 추정한 것이며, 글쓴이가 GEO 업체라는 이해관계가 있습니다.

### 27개 회사 조사: AI 지출이 크게 늘었어도 PR 처리량의 증가는 회사 문화와 품질 기준에 따라 제각각이다

개발자 1인당 월 3,000달러를 쓰는 2인 .NET 회사는 PR을 5~10배 늘렸고, 월 2,200달러를 쓴 다른 엔지니어의 팀은 PR 빈도가 거의 그대로입니다.

- 저자는 PR 처리량을 비교 지표로 고릅니다. 대부분의 회사에 이미 있고 아직 덜 조작됐고 AI 도입 전후를 비교할 수 있기 때문입니다. 27개 회사의 엔지니어링 리더와 시니어 이상을 취재했고 CodeRabbit과 Gitar의 집계도 받았습니다. CodeRabbit 사용 개발자의 주간 PR은 1년 전보다 113% 늘었고, 같은 2만 명을 1년 추적한 값도 128%로 비슷합니다. Gitar는 AI 네이티브 팀이 개발자 1인당 주 60개 넘게 올린다고 봅니다.
- 지출 패턴은 회사 규모와 무관합니다. 직원 1,500명 상장사가 월 150달러로 제한하는 반면 2인 회사가 3,000달러를 씁니다. 한 퀀트 회사는 1월 월 50만 달러에서 9월 800만 달러로 16배가 됐고, 1인당 평균이 80달러에서 1,600달러로 올랐으며 가장 많이 쓰는 사람은 개발자가 아니라 트레이더입니다. 지출은 6, 7월에 정점을 찍고 API 요금제 기준으로 대략 절반으로 떨어졌는데, 원인으로 Opus 5.5 전환과 오픈 모델 이동이 꼽힙니다.
- 품질을 유지하려는 팀은 속도가 별로 안 오릅니다. 한 스태프 엔지니어는 "사람 리뷰가 에이전트와 에이전트 리뷰가 놓치는 불필요한 변경이나 열 배 커진 변경을 잡는다"고 말하고, 품질 기준을 AI 이전처럼 유지하는 팀은 개발 속도가 크게 늘지 않았다고 전합니다. 이득은 고객 이슈 분류(하루 걸리던 일이 몇 분과 최대 1시간 검증), 코드 이력 조사, 프로토타입에서 컸습니다.
- 숫자가 반대로 가는 사례도 있습니다. 한 회사는 PR 빈도는 그대로인데 PR 크기가 3배(변경당 코드 줄 수)가 됐고, 저자는 LLM이 장황한 탓일 수 있다고 추측합니다. 보조금이 붙은 구독이 끝나면 비용이 5~10배가 될 수 있다고 걱정하는 회사들도 있습니다. 한도를 둔 회사에서는 "쉽게 우회된다"는 증언이 흔합니다.
- 이 글은 조사 방법의 한계를 갖습니다. 27곳은 저자가 주변에 물어 모은 표본이고, 대부분 익명이며 다수가 숫자 없이 기억에 의존한 증언입니다. "AI의 ROI"는 아직 답할 수 있는 회사가 거의 없다는 것이 저자의 결론입니다.

AI 도구 예산과 리뷰 병목을 팀 차원에서 설계하는 사람에게 다른 회사의 한도, 사용 규칙, PR 크기 변화를 비교할 기준점이 됩니다. 인과가 아니라 상관을 보여 주는 사례 모음이고 제가 읽은 본문은 중간에 잘려 있어서 뒷부분 사례는 확인하지 못했으니, 통계로 인용하기보다 질문 목록으로 쓰는 편이 안전합니다.

### Vercel이 어떤 코딩 에이전트 하네스든 크래시 후 이어서 돌리게 하는 durable-harness를 공개했다

`Vercel Blog` [원문](https://vercel.com/blog/making-every-harness-durable)

에이전트 턴 도중 함수가 타임아웃으로 죽어도, 이미 끝난 모델 호출은 로그에서 읽어 오기 때문에 토큰 비용을 두 번 내지 않습니다.

- 문제 설정은 이렇습니다. Claude Code나 Codex 같은 하네스는 로컬에서는 같은 디스크의 세션 기록 덕에 중단된 일을 쉽게 재개하지만, 클라우드의 VM과 영구 저장소 조합은 어떤 모델 호출과 도구 호출이 끝났는지 기록하지 않아서 크래시나 네트워크 오류는 작업 손실로 이어집니다. durable-harness는 Pi, OpenCode, Codex, Claude Code 같은 기존 하네스를 수정 없이 바깥에서 감쌉니다.
- 동작은 write-ahead 로그입니다. 모델 호출과 도구 호출을 실행하기 전에 의도를, 끝난 뒤에 결과를 Workflow SDK의 World(로그, 큐, 스트림을 묶은 인터페이스)에 적습니다. 턴 자체는 큐 메시지가 받쳐서, 함수가 죽으면 큐가 새 함수에 턴을 넘기고 로그를 읽어 이어 갑니다. Claude Code의 transcript나 Codex의 rollout 같은 자체 세션 파일도 로그로 미러링해서 새 샌드박스에서 복원합니다.
- 중단된 도구 호출은 `replay` 정책으로 갈립니다. `'safe'`(조회 등)는 다시 실행하고, `'never'`(환불, PR 댓글 등)는 다시 실행하지 않고 모델에게 "호출이 이미 일어났을 수 있다"고 알려 확인하게 합니다. 지정하지 않은 도구도 같은 식으로 "실행됐을 수 있음"으로 돌아갑니다.
- World는 교체 가능합니다. Vercel에서는 Vercel World, 개발 중에는 로컬 파일, 자체 서버에서는 Postgres, MongoDB, Redis, Turso를 쓰고, 환경 변수 두 개(`WORKFLOW_TARGET_WORLD`, `WORKFLOW_POSTGRES_URL`)로 Postgres로 옮깁니다. 파일은 세션 로그 안의 가상 워크스페이스 `virtual()`(셸은 네트워크와 함수 파일에 못 닿음), 메모리 `virtual({ durable: false })`, 세션 전용 Vercel Sandbox `sandbox()` 중 고릅니다. Claude Code와 Codex는 진짜 셸이 필요해서 항상 Sandbox에서 돕니다.
- 할 일 목록 같은 세션 상태는 로그 안에 타입이 있는 JSON "document"로 저장되어 도구 결과와 같은 커밋으로 기록되고, 앱이 별도 DB 없이 읽을 수 있습니다. Agent Runs 화면은 크래시 후 재개된 턴도 하나의 트레이스로 보여 줍니다.

장시간 도는 에이전트를 서버 쪽에서 운영하려는 팀에게 "재시도 안전성"을 도구 단위로 선언하는 설계가 참고가 됩니다. 제품 공개 글이라 장애 사례나 성능 수치는 없고 Vercel의 Workflow SDK에 묶인 설계라는 점을 감안해야 합니다.

## 보안과 릴리스

- [Security advisory: Critical remote code execution vulnerabilities, update now](https://www.php.net/archive/2026.php#2026-10-21-5) `php.net` (Hacker News 경유) **보안, Critical.** PHP 8.5.12, 8.4.27, 8.3.36, 8.2.35가 인증 없이 원격 코드 실행이 가능한 두 취약점(CVE-2026-109618 메모리 부족 처리 중 요청 데이터 손상, CVE-2026-109619 해제된 메모리를 가리키는 요청 상태 잔존, 둘 다 CVSS v4.0 9.2)을 고쳤습니다. 내가 할 일: PHP를 쓰는 서버가 있으면 패치 버전으로 올리고, 당장 못 올리면 `session.upload_progress.enabled=0`과 낮은 `post_max_size` 같은 완화책을 쓰되 완전한 보호가 아니라는 점을 기억해야 합니다.
- [8 eMudhra certificates are compromised. Here's what you need to know](https://blog.cloudflare.com/emudhra-certificate-compromise/) `Cloudflare` **보안.** 인도 인증기관 eMudhra의 중간 인증서 8개의 약한 개인 키가 노출되어, 공격자가 임의 도메인의 위조 인증서로 서버를 사칭할 수 있습니다. 내가 할 일: 번들한 CA 신뢰 저장소가 있는 SDK, 베이스 이미지, 런타임을 업데이트해 다시 배포하고, 인증서 오류가 뜨더라도 검증을 끄지 말아야 합니다.
- [Beyond the patch: Protecting your NetScaler gateway against future vulnerabilities](https://blog.cloudflare.com/protect-your-netscaler-gateway/) `Cloudflare` **보안.** Citrix NetScaler Gateway의 인증 전 명령 실행 취약점(CVE-2026-88771)이 실제 악용 중이며, 패치 이후에도 로그인 페이지를 SSO 뒤로 옮기고 원본 서버 직접 접속을 막으라고 권합니다. 내가 할 일: NetScaler를 운영하면 먼저 패치하고 침해 여부를 점검합니다.
- [pnpm 12.15.0](https://pnpm.io/blog/releases/12.15.0) `pnpm` **보안.** 레지스트리가 요청한 것과 다른 이름의 패키지 메타데이터를 돌려주면 `ERR_PNPM_REGISTRY_NAME_MISMATCH`로 실패합니다. 전에는 메타데이터의 이름으로 설치해서 요청한 패키지 기준의 `allowBuilds` 규칙이 적용되지 않았습니다. 내가 할 일: 12.x를 쓰면 올립니다. 이 릴리스는 `pnpm-workspace.yaml`의 `include`로 설정 분할, `lockfile.integrityTarget: tar`, zstd 응답 지원, macOS 설치 속도 개선(1,352개 패키지 2.2초에서 1.3초)도 담습니다.
- [Announcing TypeScript 7.1 Beta](https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta/) `TypeScript` 환경 모듈 선언에서 import attributes(`declare module "*" with { type: "css" }`)를 지원하고, 소스 단계 import(`import source`), `--target es2026`, 구문과 의미 분석용 새 API(`typescript/sync`, `typescript/async` 등 진입점)가 들어옵니다.
