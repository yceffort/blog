## 오늘 하나만 본다면

### 정상 trusted publishing 파이프라인이 유효한 provenance를 붙여 악성 npm 패키지를 배포했습니다

`Socket` [원문](https://socket.dev/blog/bee-js-compromise?utm_medium=feed)

토큰 없이 OIDC로 배포하는 trusted publishing과 유효한 SLSA provenance를 모두 갖춘 패키지가, 릴리스 이벤트 하나만으로 악성 코드를 npm에 올렸습니다.

- 11월 9일 Ethersphere의 @ethersphere/bee-js 13.3.0에서 scripts/generate-version.cjs가 원격 코드 로더로 바뀌고 postinstall 훅으로 승격됐습니다. 이 패키지의 177개 이전 버전에는 설치 시점 훅이 하나도 없었습니다. 로더는 api.frameworkmetrics.xyz에서 받은 응답을 `new Function`으로 실행하며, 환경이나 CI 여부를 확인하는 조건이 없습니다. npm은 게시 약 75분 뒤에 이 버전을 내렸고, 같은 계열의 Swarm Desktop 0.56.2 GitHub 릴리스는 약 8시간 30분 동안 남아 있었습니다. 이 릴리스는 Apple 서명과 공증까지 거쳐 자동 업데이트로 배포됐습니다.
- 우회로는 CI 설계의 틈이었습니다. 공격자는 PR이나 브랜치에 속하지 않는 서명 없는 커밋을 만들고 그 태그로 GitHub 릴리스를 발행했습니다. 이 저장소의 npm 배포 워크플로는 push 이벤트에서만 테스트와 검사 잡을 돌리고, 릴리스 이벤트에서는 그 잡들을 건너뛴 채 publish 잡을 통과시킵니다. publish 환경에는 승인자도 태그 정책도 없어서 배포가 생성부터 성공까지 73초 만에 끝났습니다. 토큰은 필요 없었고, 정상 워크플로가 공격자의 커밋을 정상적으로 게시했습니다.
- 진입 경로는 두 GitHub 계정 탈취로 추정됩니다. 하나는 2021년부터 있던 메인테이너 계정이고 다른 하나는 릴리스 자동화 계정입니다. 이틀 전인 11월 6일에는 같은 공격자가 CI 비밀값을 빼내려다 실패했는데, 그 시도로는 두 계정의 자격 증명을 얻지 못했으므로 탈취는 그 이전에 일어났고 경로는 아직 설명되지 않았습니다. 비밀값 수집 시도는 `toJSON(secrets)` 전체 덤프에서 시작해 PAT, 코드 서명 자료, NPM_TOKEN으로 좁혀지며 72분 동안 열한 번 수정됐습니다. 저장소에 없는 시크릿 이름까지 열거한 점으로 보아 짐작에 의존한 시도로 Socket은 평가합니다.
- 로더 뒷단은 Ethereum 스마트 컨트랙트에서 C2(공격 서버) 주소를 읽는 구조입니다. 이 컨트랙트와 이를 관리하는 지갑은 10월 1일 Pluto Security가 분석한 Open VSX 확장 캠페인(SleepyDuck)과 같습니다. 설치가 실패했다고 안전한 것도 아닙니다. 응답이 올바른 JavaScript가 아니거나 도중에 끊기면 처리되지 않은 promise rejection으로 설치가 실패하지만, 그 전에 요청은 이미 나간 뒤입니다. npm 11 이하, Yarn Classic, 4.14.0 미만 Yarn Berry는 postinstall을 기본 실행하고, npm 12, pnpm 10 이상, Yarn Berry 4.14.0 이상, Bun, Deno는 검토 전 의존성 스크립트를 기본으로 건너뜁니다.

공급망 보안에서 provenance가 "누가 어디서 빌드했는가"만 보증하고 "그 커밋이 정당한가"는 보증하지 않는다는 점을 실제 사례로 보여줍니다. 릴리스 워크플로에 승인자와 브랜치 조건을 걸었는지 점검하기에 좋은 체크리스트입니다. 보안 벤더 한 곳의 분석이고 유출 여부는 "중간 정도의 확신으로 없음"이라는 평가에 그칩니다. 본문 뒷부분(후속 단계, IOC)은 이번 요약에서 읽지 못했습니다.

### 에이전트가 쓴 PR 설명은 정확해도 읽히지 않으니 사람이 쓴 한 단락만 앞에 두고 나머지는 접습니다

`Simon Willison` [원문](https://simonwillison.net/2026/Nov/9/details-summary/)

에이전트가 쓴 PR 설명이 정확하고 완전할수록, 읽는 사람은 "이걸 다 읽을 수는 없다"는 반응부터 하게 됩니다.

- 저자의 변경 대부분은 Claude Code나 Codex가 연 PR로 들어옵니다. 에이전트의 PR 설명은 문제, 상세한 해법, 검증 단계까지 담고 있어 슬롭(대충 찍어낸 글)은 아니지만 슬롭처럼 읽힙니다. 쓰는 데 걸린 시간보다 읽는 데 걸릴 시간이 길 것 같다는 인상이 들고, 그 필자가 본인이어도 마찬가지라고 합니다.
- 해법은 사람의 편집 판단을 맨 앞에 두는 것입니다. PR 첫 단락에 "이 PR이 무엇을 위한 것이고 더 볼 가치가 있는지"를 사람이 읽고 확인한 가장 짧은 글로 쓰고, 필요하면 스크린샷을 붙입니다. 그 아래 에이전트가 쓴 긴 글은 HTML `<details><summary>` 안에 넣어 접습니다. summary에는 "Claude Opus 5.5 Medium"처럼 모델 이름과 노력 수준을 적어 누가 쓴 글인지 분명히 합니다.
- GitHub Markdown은 이 태그를 지원하므로 이슈 댓글과 PR 설명에 그대로 붙일 수 있습니다. 저자는 datasette, llm 저장소의 PR 다섯 건을 예로 듭니다. 예를 들어 JS 파일 하나(약 220KB)가 편집 권한이 없는 사용자에게도 모든 페이지에서 로드되던 문제를, "이제 편집 권한이 있는 사용자가 처음 상호작용할 때만 로드한다"는 한두 문장으로 요약해 열어 둡니다.
- 직접 쓰지 않는 경우도 있습니다. 에이전트가 낸 긴 글 속에 이미 필요한 요약이 묻혀 있으면 그것을 끌어옵니다. 저자가 독자에게 하는 약속은 "짧은 첫 단락은 내가 읽을 가치가 있다고 판단한 내용"이라는 것입니다.

AI가 코드를 쓰는 시대에 리뷰어의 주의력을 어떻게 아낄지를 PR 템플릿 수준에서 해결한 작은 규율입니다. 팀 PR 컨벤션에 바로 옮길 수 있습니다. 다만 효과는 저자 본인의 체감이고, 팀에서 측정한 근거는 없습니다.

### 상주 에이전트의 비용은 지능이 필요한 두 지점에만 LLM을 쓰고 나머지는 코드로 처리해서 줄입니다

`Grafana Labs` [원문](https://grafana.com/blog/run-cost-effective-always-on-agents-to-monitor-your-environment-the-engineering-behind-watchers/)

10분마다 에이전트가 돌면 한 달 4,320회인데, 한 번의 조사에 0.56달러에서 1.26달러가 들면 감시 하나가 월 수천 달러가 됩니다. Grafana는 같은 일을 중앙값 월 5달러 미만으로 돌린다고 주장합니다.

- 감시라는 일을 세 가지로 쪼갭니다. 무엇을 볼지와 정상이 무엇인지 정하기, 같은 신호를 정상과 반복 비교하기, 사람을 깨울 만한지 판단하기입니다. 첫 번째와 세 번째만 지능이 필요하고, 가운데는 쿼리와 통계 계산이라 코드가 잘합니다. 그래서 첫 번째는 도구를 쥔 유능한 모델이 한 번만 하고, 두 번째는 일반 코드가, 세 번째는 도구 없이 작은 모델을 한 번 호출하는 방식으로 나눕니다.
- 처음 만들 때 도는 캘리브레이션 에이전트가 가장 비싼 부분입니다. 알림 규칙과 대시보드를 먼저 읽어 팀이 합의한 임계값을 가져오고, 지난 한 주 동안 여러 시점의 값을 재서 요일과 시간대별 주기를 파악합니다. 모든 검사를 실제 데이터로 검증한 뒤 정상 범위와 알려진 노이즈를 담은 판단 가이드를 저장합니다. 몇 분이면 끝나고 한 번만 돌립니다.
- 매 실행에서 코드는 어제 같은 시각과 통계적 기준선을 비교해 판정을 만들고, 모델이 계산을 틀릴 일이 없게 합니다. 로그는 Loki의 패턴 API로 묶은 패턴 목록을 실행 사이에 유지해 새 패턴과 비율이 두 배가 된 패턴만 골라냅니다. 정상 검사는 한 줄로 접어 모델에 한 번만 넘기고, 모델은 OK, warning, critical 중 하나와 짧은 보고서를 구조화해 돌려줍니다.
- 수치는 자체 보고입니다. 내부 43개 감시 중 41개가 월 10달러 미만이고 가장 비싼 것(검사 43개, 15분 간격)이 20달러를 조금 넘습니다(100만 토큰당 2달러 기준). 실제 운영 결과를 재생하는 평가에서 현재 모델은 위기 사례를 하나도 놓치지 않았고, 이전 모델의 절반 비용이었다고 합니다. 이 도구로 고객에게 영향을 준 프로덕션 버그를 10건 넘게 찾았지만, MySQL 고갈 건에서는 원인을 잘못 짚은 사례도 밝혔습니다.

LLM이 필요한 지점이 어디인지 가르는 기준이 에이전트 운영 비용 설계에 그대로 쓰입니다. 쿼리와 계산은 코드로, 판단과 설명만 모델로 맡기는 구조는 관측 쪽 에이전트를 만들 때 참고할 만합니다. Grafana 제품 소개를 겸한 글이고, 12월 1일까지는 무료라 요금은 아직 검증되지 않았습니다.

### CSS 등록 속성 하나로 다크 모드와 컨테이너 스타일 쿼리를 묶는 구성입니다

`dbushell.com` (Lobsters 경유) [원문](https://dbushell.com/2026/11/09/dark-mode/)

`@property`로 `--theme`을 등록하면 그 값이 컨테이너 스타일 쿼리의 조건이 되어, 한 변수로 전체 색 구성을 바꿀 수 있습니다.

- 구성은 세 개의 at-rule입니다. `@property --theme`을 `syntax: "light | dark"`, `initial-value: light`, `inherits: true`로 등록합니다. `prefers-color-scheme: dark` 미디어 쿼리가 `html`에서 값을 dark로 바꾸고, `@container style(--theme: dark)`가 `body`에 어두운 색을 적용합니다.
- 기본 색(A)은 루트 `html`에, 어두운 색(B)은 `body`에 스타일 쿼리로 적용합니다. A와 B 규칙에서 벗어나는 예외는 두 가지로 처리합니다. 컴포넌트 안에서 스타일 쿼리를 다시 쓰거나, `color-scheme: var(--theme)`를 설정한 뒤 `light-dark()` 함수를 씁니다. `color-scheme`을 설정해야 사용자가 시스템 설정을 덮어쓴 선택도 `light-dark()`에 전달됩니다.
- `color-scheme: var(--theme)`을 `html`에 두는 것은 안전하지 않다고 합니다. 브라우저가 이 값을 보고 적응형 다크 모드를 적용하기 때문입니다. `body`에서는 안전한지 저자도 확신하지 못해 독자에게 묻고 있습니다. 그래서 당분간은 장황해도 스타일 쿼리를 씁니다.
- 토글 선택은 localStorage에 저장하고 JS 몇 줄로 `--theme`을 설정합니다. 정적 CDN에 호스팅하고 엣지 워커 지연을 피하려는 선택이라, 사용자 선택이 시스템 설정과 다를 때만 색이 한 번 잘못 보이는 깜빡임(저자는 FART라고 부릅니다)이 생길 수 있습니다. 쿠키와 서버 템플릿이 더 낫다고 인정합니다.

CSS 계산 시점에 대한 구체적인 패턴이라 디자인 시스템이나 공유 라이브러리의 테마 처리에 참고가 됩니다. 한 개인 블로그의 구현이고 브라우저별 검증은 없습니다. 글의 앞부분은 Apple이 발표한 적응형 다크 모드에 대한 감상입니다.

### Docker Desktop의 VM은 2016년부터 microVM이었다는 회고가 에이전트 샌드박스로 이어집니다

`dave.recoil.org` (Lobsters 경유) [원문](https://dave.recoil.org/docker-has-always-used-microvms/)

microVM이 컨테이너보다 안전한 새 기술로 소개되지만, Docker for Mac은 2016년부터 그 방식이었고 당시 10BTC 현상금을 건 보안 챌린지도 아무도 가져가지 못했다고 합니다.

- microVM은 stripped-down Linux 커널과 최소한의 VMM(가상 머신 모니터, firecracker 같은 것)으로 워크로드를 돌리는 방식입니다. 그 선조 격인 유니커널은 앱에 필요한 드라이버와 파일시스템만 링크해서 프로세스도 셸도 없습니다. 인용된 논문은 VM 생성 시간을 x86에서 약 20ms(2015년 저성능 ARM 보드에서 120ms)까지 줄였습니다. 단점은 기존 Linux 프로그램을 그대로 못 돌린다는 것입니다.
- Docker는 2016년 Unikernel Systems를 인수했고, 이를 Docker for Mac(이후 Docker Desktop)에 결합했습니다. 목표는 microVM 자체가 아니라 Mac과 Windows에서 Docker가 부품 묶음이 아닌 네이티브 앱처럼 느껴지게 하는 것이었습니다. 그래서 앱 안에 내장하는 "라이브러리 VMM"을 만들었고, 첫 버전이 hyperkit(xhyve의 포크)이며 지금은 Docker VMM입니다. 네트워크는 MirageOS의 TCP/IP 스택을 쓴 vpnkit이, VM 커널과 루트 파일시스템은 LinuxKit이 맡았습니다.
- 이 구조의 이점으로 세 가지를 듭니다. 모든 플랫폼에서 루트 권한 없이 실행되고, 리눅스 커널 전체를 신뢰하지 않으므로 Linux CVE도 호스트에 영향이 없습니다. VM과 호스트 사이의 장치를 최소화해 감사하기 쉽습니다. VPN과 네트워크 정책 연동이 쉽습니다.
- 2026년 현재 같은 기술이 Docker Sandboxes의 기반입니다. 샌드박스마다 별도 microVM에서 돌아 서로 그리고 호스트와 격리되며, 저자는 `sbx run claude`로 코딩 에이전트를 가둬 돌려 보라고 권합니다.

코딩 에이전트에게 얼마나 권한을 줄지 고민하는 독자에게 "컨테이너와 VM 사이에서 격리 경계를 어디에 둘 것인가"라는 배경을 줍니다. Docker 측 입장에서 쓴 역사 회고이고 제품을 권하며 끝납니다. 컨테이너와의 보안 차이를 보여주는 측정이나 비교는 없습니다.

### 에이전트에게 귀를 달아주자 상자 더미 속 삐 소리가 40cm 오차로 좁혀졌습니다

`Simon Willison` [원문](https://simonwillison.net/2026/Nov/9/mysterious-beeps/)

소리를 입력으로 받지 못하는 Claude Code가, 마이크를 단 기기 다섯 대와 WebSocket으로 보낸 코드를 이용해 집 안의 정체불명 삐 소리 위치를 찾아냈습니다.

- 저자는 박스룸에서 간헐적으로 울리는 삐 소리의 출처를 찾기 위해 Claude Code에게 삼각측량 시스템 Beep Locator를 만들게 했습니다. iPad 두 대, 폰, MacBook Pro, Surface가 브라우저의 WebAudio로 마이크를 열어 듣고, Python 서버가 이를 조정합니다. 결과는 약 40cm 오차였고, 그 더미를 뒤져 배터리 교체를 애타게 요구하던 오래된 일산화탄소 감지기를 찾았습니다.
- 동작 원리는 2007년 BeepBeep 논문(스피커와 마이크만으로 기기 간 거리를 재는 방식)입니다. 각 리스너는 최근 60초 오디오를 버퍼에 두고 FFT와 고역 통과 필터로 비프 후보를 탐지해 서버에 보냅니다. 서버는 라운드트립이 가장 짧은 기기가 칩음을 내게 하고 모든 리스너에게 비프 직전 0.6초부터 칩 후 0.8초까지의 클립을 올리게 해, 칩음을 기준으로 클립을 정렬합니다.
- 처음에는 서로 소리를 내 위치를 추정하게 했는데 잘 되지 않아서, 아이콘을 직접 끌어 대략 위치를 주고 소리로 보정하는 "Rough mode"를 추가했습니다. 박수 모드로 위치 추정이 맞는지 확인하고, 재생 버튼과 "이게 그 비프" 버튼으로 소리를 확정해 이후 같은 주파수에 대해 간격과 위치를 좁혔습니다.
- 가장 흥미로운 부분은 구조입니다. Opus 5.5가 만든 `installModule()`로 서버가 연결된 리스너에 임의 코드를 보낼 수 있었고, 마이크 권한은 페이지를 새로고침할 때마다 다시 요청되는 기기가 있어 이 핫스왑 덕분에 기기를 하나씩 만지지 않아도 됐습니다. 이후 Fable 5.2가 노트북에서 서버를 돌리며 로그를 읽고 코드를 실시간으로 고쳤습니다.

에이전트가 세상을 관측하고 그 위에서 스스로 고치게 하는 루프를 만드는 방법을 구체적으로 보여줍니다. 검증 가능한 피드백을 에이전트에게 연결하는 설계라는 점이 요점입니다. 한 사람의 사례이고 소리 정확도 외의 수치는 없으며, 프롬프트와 세션 링크는 본문에 있습니다.

### malloc은 시스템 콜을 22.7배 줄이려고 큰 덩어리를 받아 직접 잘라 씁니다

`benmandrew.com` (Lobsters 경유) [원문](https://benmandrew.com/articles/what-is-malloc-doing-anyway)

`malloc(16)`을 1,000번 호출해도 커널에 들어가는 `brk` 시스템 콜은 단 두 번이고, 첫 번째는 현재 힙 끝 위치를 묻는 호출입니다.

- 빈 시스템 콜은 575ns인데 `sbrk(16)`이 610ns, `malloc(16)`은 26.9ns입니다. `malloc`이 `sbrk`보다 22.7배 빠른 이유는 커널에서 큰 덩어리(첫 호출에서 132KiB)를 한 번 받아 직접 쪼개 주기 때문입니다.
- 저자는 `sbrk`만 쓰는 범프 할당기에서 시작해 한 단계씩 개선합니다. 범프 할당기는 해제한 메모리를 재사용하지 못합니다. 청크마다 앞에 크기 헤더를 두면 `free`에 크기를 넘기지 않아도 되고, glibc에서 청크 크기는 항상 16의 배수여서 하위 비트 세 개를 플래그로 씁니다. 요청 크기에 헤더 8바이트를 더해 16의 배수로 올리고 최소 32바이트입니다. 해제된 청크는 사용자 데이터가 있던 자리에 다음 청크 포인터를 저장해 프리 리스트를 이룹니다.
- 장난감 할당기는 프리 리스트에서 충분히 큰 첫 청크를 골라 쪼개고(splitting), `free` 때 이웃한 빈 청크를 합칩니다(coalescing). 실제 출력으로 a와 b를 해제하면 352바이트 청크 하나로 합쳐지고, d(50바이트)가 그 앞부분에서 나뉘며, 마지막에는 처음의 64KiB 하나로 돌아갑니다.
- 메모리 반환은 별개 문제입니다. 1GiB를 `sbrk`한 직후 가상 크기는 1GiB를 넘지만 상주 메모리(RSS)는 1308KiB이고, 256MiB를 쓸 때마다 65,536번의 페이지 폴트가 나며 RSS가 늘어납니다(요구 페이징). `free` 후에도 쓴 페이지는 할당기가 커널에 돌려주기 전까지 상주합니다. 힙 맨 위의 빈 청크가 128KiB에 이르면 64KiB를 남기고 break를 내리는 `trim`을 추가했는데, 그 위에 살아 있는 청크 하나가 있으면 아래 빈 공간은 돌려줄 수 없습니다.

Node 서버나 SSR 컨테이너의 RSS가 왜 `free` 후에도 줄지 않는지 같은 질문의 바닥에 있는 동작입니다. glibc 위주 설명이라 V8이나 jemalloc 같은 실제 런타임의 할당기와는 거리가 있고, 본문 뒷부분은 잘려서 읽지 못했습니다.
