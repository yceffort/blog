## 오늘 하나만 본다면

### 개발자가 야심을 접는 이유는 에이전트 이전의 비용 감각을 그대로 쓰기 때문입니다

`Dan Luu` [원문](https://danluu.com/ambitious/)

Dan Luu는 코딩 에이전트의 도움으로 "배우지도 않은 분야"의 정규식 엔진과 Rust 인터프리터를 몇 시간 만에 만들었고, 같은 일을 예전에는 1년 이상 걸렸을 것이라고 씁니다.

- 출발점은 Postgres를 Rust로 다시 쓰는 프로젝트 pgrust입니다. 만든 Michael Malis는 테스트를 매우 철저히 해서 진짜 Postgres 버그까지 찾아냈습니다. SP-GiST 연산이 실패하는 수치 버그, JSONPath가 틀린 결과를 내는 포맷 캐시 버그, 사전 로더의 메모리 안전성 버그, money 오버플로 버그 등입니다. Luu는 뉴스 사이트에서 이런 재작성 프로젝트가 대부분 "바이브 슬롭"으로 치부되는 것을 이해하지만, 만드는 쪽에서는 남들이 쓰레기를 쏟아내는 것과 상관없이 테스트와 벤치마크를 제대로 하면 쓸 만한 품질이 나온다고 말합니다.
- Luu는 SOTA 모델이 10배에서 100배 빨라진다면 자기 컴퓨터에서 시간이 어디로 갈지 따져 봤습니다. 병목은 ripgrep, Rust 컴파일, 시스템 콜과 파일시스템 오버헤드였습니다. 그래서 워크로드에 맞게 조정할 수 있는 정규식 엔진, 그 엔진의 네이티브 코드 컴파일러를 쓰는 ripgrep 포크, 빌드를 빠르게 하는 Rust 인터프리터를 만들었습니다. 인터프리터는 콜드 빌드에서 50배, 웜 빌드에서 2배 빨랐다고 하며, 들어간 시간은 한 자릿수 시간입니다.
- 핵심 주장은 사람들이 "에이전트 이전의 비용 모델"을 머릿속에 두고 있다는 것입니다. 10년 전에는 컴파일러가 느리다고 새 컴파일러를 만드는 사람은 게임을 만들겠다며 3D 엔진부터 짜는 사람, 곧 아무것도 출시하지 못하는 사람이었습니다. 지금은 그런 일이 현실적인데도 생산적인 프로그래머 대부분이 여전히 손을 대지 않는다고 Luu는 봅니다.
- 모델의 이해도가 달라졌다는 사례도 듭니다. GPT-5.1과 5.2로 보드게임 AI를 만들 때는 모델의 제안이 거의 다 틀려서 계속 바로잡아야 했습니다. 논문의 기법을 지목해도 겉만 비슷한 구현을 내놨습니다. 반면 Gabriel Cangussu는 Fable 5.1과 Opus 5.5로 Luu의 AI를 압도하는 AI를 더 짧은 시간에 만들었습니다. zstd 구현 평가에서도 GPT-6 Astra는 등록된 테스트를 모든 조건에서 99% 넘게 통과했고 비용은 약 1달러여서, Luu는 IMAP RFC와 Pandoc 구현으로 평가를 바꿔야 했습니다.
- 단서가 붙습니다. "모델이 좋아져서 다 알아서 된다"는 말은 Luu의 경험과 맞지 않습니다. 원샷으로 되는 일이 늘어난 만큼 더 야심찬 일을 하게 되고, 모델이 구현할 수 있는 것과 사람 손 없이 검증할 수 있는 것 사이의 간극은 모델이 좋아질수록 오히려 벌어졌다고 합니다.

저자는 이 글을 30분 만에 거의 검토 없이 썼고, 언급한 프로젝트의 엄밀한 벤치마크도 없다고 스스로 밝힙니다. 그래서 수치는 근거가 아니라 인상으로 읽어야 합니다. 그래도 "느리다는 불평이 사실은 풀 수 있는 문제일 수 있다"는 관점과 "구현 능력보다 검증 능력이 병목"이라는 관찰은, 팀의 도구 체계와 리뷰 체계를 고민하는 독자에게 바로 닿습니다.

## 읽을 만한 것

### 자연어는 기계를 편하게 하는 인터페이스가 아니라 터무니없음을 숨기기 쉬운 인터페이스입니다

`cs.utexas.edu` (Edsger W. Dijkstra, Hacker News 경유) [원문](https://www.cs.utexas.edu/~EWD/transcriptions/EWD06xx/EWD667.html)

1978년에 Dijkstra는 "자연스러움이란 터무니없는 진술을 쉽게 할 수 있다는 뜻일 뿐"이라고 썼고, 이 문장은 프롬프트로 프로그래밍하는 지금 그대로 읽힙니다.

- 고급 언어의 가치를 먼저 짚습니다. 기계어에서는 사소한 실수가 틀린 답으로 이어졌지만, 고급 언어에서는 많은 실수가 오류 메시지로 바뀌었습니다. 그런데 오류 메시지를 무시할 수 없어 짜증스러워하고, 실수를 들키지 않고 저지르는 쉬움을 "프로그래밍이 쉽다"와 같은 말로 여기는 사람도 있었다고 비꼽니다.
- 자연어로 지시하는 기계를 만들자는 제안은 인터페이스를 노동의 분담으로만 본다고 비판합니다. 인터페이스를 바꾸면 양쪽이 협력하고 소통하는 데 드는 일이 추가되고, 경험상 양쪽의 일이 오히려 크게 늘기도 했습니다. 그래서 "좁은 인터페이스"를 선호하게 되었다는 것이 논거입니다.
- 수학사를 근거로 듭니다. 그리스 수학은 말과 그림에 머물러 막혔고, 이슬람의 대수학은 기호화를 시도하다 수사적 서술로 돌아가며 시들었다고 합니다. 근대는 Vieta, Descartes, Leibniz, Boole이 의식적으로 설계한 형식 기호 덕분에 가능했다는 주장입니다. 형식 텍스트는 유효한 조작이 소수의 단순한 규칙만 만족하면 되므로, 모국어에서는 피하기 거의 불가능한 온갖 헛소리를 걸러냅니다.
- 처음부터 입출력이 모국어뿐이었다면 컴퓨터 과학은 그 위에서 잘 정의된 형식 체계를 부트스트랩하는 "흑마술"이 되었을 것이고, 쓸 만큼 좁은 인터페이스를 얻는 데 다시 수천 년이 걸렸을 것이라고 추측합니다. 덧붙인 주석에서는 모국어 구사력이 떨어지는 추세를 들어, 기술적 통찰이 없는 자연어 프로그래밍 신봉자를 경계합니다.
- 맺음은 직감입니다. 모국어로 프로그래밍하는 기계는 만들기도, 쓰기도 지독하게 어려울 것이라고 합니다.

원문은 AI가 없던 시절의 글이라 LLM의 실제 동작에 대한 근거는 없고, 논증은 역사적 유비와 직관에 기댑니다. 그래도 "코드 리뷰와 검증 체계가 왜 필요한가"를 가장 짧게 설명하는 문장으로 인용할 만합니다. 사양을 자연어로 쓰는 비중이 커질수록 검증 가능한 형식(타입, 테스트)이 더 중요해진다는 입장의 오래된 근거입니다.

### 에이전트가 필요하다고 판단해도 토큰의 권한 밖이면 API가 거절합니다

`Vercel Blog` [원문](https://vercel.com/blog/how-vercel-agent-accesses-production-safely)

Vercel Agent는 "이 배포 고쳐줘"라는 요청에서 어떤 권한이 필요한지 미리 알 수 없어서, 조사는 읽기 전용으로 먼저 하고 고칠 계획을 세운 뒤에야 쓰기 권한을 승인받습니다.

- 문제 설정부터 양쪽이 모두 나쁩니다. 에이전트에게 넓은 권한을 주면 실수가 관계없는 리소스까지 건드리고, 단계마다 승인을 받으면 사용자는 승인 버튼을 누르는 습관만 얻습니다. 그래서 계획(plan)이 권한을 정합니다. 의도, 작업, 필요한 scope, 이를 강제하는 자격증명과 API 검사가 하나의 계획으로 묶입니다.
- 읽기 전용 기준선은 `read:`로 시작하는 등록된 scope 전부입니다. 이 선을 넘는 권한이나 GitHub PR 생성 같은 외부 작업이 들어간 계획은 그 안의 읽기 작업까지 포함해 통째로 승인을 기다립니다. 글은 읽기 전용이라도 민감한 정보가 노출될 수 있어서 자동 승인이 무해하다는 뜻은 아니라고 못 박습니다.
- 에이전트는 Vercel App으로서 사용자의 권한 범위 안에서만 동작하고, OAuth 서비스가 이를 특정 scope를 가진 수명 짧은 토큰으로 바꿔 줍니다. 모델이 토큰 범위 밖의 작업을 시도하면 모델이 필요하다고 판단했더라도 API가 거절합니다. 계획에 배포 X라고 적어도 토큰이 그 배포 하나로 좁혀지지는 않으므로, 쓰기 권한은 그 팀의 다른 배포에도 미칩니다. GitHub 쪽은 소유자와 저장소 단위로 묶여서, `acme/storefront`를 승인해도 `acme/payments`는 별도 승인이 필요합니다.
- 처음에는 에이전트용 권한 목록을 따로 관리했는데, 토큰을 발급하는 OAuth 서비스와 어긋나곤 했습니다. 지금은 같은 scope 레지스트리를 세션 시작 때 메모리 카탈로그로 불러와 계획 검증, 승인, 토큰 준비 세 단계에서 씁니다. 오래된 scope 이름을 요청하는 계획은 거절되고 유효한 scope 목록과 함께 돌아와서, 더 넓은 권한으로 대체되지 않고 명시적으로 고치게 됩니다. 레지스트리 조회에는 지연이 있어 카탈로그를 캐시합니다.
- 중단된 계획은 토큰의 유효 시간이 남아 있어도 재개 시 검사에서 실패합니다. 승인과 중단 요청이 동시에 오면 중단이 아직 상태를 바꾸지 않았을 때만 계획이 활성화됩니다. 남은 한계도 적습니다. 에이전트는 불완전한 정보로 scope를 골라서 너무 적게 또는 너무 많이 요청할 수 있고, 빌드 로그 같은 읽은 내용에 심어진 악성 지시에 속을 수도 있습니다. 올바른 권한이 있어도 어떤 커밋을 배포해도 안전한지는 별개의 판단입니다.

벤더가 자기 제품 설계를 설명하는 글이어서 실제 사고율이나 우회 사례 같은 수치는 없습니다. 그래도 에이전트에게 권한을 주는 방법을 "프롬프트로 타이르기"가 아니라 "토큰 범위와 API 검사로 강제하기"로 보는 구조는, 사내 도구에 코딩 에이전트를 붙이는 팀이 참고할 만한 레퍼런스입니다.

### UUIDv7이 보장하는 것은 유일성뿐이고, 시간순 정렬과 생성 시각은 구현에 달려 있습니다

`alexsci.com` (Hacker News 경유) [원문](https://alexsci.com/blog/uuidv7-is-weird/)

Python 표준 라이브러리의 `uuid.uuid7()`은 시스템 시계를 1시간 되돌리면 ID에 담긴 시각이 현재보다 3695초 앞선 값에서 시작해 계속 더 앞서 나갑니다.

- 블로그에서 흔히 말하는 UUIDv7의 장점은 단조 증가, 생성 시각 포함, 추측 불가입니다. 저자는 RFC 9562를 준수하는 구현도 이 성질들을 크게 깨뜨릴 수 있고 엄격히 보장되는 것은 유일성(충돌 저항)뿐이라고 주장합니다. 추측 가능성은 앞선 글에서 다뤘다고 합니다.
- 타임스탬프가 생성 시각과 같다는 보장이 없습니다. RFC 9562는 구현이 실제 타임스탬프를 바꿔도 되고, 시계보다 앞서 증가시켜도 된다고 허용하며, 시계 값이 실제 시각에 얼마나 가까워야 하는지 요구하지 않습니다. Postgres 문서도 `uuid_extract_timestamp`가 돌려주는 값이 생성 시각과 꼭 같지는 않다고 경고합니다.
- Python의 구현은 같은 밀리초에 카운터가 넘치면 타임스탬프를 올립니다. 시계가 뒤로 한 번 튀면 ID 생성 속도가 밀리초당 1개를 넘는 부하에서 차이가 3695, 3795, 3894, 3994초로 한계 없이 커집니다. 저자가 인용한 이슈에서 Python 개발자들은 RFC와 다른 구현과 일관되며 "결함 있는 시스템"에서 할 수 있는 일이 많지 않다고 답했고, 저자도 그 점은 맞다고 인정합니다. 다만 시계 점프에 폭주하지 않으면 좋겠다고 말합니다.
- 단조성도 약합니다. 노드 사이에서는 시계를 충분한 정밀도로 맞출 수 없어서 시간순 보장이 불가능하며, 이는 1970년대에 벡터 시계가 나온 이유입니다. 저자의 표현으로는 "타임스탬프는 지금 몇 시인지 알 때만, 그리고 모를 때만 시간순이다"입니다. 단일 노드에서도 카운터 없이 밀리초 타임스탬프만 쓰는 구현은 짧은 for 루프에서 순서가 뒤집힌 ID를 만듭니다. 프로세스를 재시작하면 마지막 타임스탬프를 영속 저장소에 쓰는 구현을 저자는 하나도 찾지 못했습니다.
- 정리는 구현을 고를 때 물을 질문입니다. RFC를 준수하는가, 어떤 추가 성질을 보장하는가, 어떤 한계 안에서 그러한가, 정확한 시계를 전제하는가, 언제 타임스탬프를 바꾸는가, 얼마나 추측 가능한가를 따지라고 합니다. 그래도 대략적인 순서는 쓸모가 있으니 지금 쓰는 UUIDv7을 당장 걷어낼 필요는 없다고 덧붙입니다.

Python 예시 하나가 실험의 전부이고, 다른 언어 구현을 비교한 실측은 없습니다. 그래도 정렬 키와 페이지네이션 커서, 생성 시각 대용으로 UUIDv7을 쓰는 설계를 리뷰할 때 "어떤 가정 위에서 성립하는가"를 묻는 근거로 쓸 수 있습니다.

### Cloudflare는 range 요청 캐시에서 "범위 크기" 설정을 없애고 캐시 청크에 맞춰 가져옵니다

`Cloudflare` [원문](https://blog.cloudflare.com/origin-range-requests/)

영상 플레이어가 몇 MB만 요청해도 예전 Cloudflare는 오리진에서 128 MiB를 받아 데이터센터 사이로 옮길 수 있었고, 그 시점에 시청자는 이미 떠난 뒤이기도 했습니다.

- 예전 구현은 nginx의 캐시 슬라이싱처럼 요청을 고정 크기 범위로 나누고, 범위 크기를 존(zone)마다 설정하게 했습니다. 크게 잡으면 요청한 것보다 훨씬 많이 내려받고, 작게 잡으면 작은 오리진 요청이 줄줄이 생겨 메모리 압박이 커집니다. 범위 크기가 캐시 키에 들어 있어 값을 바꾸면 캐시가 무효화되었습니다. 설정된 크기는 수십 KB부터 수십 GB까지 다양했습니다.
- 같은 범위 안의 동시 요청은 서로를 막았고, 한 번에 여러 클라이언트가 쓰는 중인 파일을 읽게 해 주는 동시 스트리밍과 range 캐시를 함께 켜면 응답이 중간에 끊겼습니다. 그래서 인기 파일도 범위마다 오리진을 따로 불러야 했습니다. 원인은 고객에게 노출된 내부 캐시의 한계였다고 글은 평가합니다.
- 해결의 실마리는 nginx에서 Pingora 기반 캐시 서버로 옮기면서 생겼습니다. Pingora는 중단된 다운로드를 이어받기 쉽게 모든 파일을 디스크에 고정 크기 청크로 저장하고 있었으므로, 범위 크기를 설정하지 않고 청크를 그 단위로 쓰면 됩니다. 요청한 바이트 중 캐시에 있는 부분은 바로 주고, 없는 부분은 청크 경계에 맞춰 오리진에서 가져와 같은 청크로 저장하며, 클라이언트에는 요청한 바이트만 돌려줍니다. 청크보다 작은 요청이 청크 하나를 통째로 가져오는 낭비는 남지만, 고객이 고른 값에 좌우되지 않고 상한이 예측 가능해졌다고 합니다.
- 한 응답을 캐시된 앞부분, 이미 진행 중인 다운로드, 새로 받는 뒷부분으로 합치는 코디네이터가 핵심입니다. 합성하기 전에 각 오리진 응답의 범위, 전체 크기, ETag가 같은지 검사하고, `If-Range`가 맞지 않으면 버전이 다른 바이트를 섞지 않고 전체 표현을 줍니다. 압축 해제할 응답은 압축된 바이트 기준의 range가 달라지므로 합성하지 않고 변환된 전체 응답을 돌려줍니다.
- 결과는 Cloudflare 자체 보고입니다. 가장 큰 내부 사용자인 R2(객체 스토리지)의 범위 크기는 64 MiB여서 경계를 걸친 작은 읽기가 128 MiB 전송으로 이어졌습니다. 새 구현으로 옮긴 뒤 R2의 p99 첫 바이트 시간이 캐시 히트와 미스 모두에서 대략 절반으로 줄었습니다. 캐시와 업스트림 바이트를 한 응답에서 합치는 변경으로 R2와 비슷한 워크로드의 계층 캐시 트래픽은 주간 기준 약 6% 줄었다고 하며, 하루 수 페타바이트 규모라고 합니다.

외부 검증 자료는 없고 수치는 모두 Cloudflare가 밝힌 값입니다. 그래도 "설정으로 떠넘기던 튜닝 값이 사실은 내부 저장 단위의 누수였다"는 진단과, 합성 응답이 같은 표현에서 온 바이트인지 검증하는 규칙은 CDN이나 이미지, 영상 서빙 계층을 다루는 독자에게 구체적인 근거가 됩니다.

### Rust로 다시 쓴 TypeScript 컴파일러 tsrs는 에이전트 여러 대를 돌리는 메모리 문제에서 시작했습니다

`Socket` [원문](https://socket.dev/blog/cloudflare-typescript-rust?utm_medium=feed)

레스토랑용 소프트웨어 회사 Owner.com의 TypeScript 백엔드는 파일 약 37,000개를 하나의 프로그램으로 검사하는데, TypeScript 7.0으로 단일 스레드 검사에 80초와 19 GiB 메모리가 들었습니다.

- 린트, 개발 서버, 여러 코딩 에이전트를 함께 돌리면 노트북이 감당하지 못했고, 이것이 tsrs의 출발점입니다. 에이전트가 워크트리를 따로 쓰면 타입 검사의 CPU와 메모리가 에이전트 수만큼 반복됩니다. Max Schwenk는 Claude 코딩 에이전트로 Rust 초안을 만들었습니다. Go 구현의 알고리즘과 동작을 보존한 채 TypeScript의 적합성(conformance) 테스트로 확인하고 Go 컴파일러와 비교하며 최적화했습니다. 10월 20일에 Cloudflare가 이를 VoidZero(Oxc, Rolldown 등을 만드는 팀, 6월에 Cloudflare가 인수)의 Oxc 도구 모음에 넣겠다고 발표했습니다.
- Cloudflare는 같은 타입 검사 워커 수에서 TypeScript 7.0보다 최대 8배 빠르고 메모리를 약 70% 적게 쓴다고 보고합니다. 다만 글이 직접 짚듯이 8배는 7.0 대비이고, 같은 발표에서 TypeScript 7.1 베타는 7.0보다 최대 2.5배 빠르다고 하므로 최신 베타에 대한 8배 우위로 읽으면 안 됩니다. Bun의 `bun check`는 TypeScript 7.0.2보다 3배에서 6.4배 빠르다고 주장해서, 같은 주에 벤치마크 주장이 여러 개 경쟁하고 있습니다. 머신 크기와 컴파일러 설정에 따라 결과가 크게 달라진다고 Cloudflare도 인정하고, 벤치마크 도구와 방법론은 공개되어 있습니다.
- TypeScript 팀의 Daniel Rosenwasser는 Hacker News에서 속도의 상당 부분은 언어 선택에서 오지 않는다고 말했습니다. tsrs에서 찾은 최적화 중 안전한 것은 7.1에 들어가고 있습니다. 그는 팀도 Rust 포팅을 직접 시도해 봤다고 밝혔습니다.
- Rust를 고른 이유로 Wasm이 있습니다. Go도 Wasm으로 컴파일되지만 가비지 컬렉터가 함께 따라오는 반면 Rust는 그렇지 않아, 브라우저나 Cloudflare Worker 안에서 에이전트가 파일을 고치고 검사하는 검증 루프를 돌리기에 낫다는 설명입니다. 현재 Wasm 빌드는 단일 스레드이며 watch 모드와 LSP가 없고 인스턴스당 선형 메모리는 최대 4 GiB입니다.
- 유지보수가 관건입니다. 포팅은 AI로 며칠 만에 되지만, 흥분이 가라앉은 뒤 누가 TypeScript의 다음 릴리스를 따라가느냐가 문제입니다. Oxc 팀이 맡고, Theo Browne의 또 다른 Rust 포팅 tsc-rs와 합치며, 업스트림 변경을 에이전트가 검토하고 테스트를 돌려 호환성 차이를 찾는 방식을 쓰겠다고 합니다. 안정 릴리스는 아직이고 오류 보고 순서 같은 차이가 남아 있습니다.

수치는 Cloudflare 보고에 의존하고, Socket 기사는 이를 독립적으로 재현하지 않았습니다. 그래도 "에이전트를 여러 대 돌리면 타입 검사 비용이 곱해진다"는 새 병목이 컴파일러 포팅 경쟁의 동기라는 점, 그리고 속도 차이의 상당 부분이 언어가 아니라 알고리즘에서 온다는 컴파일러 팀의 말은 빌드 체인 선택에 중요한 맥락입니다.

### LiteLLM 공급망 공격의 비밀 탈취 워크플로는 릴리스 공격보다 11일 앞서 이미 돌고 있었습니다

`Socket` [원문](https://socket.dev/blog/litellm-attack-timeline?utm_medium=feed)

악성 `litellm==1.107.0`이 PyPI에 올라온 것은 10월 21일이지만, CI 비밀을 빼내는 워크플로는 10월 10일에 이미 한 번 성공적으로 실행되었습니다.

- Socket이 찾은 것은 `ci: bump cache config`라는 같은 제목의 커밋 두 개입니다. 10월 10일과 12일에 각각 `.github/workflows/cache.yml`을 새로 추가합니다. 둘 다 `ci-tmp-<hex>`라는 임시 브랜치에 푸시되어 몇 분 안에 삭제되었고, 그래서 저장소의 평소 기록에는 거의 흔적이 남지 않았습니다. 브랜치는 직전에 병합된 정상 커밋에서 갈라져 나와 겉보기에 평범한 작업처럼 보입니다.
- 워크플로가 `on: [push]`로 트리거되므로 어떤 브랜치에 푸시해도 실행되고, 이때 `secrets.*`가 실제 값으로 풀립니다. 그래서 공격자는 `main`을 건드릴 필요가 없었습니다. 단계는 비밀을 환경 변수로 받아 파일에 쓰고 base64로 인코딩한 뒤 webhook.site로 `curl` 전송하며, 끝의 `|| true`로 실패해도 실행이 성공으로 보이게 합니다.
- 증거는 저장소 자체의 기록에서 나옵니다. Actions 성능 지표(Insights)는 10월 10일 하루에 `cache` 워크플로의 성공 실행 1회, 잡 1개, 평균 4초, 실패율 0%를 보여 줍니다. 또 환경(Environment)에 묶인 잡은 배포 기록을 남기는데, 이 기록은 워크플로 파일이 삭제된 뒤에도 남습니다. `integration-redis` 환경에는 삭제된 브랜치 `ci-tmp-4d8517`에서 배포된 활성 기록이 있습니다. 공격자가 실제 환경 이름을 정확히 써서 환경 목록을 미리 조사했음을 알 수 있습니다.
- 두 워크플로는 목표가 다릅니다. 10월 10일은 조직 수준 비밀 6개(GitHub 토큰, GitHub App의 ID와 개인 키, Linear, LiteLLM, Together API 키)를 가져갔고, 12일은 겹치지 않는 14개를 환경 5개를 묶어 가져갔습니다. Socket은 재시도가 아니라 첫 수집에서 빠진 것을 모은 정찰 뒤 확장으로 보는 것이 일관된다고 해석합니다. GitHub App의 개인 키는 설치 토큰을 계속 발급할 수 있어 사용자 토큰처럼 만료되지 않는다는 점이 중요하다고 짚습니다.
- 초기 침투 경로는 LiteLLM의 조사 결과로, 5월에 공개 저장소에 실수로 커밋되어 폐기되지 않은 Agent Platform 마스터 키입니다. 공격자가 이 키로 조직 소유자의 GitHub 토큰을 얻은 다음, 악성 워크플로로 다른 메인테이너의 자격증명을 훔쳤다고 합니다. LiteLLM의 감사 로그는 10월 10일 워크플로가 훔친 `GH_TOKEN`을 10월 21일 악성 릴리스 승인과 연결합니다. 반면 Socket 자신은 최초 접근 경로를 확정하지 못했고 10일의 탈취가 21일에 쓴 접근을 만들었다고 주장하지 않는다고 구분해서 적습니다. 어떤 비밀이 실제로 전송되었는지도 지표만으로는 알 수 없습니다.

Python 패키지 사건이지만 원인은 GitHub Actions 설정이어서 npm 패키지를 배포하는 저장소에도 그대로 적용됩니다. 임시 브랜치 푸시만으로 시크릿에 닿는 구조, 환경 시크릿 범위, 장기 유효한 App 키를 점검할 근거로 쓸 수 있습니다. 다만 침투 경로와 시간 순서의 일부는 LiteLLM의 자체 조사에 기대고 있고, Socket 글은 연관을 조심스럽게만 서술합니다.
