### 에이전트 시대에는 "원래 비싸서 안 하던 일"의 목록을 다시 써야 합니다

`Dan Luu` [원문](https://danluu.com/ambitious/)

저자는 코딩에 쓰는 시간이 몇 시간뿐이었는데도 자기 워크로드에 맞춰 튜닝한 정규식 엔진과 Rust 빌드를 빠르게 하는 도구를 만들었고, 그 이유를 "사람들이 에이전트 이전의 비용 모델을 머릿속에 들고 다니기 때문"이라고 설명합니다.

- 출발점은 Postgres를 Rust로 다시 쓰는 pgrust 프로젝트입니다. 이런 재작성 프로젝트는 대부분 AI가 찍어낸 쓰레기라서 커뮤니티에서는 흔히 무시당합니다. 그런데 저자는 pgrust 개발자 Michael Malis가 테스트를 철저히 해서 원본 Postgres의 실제 버그(JSONPath 결과 오류, 메모리 안전성 버그, money 오버플로 등)까지 찾아냈다고 말합니다. 프로젝트가 실패하더라도 Postgres가 영구적으로 나아진다는 논지입니다.
- 저자는 OpenAI가 최상위 모델에 Cerebras 칩을 쓴다는 소식을 듣고 "모델이 10배에서 100배 빨라지면 내 컴퓨터에서 병목은 어디일까"를 따져 봤습니다. 답은 ripgrep, Rust 컴파일, 시스템 콜과 파일시스템 오버헤드였습니다. 그래서 정규식 엔진, 그 엔진의 네이티브 코드 컴파일러를 쓰는 ripgrep 포크, 콜드 빌드를 크게 줄이는 Rust 인터프리터 겸 빌드 가속기를 직접 만들었습니다. 정규식, 문자열 매칭, 컴파일러 지식이 없는 저자에게 이전이라면 1년 이상 걸렸을 일이 한 자릿수 시간으로 줄었다고 합니다.
- 핵심 주장은 문제가 "해결 불가능해서"가 아니라 "해결 비용이 높다고 가정해서" 남아 있다는 것입니다. 몇 주 동안 Rust 컴파일이 느리다는 불평이 계속 올라왔지만, 컴파일러를 새로 만드는 일은 10년 전에는 게임 엔진부터 만들겠다는 사람이나 하던 일이었습니다. 생산적인 프로그래머일수록 그런 일을 피하는 습관이 남아 있다고 저자는 지적합니다.
- 모델 능력의 변화도 구체적으로 적습니다. GPT-5.1과 5.2로 보드게임 AI를 만들 때는 논문을 읽혀도 기법 이름만 흉내 낸 코드가 나와 계속 바로잡아야 했습니다. 지금 모델로는 다른 사람이 훨씬 짧은 시간에 저자의 AI를 이기는 AI를 만들었다고 합니다. 저자의 zstd 구현 평가에서는 최신 모델이 등록된 테스트를 99% 넘게 통과했고 비용은 약 1달러였습니다. 그래서 평가 과제를 IMAP RFC와 Pandoc 구현으로 바꿔야 했습니다.
- 다만 "이제 다 알아서 된다"는 주장에는 선을 긋습니다. 모델이 한 번에 해내는 일이 늘수록 저자는 더 야심찬 일을 맡기게 되고, 모델이 구현할 수 있는 범위와 사람 손을 덜 빌리고 검증할 수 있는 범위의 간격은 오히려 벌어졌다고 합니다. 저자는 이 글을 30분 만에 썼고 벤치마크도 엄밀하게 하지 않았다고 직접 밝힙니다.

왜 볼 만한가: 공유 라이브러리와 개발자 도구로 팀 생산성을 고민하는 사람에게는 "이건 원래 비싸니까 안 한다"는 판단을 점검해 볼 근거가 됩니다. 한계도 분명합니다. 수치는 저자 개인의 "내 워크로드" 비교이고, 글 스스로 엄밀한 벤치마크가 없다고 인정합니다. 검증이 병목이 된다는 마지막 논지가 이 독자의 관심과 가장 맞닿아 있습니다.

### 자연어로 프로그래밍하자는 꿈이 틀린 이유를 1978년에 이미 설명했습니다

`cs.utexas.edu` (Hacker News 경유) [원문](https://www.cs.utexas.edu/~EWD/transcriptions/EWD06xx/EWD667.html)

1978년에 쓴 글입니다. Dijkstra는 기계가 사람의 모국어를 알아듣게 하면 일이 쉬워지기는커녕 "말이 되지 않는 말도 그럴듯하게 들리게" 만들 뿐이라고 주장합니다.

- 출발점은 프로그래밍이 형식 기호를 요구한다는 사실을 불평하는 오래된 흐름입니다. 기계어에서 고급 언어로 오면서 사소한 실수가 틀린 답 대신 오류 메시지가 되었다는 점이 큰 진전이었는데, 일부는 오류 메시지가 거슬린다고 불평했다고 비꼽니다.
- 인터페이스를 바꾸는 일은 고정된 일의 양을 나누는 것이 아니라고 그는 말합니다. 인터페이스를 가로질러 소통하는 비용이 양쪽 모두에 더해지기 때문에, 인터페이스를 바꾸면 양쪽의 일이 함께 늘어날 수도 있습니다. 그래서 "좁은 인터페이스"를 선호하게 되었다는 것입니다.
- 근거로 수학의 역사를 듭니다. 그리스 수학은 말과 그림에 머물러 막혔고, 이슬람 대수학은 기호 체계를 시도하다 다시 서술 방식으로 돌아가 사라졌습니다. 현대 수학은 Vieta, Descartes, Leibniz, Boole이 설계한 형식 기호 덕분에 나왔다고 합니다.
- 형식 기호의 장점은 합법적인 조작이 몇 가지 단순한 규칙만 만족하면 된다는 점이고, 덕분에 온갖 헛소리를 걸러냅니다. 반대로 모국어의 "자연스러움"은 헛소리가 헛소리인 줄 모르게 말할 수 있는 편안함이라고 꼬집습니다.
- 처음부터 모국어만으로 기계와 소통했다면 컴퓨터 과학은 모국어에서 충분히 엄밀한 형식 체계로 올라가는 "흑마술"이 되었을 것이고, 쓸 만한 좁은 인터페이스를 만드는 데 수천 년이 걸렸을 것이라고 추측합니다.

왜 볼 만한가: 프롬프트로 코드를 생성하는 시대에 "명세가 모호하다는 것이 왜 근본 문제인가"를 가장 짧게 짚는 고전입니다. 1978년 글이라 LLM을 직접 다루지는 않고, 논증도 역사적 유추와 직관에 기대고 있으니 실증 자료로 읽지는 않으시길 권합니다.

### 에이전트에게 프로덕션 권한을 주는 방법으로 "계획 단위 승인"을 택했습니다

`Vercel Blog` [원문](https://vercel.com/blog/how-vercel-agent-accesses-production-safely)

모든 동작마다 승인을 받으면 사용자는 결국 승인 버튼을 습관적으로 누르게 되고, 넓은 권한을 한 번에 주면 실수가 무관한 리소스까지 번집니다. Vercel은 이 둘 사이에서 "조사는 읽기 전용으로 자동, 변경은 계획을 통째로 승인"하는 구조를 택했습니다.

- Vercel Agent는 먼저 읽기 전용으로 문제를 조사한 뒤, 무엇을 할 것이고 어떤 접근 권한(scope)이 필요한지를 담은 계획을 제시합니다. 사용자가 계획을 승인해야 추가 권한이 열립니다. 읽기 전용 기준선은 이름이 `read:`로 시작하는 모든 scope입니다.
- 에이전트는 사용자가 이미 가진 권한 안에서만 동작하는 Vercel App으로 실행됩니다. 승인된 계획은 수명이 짧은 토큰으로 바뀌고, 모든 API 요청이 그 토큰의 scope를 검사합니다. 모델이 필요하다고 판단해도 토큰 범위 밖의 동작은 API가 거절합니다.
- 계획의 scope 이름은 토큰을 발급하는 OAuth 서비스와 같은 정의를 씁니다. 처음에는 에이전트용 권한 목록을 따로 관리했다가 서로 어긋나서 통합했습니다. 존재하지 않거나 이름이 바뀐 scope를 요청하면 계획 단계에서 거절하고 올바른 scope를 돌려주어, 넓은 권한으로 폴백하지 않고 명시적으로 고치게 합니다.
- 계획 상태는 저장되고, 작업을 재개할 때마다 계획이 아직 활성인지 다시 확인합니다. 중지된 계획은 토큰 만료 시간이 남아 있어도 실패합니다. 승인과 중지 요청이 동시에 오면 중지가 먼저 반영된 경우 승인이 무시됩니다.
- 한계도 직접 적습니다. 배포 쓰기 권한은 특정 배포 하나가 아니라 더 넓은 권한이라 계획에 배포 X를 적어도 토큰이 그것만으로 제한되지 않습니다. 모델은 scope를 불완전한 정보로 고르기 때문에 너무 적게 또는 너무 많이 요청할 수 있고, 빌드 로그에 섞인 악성 지시를 읽을 수도 있습니다. 그래서 샌드박스, 네트워크 정책, 감사 로그 같은 다른 통제와 함께 써야 한다고 말합니다.

왜 볼 만한가: AI 코딩 도구의 권한 모델을 팀에 도입하려는 사람에게 "승인 피로"와 "과도한 권한" 사이의 설계 선택을 구체적으로 보여 줍니다. 자사 제품 소개 글이므로 효과를 검증한 수치는 없고, 읽기 전용 단계의 정보 노출 위험도 열린 문제로 남겨 둔다는 점을 감안해야 합니다.

### 취약점 공개에서 실전 공격까지 걸리는 시간이 몇 주에서 몇 시간으로 줄었습니다

`drew.silcock.dev` (Hacker News 경유) [원문](https://drew.silcock.dev/blog/is-this-the-new-cyber-normal/)

PHP의 원격 코드 실행 취약점 두 건이 알려지자 패치가 나오기도 전에 이미 실제 공격이 시작되었습니다. 저자는 보안 패치 공지가 나온 순간을 "완전한 익스플로잇이 퍼지지 않았다고 장담할 수 있는 마지막 시점"으로 보라고 주장합니다.

- 저자가 짚는 구조는 이렇습니다. 요즘은 패치가 공개되면 곧바로 사람들이 LLM 에이전트를 코드베이스에 풀어서 diff를 읽고, 보안 패치처럼 보이는 변경을 찾고, 거슬러 올라가 취약점을 특정하고, 익스플로잇까지 만듭니다. 이 과정이 너무 빨라서 취약점 소문이 돈 시점부터 자동화된 공격까지 걸리는 시간이 몇 주나 몇 달에서 몇 시간이나 몇 분으로 줄었다고 봅니다.
- PHP2Shell로 불리는 이 사건은 두 보안 팀이 각각 프런티어 모델로 찾아냈고, 비공개 기한(embargo) 전에 Hacker News에 소문이 올라가면서 패치 일정이 하루 앞당겨졌습니다. PHP 재단은 한 보안 업체가 익스플로잇 시연 영상을 유출했고 다른 업체가 기한보다 6시간 먼저 수정본을 공개했다고 주장합니다. 저자는 약 17시간 안에 여러 일이 겹쳤다고 정리합니다. 원문에 CVSS 10.0 점수가 퍼졌지만 실제 점수는 9.2였다고도 밝힙니다.
- 두 취약점 중 하나는 2024년 보안 감사에서 이미 이론상 문제로 지적되었지만, 실제 익스플로잇 방법을 아무도 몰라서 후순위로 밀렸다고 합니다. 저자는 LLM이 막연한 이론적 취약점을 완전한 익스플로잇으로 만드는 데 특히 능하다고 봅니다.
- 반론도 소개합니다. LLM이 만드는 익스플로잇은 서버가 업로드한 PHP를 실행한다는 식의 잘못된 가정을 하거나 속임수를 쓰는 경우가 많아서 쓸모없는 "슬롭"이 쌓인다는 지적입니다. 그러나 슬롭이 1만 개여도 작동하는 하나만 있으면 충분하고, 무엇을 보고 있는지 모르면 AI가 속임수를 썼는지 판별할 수 없으니 전문 지식은 여전히 필요하다고 저자는 결론 내립니다.
- 같은 주에 GitLab 최대 심각도 정규식 파싱 RCE 두 건, eMudhra 인증기관이 "115", "56", "4" 같은 극단적으로 짧은 키를 중간 인증서에 썼다가 Mozilla에 차단당한 일, Railway의 환경 변수 유출 사고가 겹쳤습니다. 저자는 이 가운데 GitLab과 eMudhra 건이 AI로 발견되었다는 증거는 없다고 구분해 둡니다.

왜 볼 만한가: 의존성과 공급망 관리를 책임지는 사람에게는 "패치 공지 후 대응 창구가 사실상 사라졌다"는 주장이 대응 체계를 점검할 계기가 됩니다. 저자는 보안 전문가가 아니라고 밝혔고 대부분 외부 글의 요약이므로, 수치나 타임라인은 링크된 원 출처로 확인하는 편이 안전합니다.

### Rust로 다시 쓴 TypeScript 컴파일러가 빠른 이유는 언어만이 아닙니다

`socket.dev` [원문](https://socket.dev/blog/cloudflare-typescript-rust)

Cloudflare가 공개한 tsrs는 TypeScript 7.0보다 최대 8배 빠르고 메모리를 약 70% 덜 쓴다고 주장하지만, TypeScript 팀은 "속도의 상당 부분은 언어 선택 때문이 아니다"라고 말합니다.

- 시작은 레스토랑용 소프트웨어 회사 Owner.com의 문제였습니다. 약 37,000개 TypeScript 파일을 한 프로그램으로 검사하는데, TypeScript 7.0(Go로 다시 쓴 컴파일러)이 단일 스레드로 80초, 메모리 19GiB를 썼습니다. 여기에 린트와 개발 서버, 코딩 에이전트 여러 개가 겹치면 노트북 자원이 바닥났습니다.
- 개발자 Max Schwenk가 Claude 코딩 에이전트로 Go 구현을 Rust로 옮긴 뒤 Go 컴파일러와 비교하며 최적화했고, 이를 Cloudflare가 인수한 VoidZero의 Oxc 툴체인으로 가져왔습니다. 알고리즘과 동작을 그대로 보존하고 TypeScript의 적합성 테스트로 검증하는 방식입니다. Bun의 `bun check`, Theo Browne의 tsc-rs도 비슷한 경쟁 프로젝트인데, tsc-rs는 tsrs와 합쳐지는 중입니다.
- 8배라는 숫자는 TypeScript 7.0과 같은 개수의 타입 검사 워커로 맞춘 비교입니다. 발표에서 TypeScript 7.1 베타는 7.0보다 최대 2.5배 빠르다고 하므로 최신 베타 대비 8배 우위로 읽으면 안 됩니다. tsrs에서 발견된 최적화 일부가 이미 7.1에 반영되었다는 것이 TypeScript 팀의 설명입니다.
- Rust를 고른 이유로 WebAssembly가 꼽힙니다. Go는 Wasm으로 컴파일하면 가비지 컬렉터가 따라오지만 Rust는 그렇지 않아서 브라우저나 Cloudflare Worker 안에서 에이전트가 파일을 고치고 타입 검사까지 하는 순환을 만들기 좋다는 설명입니다. 현재 Wasm 빌드는 단일 스레드이고 watch 모드와 LSP가 없으며 인스턴스당 메모리는 4GiB가 한도입니다.
- 에이전트가 포팅을 며칠 만에 해내는 시대에 남는 질문은 유지보수입니다. Oxc 팀이 TypeScript 새 릴리스를 따라가는 일을 맡고, 에이전트가 상류 변경을 검토해 호환성 차이를 찾는 프로세스를 쓴다고 합니다. 진단 메시지 순서처럼 공식 컴파일러와 다른 부분이 남아 있고 안정 버전도 아직 아닙니다.

왜 볼 만한가: 대규모 모노레포의 타입 검사 시간과 에이전트 병렬 실행 비용을 고민하는 팀이라면 `npx tsrs --noEmit`으로 직접 재 볼 만합니다. 이 글은 Cloudflare 발표를 보안 업체 블로그가 요약한 것이라 벤치마크는 모두 발표 주체의 수치이며, 독립 검증은 아닙니다.

### 범위 요청을 캐시하는 크기를 고객이 정하게 했던 것이 문제였습니다

`Cloudflare` [원문](https://blog.cloudflare.com/origin-range-requests/)

영상 플레이어가 영화 중간으로 건너뛰며 몇 MB를 요청했을 뿐인데, 예전 Cloudflare 캐시는 원본 서버에서 128MiB를 가져와 데이터센터 사이로 옮길 수 있었습니다.

- 이전 구현은 nginx 캐시 슬라이싱 방식이었습니다. 클라이언트 요청을 영역(zone)마다 설정한 고정 크기의 범위로 쪼개 캐시했습니다. 범위가 작으면 원본으로 가는 요청이 잘게 쪼개지고 메모리에 요청을 합치느라 압박이 생기며, 크면 필요한 것보다 훨씬 많이 내려받는 문제가 있었습니다. 범위 크기가 캐시 키에 들어가서 값을 바꾸면 캐시가 무효화되기도 했습니다.
- 같은 범위 안에 있는 동시 요청은 서로를 막았고, 여러 클라이언트가 쓰는 중인 파일을 동시에 읽게 해 주는 스트리밍 기능과 범위 캐싱을 같이 켜면 응답이 중간에 끊겼습니다. 그래서 범위 하나를 다 받아야 누구든 읽을 수 있었고, 인기 있는 파일도 범위마다 원본 요청이 따로 필요했습니다. 설정된 범위 크기는 수십 KB부터 수십 GB까지 제각각이었고, 가장 큰 내부 사용자였던 R2는 64MiB로 설정되어 있었습니다.
- 해법은 nginx에서 Pingora 기반 캐시 서버로 옮기면서 이미 있던 구조를 쓰는 것이었습니다. Pingora는 캐시 파일을 이미 고정 크기 청크로 디스크에 저장하므로 범위 크기 설정이 필요 없고 청크 경계가 곧 범위가 됩니다. 요청 범위를 청크에 맞춰 원본에서 가져오고 청크로 저장한 뒤 클라이언트에는 요청한 바이트만 돌려줍니다. 청크보다 작은 요청이 청크 전체를 가져와야 하는 낭비는 남지만, 고객 설정에 좌우되지 않고 한계가 정해져 있습니다.
- 한 응답에 디스크의 캐시된 구간, 진행 중인 다운로드, 새로 가져올 구간이 섞이는 경우를 하나의 조정자(coordinator)가 합칩니다. 합치기 전에 원본 응답의 범위, 전체 크기, ETag가 일관된지 검사하고, `If-Range`가 맞지 않거나 압축 해제 중인 응답이라면 범위를 합성하지 않고 전체 응답을 내려보냅니다.
- R2를 새 구현으로 옮기자 지역별 p99 첫 바이트 시간(TTFB)이 캐시 적중과 미스 양쪽에서 약 절반으로 줄었습니다. 캐시에 있는 바이트와 상류에서 받은 바이트를 한 응답으로 합치는 변경 뒤에는 R2와 비슷한 워크로드의 계층 간 캐시 트래픽이 주 단위로 약 6% 줄었다고 합니다. 이제 모든 요금제에서 캐시 규칙으로 Origin Range Requests를 켤 수 있습니다.

왜 볼 만한가: 정적 자산이나 대용량 파일을 CDN 뒤에서 서비스한다면, 범위 요청이 캐시 계층에서 어떻게 증폭되는지와 `206`, `416`, `If-Range` 처리의 정확성 조건을 한 번에 볼 수 있습니다. 수치는 모두 Cloudflare 내부 측정이고 자사 기능을 소개하는 글이라는 점을 고려해야 합니다.

### UUIDv7의 타임스탬프는 시간 순서도, 생성 시각도 보장하지 않습니다

`alexsci.com` (Hacker News 경유) [원문](https://alexsci.com/blog/uuidv7-is-weird/)

Python 3.14 표준 라이브러리의 `uuid.uuid7()`은 시스템 시계를 1시간 뒤로 돌리면 ID에 담긴 시각이 현재보다 3600초 앞선 값에서 시작해 부하가 높을수록 앞선 폭이 오히려 계속 커집니다.

- UUIDv7을 소개하는 글들은 단조 증가, 생성 시각을 담은 타임스탬프, 추측 불가능성을 장점으로 내세웁니다. 저자는 RFC 9562가 이 세 가지를 엄밀하게 보장하지 않는다고 주장합니다. RFC는 구현이 타임스탬프를 바꿔도 된다고 하고, 시계 값이 실제 시각에 얼마나 가까워야 하는지 요구하지 않습니다. Postgres 문서도 추출한 타임스탬프가 생성 시각과 꼭 같지는 않다고 경고합니다.
- 시연 코드가 핵심 증거입니다. 구현은 타임스탬프가 뒤로 가지 않게 지난번 값을 유지하고 카운터를 올립니다. 시계가 1시간 뒤로 가면 ID의 시각은 막힌 채 카운터가 넘칠 때마다 앞으로 밀리고, 밀리초당 1건 넘게 ID를 만들면 차이가 1시간에서 시작해 계속 늘어납니다. 저자는 Python 개발자들이 RFC와 다른 구현과 일치하므로 할 수 있는 게 없다고 판단했다고 전하면서, 그래도 시계 점프를 처리하는 편이 낫다고 말합니다.
- 단조성은 더 근본적인 문제입니다. 서로 다른 노드의 ID를 시간순으로 줄 세우는 것은 1970년대에 불가능하다고 증명되었고, 그래서 벡터 시계 같은 기술이 나왔다고 합니다. 한 노드에서도 밀리초 타임스탬프에 카운터가 없는 구현은 반복문 안에서 순서가 뒤집힌 ID를 만듭니다. 저자는 "시각이 시간순이려면 지금이 몇 시인지 알아야 하는데, 우리는 모른다"고 요약합니다.
- 재시작도 문제입니다. 마지막 타임스탬프를 영속 저장소에 써 두어야 시계가 뒤로 간 뒤 프로세스가 재시작해도 순서를 지킬 수 있는데, 저자가 본 구현 중에는 그렇게 하는 것이 없었다고 합니다. 반대로 시계가 미래로 잘못 설정된 경우에는 보호 장치 때문에 틀린 시각을 계속 쓰게 됩니다.
- 저자의 결론은 UUIDv7을 버리라는 것이 아닙니다. 대략적인 순서는 여전히 유용하고, 보장되는 것은 고유성과 충돌 회피뿐이라고 정리합니다. 구현을 고를 때 RFC 준수 여부, 추가 보장, 그 보장이 성립하는 조건(정확한 시계 등), 타임스탬프를 바꾸는 조건, 추측 가능성을 따져 보라고 권합니다.

왜 볼 만한가: 주키를 UUIDv7로 바꾸면서 정렬 키나 생성 시각 컬럼을 없애는 설계를 고민하고 있다면 어떤 가정이 깨질 수 있는지 짚어 줍니다. 저자 스스로 입문 글이 아니라 오해를 바로잡는 글이라고 밝혔고, 사례는 Python 구현 한 가지가 중심이라 다른 언어 구현은 직접 확인해야 합니다.

### LiteLLM 공급망 공격의 비밀 탈취 워크플로는 공격 11일 전부터 돌고 있었습니다

`socket.dev` [원문](https://socket.dev/blog/litellm-attack-timeline)

악성 `litellm==1.107.0`이 PyPI에 올라온 10월 21일보다 11일 앞선 10월 10일에, 같은 저장소의 GitHub Actions에서 조직의 CI 비밀을 외부로 보내는 워크플로가 이미 성공적으로 실행되고 있었습니다.

- 증거는 저장소의 Actions 성능 지표입니다. `cache.yml` 워크플로가 10월 10일에 1건, 12일에 1건 성공한 것으로 기록되어 있고, 10일 실행은 작업이 1개에 평균 4초였습니다. 이는 저장소 체크아웃 없이 환경 변수를 읽어 `curl` 한 번만 호출하는 구조와 맞고, 실패를 숨기는 `|| true` 덕분에 실패율은 0%였습니다.
- 공격 방식은 임시 브랜치로 흔적을 줄이는 것이었습니다. 정상 커밋에서 `ci-tmp-<hex>` 브랜치를 따서 `ci: bump cache config`라는 커밋 하나로 워크플로를 추가하고, `on: [push]`로 실행시키고, 브랜치를 바로 삭제했습니다. 푸시가 일어난 브랜치는 `main`이 아니어도 저장소 비밀에 접근할 수 있어서 `main`에는 파일이 남지 않았습니다. 그래도 환경(environment) 배포 기록은 파일이 지워진 뒤에도 남아 있었습니다.
- 두 워크플로는 목표가 달랐습니다. 10일 것은 조직 수준 비밀 6개(GitHub 토큰, GitHub App 비공개 키 등)만 가져갔고, 12일 것은 환경 5개를 묶어 서로 겹치지 않는 비밀 14개(Anthropic, OpenAI, AWS Bedrock API 키 등)를 가져갔습니다. 저자는 이를 정찰 후 확대 수집으로 읽을 수 있고, 전송 채널이 바뀌지 않은 점은 10일 전송이 성공했다는 해석과 맞다고 봅니다. GitHub App 비공개 키는 만료되지 않는 설치 토큰을 계속 발급할 수 있어서 가장 위험한 항목입니다.
- LiteLLM 측 조사에 따르면 초기 접근은 5월에 공개 저장소에 실수로 커밋되고 폐기되지 않은 Agent Platform 마스터 키였습니다. 그 키로 조직 소유자의 GitHub 토큰을 얻어 악성 워크플로를 돌렸고, 감사 로그상 10일 워크플로가 훔친 `GH_TOKEN`이 21일 악성 릴리스 승인과 연결된다고 합니다.
- 저자가 확인하지 못한 것도 분명합니다. 워크플로가 실제로 어떤 비밀을 전송했는지는 지표에서 알 수 없고, 10일 탈취가 21일 접근의 직접 원인이라고 단정하지도 않습니다.

왜 볼 만한가: 공급망 공격이 패키지 레지스트리 이전에 CI 비밀 관리에서 시작된다는 점, 그리고 `on: [push]` 워크플로와 장기 유효 자격증명이 만드는 위험을 구체적 타임라인으로 보여 줍니다. 대상이 Python 패키지지만 npm 배포 파이프라인에도 그대로 적용되는 교훈입니다. 이 글은 조사 업체의 분석이며 일부 내용은 LiteLLM 측 설명에 기대고 있습니다.
