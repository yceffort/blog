같은 포켓몬 앱을 프레임워크 12종으로 각각 5번씩 에이전트에게 만들게 했더니, 가장 싼 Hono+htmx는 $2.67이고 가장 비싼 Angular는 $4.97이었습니다.

### 취약점이 쏟아지는데 병목은 패치가 아니라 "우리 환경에 뭐가 있는지 아는 것"입니다

AI가 쓴 취약점 보고서에 재현 방법을 물으면, 원리를 아는 사람이 쓰던 한 장짜리 설명 대신 7,000단어짜리 README.md가 돌아옵니다.

### 논리 버그 4개만 엮어서 Edge 샌드박스를 탈출했습니다

`blog.orange.tw` (Orange Tsai, Lobsters 경유) [원문](https://blog.orange.tw/posts/2026-10-the-last-proof-of-human-craft-browser-full-chain/)

Chromium에서 "현재 탭"에 새 탐색을 시키면서 출발 탭을 지정하지 않으면, 사용자가 8초 사이에 다른 탭으로 옮겼을 때 그 탭이 공격 대상이 됩니다.

- 저자는 Pwn2Own Berlin 2026에서 메모리 손상 없이 논리 버그만으로 만든 Edge 풀 체인(버그 5개와 Windows 기능 2개)을 선보였습니다. 이 체인은 $175,000을 받았고 Pwnie Awards의 Epic Achievement도 받았습니다. 출발점은 브라우저 프로세스에서 탐색 요청을 가로채는 Navigation Throttle로, 지난 5년간 Chrome이 고친 CVE 3,000건 이상 중 관련된 것은 20건도 안 된다고 합니다.
- Edge의 EdgeCAGuidanceNavigationThrottle은 엔터프라이즈 계정 안내를 위해 `https://guidance-ca-error/?email=...&switch_profile={url}` 형태의 탐색을 가로채고, 이메일이 일치하면 쿼리의 URL로 브라우저 프로세스가 새 탐색을 시작합니다. 처음엔 오픈 리다이렉트의 강화판 정도로 보았지만, 이 새 탐색에는 렌더러와의 연결이 없었습니다. `Navigate()`가 source_contents 없이 호출되면 Chromium이 "지금 활성인 탭"을 출발점으로 삼기 때문에, 지연을 두고 다른 탭으로 옮기자 google.com에서 UXSS(다른 사이트에서 코드를 실행하는 공격)가 되었습니다. 저자는 이 기본값이 Chromium 예제 코드에도 있어 같은 실수가 다른 곳에도 있을 수 있다고 봅니다.
- 이 UXSS를 0클릭으로 만들려면 장애물 넷을 넘어야 했습니다. 먼저 Microsoft 도메인에서만 발동하는 검사는 `GetLastCommittedURL()` 기준이라 `window.open`으로 띄운 login.live.com 팝업에서 탐색시키면 우회됩니다. 다음으로 팝업 차단기는 Edge 내부용 허용 목록의 `about:blank#quickAuthPopup`을 쓰면 통과하고, 그 뒤 원하는 사이트로 옮기면 됩니다.
- 나머지 둘도 우연한 기능에 기댑니다. 로그인된 프로필이 필요한 조건은 Windows 25H2의 MSA 로그인 요구와 Edge의 OneAuth 자동 로그인으로 해결됩니다. 피해자 이메일은 assets.msn.com의 CORS 설정 오류 덕에 임의 사이트에서 `fetch`로 읽어 냈습니다.
- 제공된 본문은 이 네 가지를 엮는 대목에서 끊겨, 이후 단계(샌드박스 탈출까지 이어지는 나머지 버그)는 확인하지 못했습니다. 저자는 HITCON과 Hexacon 발표 자료를 따로 공개했다고 합니다.

브라우저 엔진 안에서 "브라우저 프로세스가 시작한 탐색"이 렌더러와 어떻게 묶이는지를 코드 수준으로 보여 줍니다. 기본값이 위험한 API 설계의 실례이기도 합니다. 저자 본인이 AI 없이 손으로 만든 체인임을 강조하는 글이고, 본문이 잘려 있어 전체 체인의 평가는 원문으로 확인해야 합니다.

### SVG 새니타이저 8개 중 6개가 뚫렸고, 응답 헤더 하나가 Firefox에서 JavaScript를 실행했습니다

`portswigger.net` (Lobsters 경유) [원문](https://portswigger.net/research/scalable-vector-grief)

본문이 완전히 무해한 XML인데도 `Link` 응답 헤더에 XSLT 스타일시트를 data URL로 실어 보내면 Firefox가 스크립트를 실행합니다.

- 저자는 SVG 업로드를 받는 서비스가 쓰는 새니타이저 8종을 시험해 6종을 우회했습니다. 대상은 ChatGPT에게 인기 라이브러리를 물어 고른 것이고, DOMPurify와 darylldoyle/svg-sanitizer는 이 글의 모든 공격을 막아 냈습니다.
- 가장 단순한 층은 네임스페이스 혼동입니다. 요소 하나의 XML 네임스페이스를 XHTML로 바꾸면 `<foreignObject>` 없이도 SVG 안에 `<frame src="javascript:...">`나 `srcdoc`이 있는 `<iframe>`이 HTML로 렌더링됩니다. 또 어떤 라이브러리는 렌더링하면서 이름이 camelCase `foreignObject`로 바뀌는데 소문자 `foreignobject`로 찾아서 아무것도 못 걸러냈습니다.
- `<animate>`가 링크의 `href`를 `JavaScript:alert(1)`로 바꾸는 방식으로 Borewit/svg-sanitizer를 통과했습니다. 별개로 `xml-stylesheet` 처리 명령이 data URL의 XSLT를 가리키면, 별도 파일 없이도 문서 출신(origin)으로 스크립트가 실행됩니다. 저자는 XSLT가 폐기되어 2026년 11월에 제거될 예정이라 서둘러 글을 썼다고 합니다.
- Firefox는 `Link` 헤더로 외부 CSS를 불러오는데, 저자는 data URL과 XSLT도 이 경로로 되는 것을 확인했습니다. Safari에서는 `<use href="test.png#x">`가 이미지 파일을 SVG로 가져오므로, 페이로드를 담은 GIF를 업로드해도 `<use>`로 불러 svg-hush류 세 라이브러리를 통과합니다.

사용자가 올린 SVG를 서비스하는 프론트엔드라면, "블록리스트 방식의 새니타이저"가 얼마나 약한지와 헤더, 처리 명령 같은 본문 밖 경로를 함께 봐야 한다는 점을 알려 줍니다. 두 개의 비공개 애플리케이션 사례는 아직 공개되지 않았고, 시험한 라이브러리는 8종뿐이라는 한계가 있습니다.

### 실패한 modulepreload는 다시 네트워크 요청을 보내지 않고 바로 reject될 수 있었습니다

`Harry Roberts` [원문](https://csswizardry.com/2026/10/web-perf-wednesday-015-failed-modulepreloads-need-to-recover/)

WebKit에서는 일시적 404 때문에 modulepreload가 한 번 실패하면, 이후 같은 URL을 `import()`해도 네트워크를 거치지 않고 곧바로 reject됐습니다.

- 문제는 preload가 실패했을 때 WebKit이 그 리소스를 메모리 캐시에 "preload됨"으로 남겨 둔 것입니다. 나중의 `import()`가 실패한 항목을 재사용해서 새 요청을 보내지 않았습니다. 짧은 CDN 장애나 끊긴 요청 한 번이 복구 불가능한 상태가 되는 셈입니다.
- modulepreload는 파일을 받는 데서 끝나지 않고 HTML 표준상 모듈 시맵(module map)에 결과를 올려 두는 특수한 preload입니다. 라우트 청크처럼 나중에 `import()`할 코드에 쓰이므로 이 경로의 실패는 곧 페이지 기능의 실패입니다. WebKit의 수정은 오류 확인을 preload 단축 경로보다 앞으로 옮겨, 실패한 리소스를 다시 받게 한 것입니다.
- 수정은 Safari Technology Preview 255에 들어갔고, 정식 Safari 반영 여부는 릴리스 노트에 없습니다. 그래서 기존 복구 코드를 지우라는 근거가 되지 못한다고 저자는 말합니다. 번들러가 분할 청크를 modulepreload한다면 첫 요청을 일부러 실패시키고 이후 `import()`나 새로고침이 실제 요청을 다시 보내는지 파이프라인에서 시험하라고 권합니다.
- 해시가 붙은 청크 이름은 배포 불일치만 막고 이 경우를 해결하지 못합니다. 랜덤 쿼리 문자열은 다른 모듈 시맵 항목이 되어 증상은 가리지만 원래 복구하려던 요청을 바꾸므로, 원래 URL로 지연을 둔 제한적 재시도와 사용자에게 보이는 재시도 UI를 권합니다. CDN과 서비스 워커가 같은 나쁜 응답을 계속 주지 않는지도 확인 대상입니다.
- 같은 호의 소소한 소식으로 Safari Web Inspector가 쓰로틀링을 반영한 응답 시간을 보고하도록 고쳐졌고, Firefox 159가 타임아웃 뒤 WebDriver 폴링이 종료까지 이어지던 메모리 누수를 고쳤습니다.

코드 분할과 청크 로딩 실패 복구를 직접 다루는 팀이면 바로 테스트 항목으로 옮길 수 있습니다. 성공한 경로만 재던 성능 감사에 "한 번 실패하고 복구되는" 경로를 넣자는 제안이 유용합니다. 필자가 성능 컨설턴트로서 글 끝에 자기 서비스를 안내하고 있고, 이 버그는 아직 Technology Preview에만 있는 수정이라는 점은 감안해야 합니다.

### JSON 체크포인트를 protobuf로 바꾸자 저장이 약 5배 빨라졌습니다

`OpenTelemetry` [원문](https://opentelemetry.io/blog/2026/filelog-protobuf-checkpoints/)

File Log receiver는 기본 설정에서 초당 5번 체크포인트를 쓰는데, 파일 1,000개를 추적하면 JSON 인코딩만으로 CPU를 초당 약 77ms 썼습니다.

- File Log receiver는 OpenTelemetry Collector에서 로그 파일을 읽는 컴포넌트이고, 체크포인트는 재시작해도 로그를 잃거나 중복하지 않도록 "어디까지 읽었는지"를 저장한 기록입니다. 저장소 확장을 켜면 기본 `poll_interval` 200ms마다 모든 추적 파일의 기록을 저장하므로 초당 5번 쓰이고, 읽는 것은 시작할 때 한 번뿐입니다. 쿠버네티스 노드에는 컨테이너 로그 파일이 수백 개 있습니다.
- 계기는 2025년 10월, 쿠버네티스 로그를 수집하는 Collector가 Fluent Bit보다 자원을 더 쓴다는 사용자 보고였습니다. 프로파일링하니 체크포인트의 JSON 인코딩에 CPU가 많이 쓰이고 있었습니다.
- JSON이 비싼 이유는 파일 지문(fingerprint)에 있습니다. 파일 앞 1,000바이트인 지문은 JSON에 raw 바이트를 넣을 수 없어 텍스트로 변환되며 크기가 약 3분의 1 늘고, 저장과 읽기마다 변환을 반복합니다. 거기에 레코드마다 필드 이름이 반복되고 숫자와 시각도 텍스트로 쓰입니다. 파일 하나 기준으로 1,818바이트가 1,186바이트가 됩니다.
- 파일 1,000개 기준 벤치마크에서 저장은 15.38ms에서 3.21ms(-79%), 읽기는 28.18ms에서 5.01ms(-82%)였고, 저장된 크기는 1.740MiB에서 1.139MiB(-35%), 저장당 할당 메모리는 5.807MiB에서 2.919MiB로 줄었습니다. 대신 레코드를 protobuf 메시지로 바꾸는 과정 때문에 할당 횟수는 10~13% 늘었습니다. 속도 향상은 파일 1개부터 1,000개까지 4~6.5배로 일정했습니다.
- v0.164.0부터는 항상 protobuf로 쓰고, 기존 JSON 체크포인트는 시작할 때 읽은 뒤 다음 저장에서 protobuf로 바뀌므로 읽기 오프셋을 잃지 않습니다. `polls_to_archive`의 아카이브도 같은 인코딩이라 같은 이득을 봅니다.

OpenTelemetry로 쿠버네티스 로그를 모으는 독자에게는 "조용한 반복 작업이 CPU를 좀먹는" 전형적인 사례이고, 업그레이드만으로 이득이 생깁니다. 벤치마크는 공용 클라우드 VM(4 vCPU)의 마이크로벤치마크라 절대값은 환경마다 다르고 비율만 참고해야 합니다. 프로덕션에서 얻은 개선 폭은 글에 없습니다.
