## 오늘 하나만 본다면

### AI로 만든 앱 24,664곳을 열어 보니 30%에서 이메일이 든 테이블이 로그인 없이 읽혔습니다

`crissyfield.de` (Lovable 연구 보고서, Hacker News 경유) [원문](https://www.crissyfield.de/research/lovable-en/)

여권번호 1,000건 이상과 비공개 채팅 메시지 20만 건 이상이, 로그인 없이 읽을 수 있는 상태로 AI가 만든 웹앱에 들어 있었습니다.

- 연구진은 자연어 설명만으로 웹앱을 만들어 주는 스웨덴 AI 서비스 Lovable로 만든 프로젝트 159,041개를 분석했습니다. 오픈 웹 아카이브 Common Crawl 데이터에서 2025년 12월부터 2026년 9월까지의 프로젝트를 골랐고, 그중 34,545개가 데이터베이스로 Supabase를 쓰고 있었습니다. 분석은 Supabase에 집중했는데, 연동 방식이 비교적 분석하기 쉽고 Lovable 프로젝트에서 가장 널리 쓰인다고 보기 때문입니다.
- 34,545개 중 24,664개 사이트는 페이지가 열리자마자, 로그인이나 다른 조작 없이 Supabase 레코드를 내려보냈습니다. 공개용 데이터일 수 있어서 그 자체는 문제가 아닙니다. 하지만 같은 API 키로 읽기 전용 요청을 더 보내 보니, 그 사이트 중 7,403곳(30%)에서 이메일 주소가 든 테이블이 총 10,560개 나왔습니다.
- 사례는 구체적입니다. 독일의 한 라이프스타일 포럼은 이름, 이메일, 생년월일이 든 프로필 8만 건 이상과 채팅 메시지 20만 건 이상을 노출했습니다. 한 서비스 업체는 여권번호, 만료일, 국적이 든 신분증 정보 1,000건 이상을, 부동산 관리 회사는 세입자와 소유주에 대한 내부 이메일을 AI로 요약한 내용을 노출했습니다. 한 사례에서는 고객에게 보낸 이메일 28만 통이 열람 가능했습니다.
- 저자가 직접 단 단서가 중요합니다. 이메일 주소는 공개 연락처나 테스트 데이터일 수 있고, 반대로 이메일이 없는 개인정보 레코드는 놓칩니다. 두 효과가 어느 정도 상쇄되는지는 확인하지 못했으므로 30%를 실제 유출률로 읽으면 안 됩니다. 표본도 Common Crawl에서 뽑은 것이라 전체 Lovable 앱을 대표하지 않고, 데이터는 일부만 내려받았으며 악용 여부도 확인하지 못했습니다.
- 구조적 문제로 짚는 지점은 두 가지입니다. 접근 제어 실수는 사람이 짠 앱에도 있지만, Lovable은 데이터베이스 연동이 반복되는 패턴을 따르기 때문에 한 앱에서 통하는 방법이 다른 앱에도 거의 그대로 통합니다. 그리고 Lovable의 약관은 앱과 데이터 처리의 책임을 고객에게 지우는데, 마케팅은 기술 지식이 필요 없다고 말해서 플랫폼이 보안까지 챙겨 줄 것 같은 인상을 줍니다.

AI가 코드를 대신 써 주는 시대에 검증 체계를 고민하는 독자에게, 결과물의 접근 권한 점검이 어디서 빠지는지를 숫자로 보여 주는 글입니다. 다만 업체가 보안 컨설팅 문의를 유도하는 문서이고, 취약점 접근 방법은 의도적으로 공개하지 않아 재현이나 검증은 할 수 없습니다.

### Project Zero는 AI가 패치 후 공격 시간을 0에 가깝게 만들었다며 공개 유예를 90일에서 30일까지 줄입니다

`projectzero.google` (Hacker News 경유) [원문](https://projectzero.google/2026/11/disclosure-policy.html)

Google의 보안 연구팀 Project Zero는 이제 패치가 나온 뒤 공격자가 취약점 상세를 알아내는 데 걸리는 시간을 "0"으로 가정해도 합리적이라고 말합니다.

- Project Zero는 2021년부터 "90 + 30" 정책을 써 왔습니다. 벤더에 수정할 시간 90일을 주고, 패치가 사용자에게 퍼질 시간으로 30일을 더 주는 방식입니다. 이 정책이 이제 불충분하다는 것이 이번 글의 출발점입니다.
- 근거는 LLM입니다. LLM이 공격자가 취약점을 찾고 악용하는 속도를 높였고, 같은 버그를 여러 쪽(악의적인 쪽 포함)이 따로 발견할 위험도 커졌습니다. 패치를 역공학해 악용하는 시간도 줄어서, 패치 후 공개까지 두는 30일의 유예(soak time)는 오히려 거짓 안전감을 줄 수 있다고 봅니다.
- 보고 건수도 바뀌었습니다. 예전에는 대상에서 1년에 몇 건 찾던 취약점을 지금은 일주일에 여러 건 찾고 있습니다. 그래서 벤더와 협의해야 하는 규칙(수정 여부 판단, 유예 적용 여부)은 관리가 어려워졌다고 설명합니다.
- 새 정책 이름은 "Full X"입니다. 보고 후 X일이 지나면 공개하고, 오늘부터 90일, 2027년 2월 2일부터 60일, 2028년 1월 3일부터 30일입니다. 유예와 변종 정책 같은 특례는 대부분 없애고, 예외는 실제 공격에 쓰이는 취약점, 이미 공개된 취약점, 벤더가 공개를 요청한 경우 셋뿐입니다.
- 단계적으로 줄이는 이유는 벤더 의견 때문입니다. 갑자기 줄이면 수정이 끝나지 않은 취약점이 공격자에게 노출될 수 있고, 덜 심각한 버그를 서둘러 고치느라 우선순위가 왜곡되거나, 지킬 수 없는 기한이라며 아예 포기할 수 있다는 우려였습니다. 심각도는 공개 시점을 정하는 기준으로 쓰지 않는데, 심각도는 공격자가 버그를 찾을 가능성이 아니라 피해 크기에만 영향을 주기 때문입니다.

Node와 npm 의존성을 운영하는 독자에게는 업스트림 보안 수정이 앞으로 더 빨리, 더 자주 공개된다는 신호입니다. 패치 적용 주기를 줄이는 쪽이 사실상 요구되는 방향입니다. 다만 이것은 정책 발표이고, "패치 후 악용 시간 0"은 글이 스스로 "불완전한 모델"이라고 밝힌 가정이며 측정 데이터는 실려 있지 않습니다.
