## 오늘 하나만 본다면

### LLM이 짠 테스트가 틀린 동작을 정답으로 못박았고, 자동 리뷰도 그걸 통과시켰습니다

`sunshowers.io` (Lobsters 경유) [원문](https://sunshowers.io/posts/nextest-install-scripts/)

Claude가 설치 스크립트에 HTTPS에서 HTTP로 가는 리다이렉트를 허용하는 동작을 넣고 그걸 검증하는 테스트까지 만들었는데, 뒤이어 돌린 Claude와 GPT의 자동 리뷰는 "테스트가 있으니 의도된 동작"이라고 판단했습니다.

- 저자는 Rust 테스트 러너 cargo-nextest의 메인테이너입니다. 출시 4년 반 만에 `curl | sh` 방식의 설치 스크립트를 처음 내놓았습니다. 그동안 미룬 이유는 유닉스용과 윈도우용 스크립트를 따로 유지해야 하고, 온갖 환경에서 생기는 문제를 끝없이 쫓게 될 것이라 자기 기준에 맞는 품질을 낼 자신이 없었기 때문입니다.
- 스크립트는 버전별 설치 매니페스트(아카이브 URL과 체크섬을 적은 텍스트 파일)를 받아 시스템에 맞는 빌드를 고르고, 체크섬을 검증한 뒤 설치합니다. glibc가 너무 오래됐거나 없으면 정적 링크된 musl 빌드를 고릅니다. macOS 기본 sh인 bash 3.2의 결함도 우회하고, aarch64 윈도우 위에서 x86_64 Git Bash를 쓰는 경우까지 감지합니다.
- 저자가 "vibed 방식"이라 부르는 흐름은 LLM에게 "실수 없이 써줘"라고 시키고, 버그가 나올 때마다 코드를 덧붙이는 것입니다. 그러면 반복되는 구간이 수백 줄인 스크립트가 됩니다. 저자는 설계(매니페스트 형식과 URL)는 직접 하고, 가장 큰 노력을 검증에 썼습니다. TLS를 붙인 HTTP 서버, 장애 주입 바이너리, 잘린 스크립트와 중단된 다운로드 테스트까지 갖춘 하네스를 LLM으로 만들었습니다. 몇 주가 걸릴 일을 LLM이 빠르게 채웠다고 합니다.
- 사람이 한 일은 설계 리뷰입니다. 두 모델의 자동 리뷰 뒤에 약 25시간, 4번의 주말을 들여 직접 읽었습니다. 집중을 유지하려고 에이전트가 특수 마커 없이는 주석을 쓰지 못하게 막았고, 이유를 글로 설명하려다 문제를 발견한 경우가 많았다고 합니다. 발견한 문제는 가장 기본적인 무옵션 경로의 테스트 부재, 해시를 문자열로 비교하던 테스트, HTTPS에서 HTTP로의 리다이렉트 허용, 윈도우의 Ctrl-C 테스트 부재입니다.
- 저자의 진단은 LLM이 언덕 하나를 골라 끝까지 오르지만 그 언덕이 맞는지는 묻지 않는다는 것입니다. 변경은 약 1만 줄이고 대부분 테스트입니다. 다만 한 사람의 경험담이고, 25시간의 수동 리뷰가 어느 규모의 프로젝트에까지 통하는지는 다루지 않습니다.

AI가 짠 테스트와 AI가 한 리뷰가 서로를 정당화하는 순환을 구체적인 사례로 보여 줍니다. 코드 리뷰와 검증 체계를 고민하는 독자에게 "무엇을 사람이 봐야 하는가"의 답을 줍니다. 한편 `curl | sh`가 새 신뢰 경계를 만들지 않는다는 저자의 주장은 각주 수준이라 근거가 얇습니다.

### 15년 전 트윗의 Bitly 링크가 재등록되어 엉뚱한 곳으로 연결됩니다

`ransomnews.com` (Hacker News 경유) [원문](https://ransomnews.com/burger-king-tweet-bitly-link-hijack-2026/)

계정이 해킹된 적이 없는 Burger King의 2011년 트윗이 2026년 11월 15일 오전에 나치 강제수용소 목록 위키백과로 연결되었고, 원인은 15년 전 짧은 링크의 뒷부분을 누군가 다시 등록한 것이었습니다.

- 원리는 단순합니다. Bitly 링크 `bit.ly/19BFiM`에서 슬래시 뒤의 뒷부분을 누가 새로 등록하면, 그 링크가 박힌 모든 트윗, 이메일, PDF, 인쇄된 QR 코드가 새 주인이 정한 곳으로 갑니다. 비밀번호를 훔치거나 계정을 건드릴 필요가 없어서 원래 링크를 올린 브랜드는 아무 이상도 못 봅니다.
- 증거는 Bitly가 모든 링크에 공개하는 정보 페이지(주소 끝에 `+`)의 생성 시각입니다. Burger King 링크는 2026년 11월 15일 05:32 UTC, McDonald's의 2011년 링크는 그보다 18분 빠른 05:14 UTC에 만들어진 것으로 나옵니다. 2011년 트윗에 2026년 생성 시각이 있을 수 없으니 같은 뒷부분이 두 번 발급된 것입니다.
- 필자는 Trump 계정의 2009~2013년 트윗에서 Bitly 링크 97개를 조사했습니다. 40개는 원본이고, 49개는 나중에 다시 만들어졌지만 원래 의도에 맞는 곳을 가리킵니다. 그중 48개는 2023년 5월 26일 17분 사이에 약 20초 간격으로 만들어졌는데, 원래 목적지를 아는 누군가의 복구 작업처럼 보인다고 합니다. 7개는 엉뚱한 곳(Roblox 프로필, YouTube 영상, 암호화폐 사칭 도메인 등)으로 가고 1개는 Bitly가 악성으로 차단했습니다.
- Bitly 도움말은 뒷부분이 계정을 삭제해도 재사용되지 않는다고 하고, 비활성 3년 계정을 삭제한다고 합니다. 두 설명이 실제 생성 날짜와 맞지 않습니다. 2025년 2월에도 비슷한 버그로 2013년 Trump 트윗 링크가 밈코인 홍보에 쓰인 사례가 보도되었고, Bitly는 당시 고쳤다고 했습니다. 이번에는 Bitly가 11월 15일 19:13 UTC에 문제를 확인하고 관련 계정을 정지했다고 밝혔습니다.
- 단서도 있습니다. 두 변경이 시간상 가깝다는 이유로 한 행위자일 가능성이 제기되었지만 필자는 증명된 것이 없다고 합니다. CNN이 보도한 Bill Gates, FBI 등의 링크는 필자가 직접 확인하지 않았습니다.

만료된 식별자를 다시 등록해 가로채는 구조는 npm에서 만료된 도메인이나 삭제된 패키지 이름을 재등록하는 공급망 공격과 같은 계열입니다. 문서, 이메일, 릴리스 노트에 외부 단축 링크를 박아 둔 적이 있다면 점검할 이유가 됩니다. 출처는 보안 점검 도구를 홍보하는 사이트이고, 조사는 한 계정의 표본에 기댄 것입니다.

### CSS 워킹그룹이 `appearance: base` 버튼에 `cursor: pointer`를 기본으로 주기로 했습니다

`blog.kizu.dev` (Lobsters 경유) [원문](https://blog.kizu.dev/cursors/)

버튼에 손가락 커서를 주느냐는 2013년부터 이어진 논쟁인데, 3주 전 CSS 워킹그룹이 처음으로 기본 스타일에 넣기로 결의했습니다. 단, 모든 버튼이 아니라 새로 도입되는 `appearance: base` 요소에만 적용됩니다.

- 결의 내용은 css-forms-1의 "base appearance용 커서" 이슈에서 마지막 코멘트의 규칙을 채택한다는 것입니다. 요약하면 포인터는 "이걸 클릭", 텍스트 커서는 "텍스트를 입력할 준비", 잡는 손은 "이걸 드래그"입니다.
- 대상은 `select`, `option`, 체크박스, 라디오, `button`, 버튼형 `input`, 색상 선택기, 이미지 입력, `::file-selector-button`입니다. 브라우저의 기존 기본 스타일을 바꾸는 것이 아니라 `appearance: base-…`가 적용된 요소에만 쓰이는 규칙입니다.
- 이 사용자 에이전트 스타일에는 `!important`가 없어서 사이트가 `default` 등으로 쉽게 덮어쓸 수 있습니다. 싫은 사람이 원하는 대로 돌릴 수 있다는 점이 합의의 바탕으로 보입니다.
- 저자는 2013년에 관련 글을 썼고 2017년에 첫 CSSWG 이슈를 열었습니다. 대표 반론인 "OS는 그렇게 안 한다"에 대해, OS가 UI에서 마지막으로 혁신한 게 언제냐고 되묻습니다. Slack, Discord, VS Code 같은 비네이티브 앱은 이미 손가락 커서를 씁니다. 저자는 버튼과 링크가 다른 커서를 가지고 링크 중에서도 새 탭으로 열리는 것이 다른 커서를 가지는 편이 더 낫다고도 인정합니다.

디자인 시스템이나 공통 컴포넌트에서 `cursor: pointer`를 버튼마다 선언해 온 팀이라면, 스타일 리셋 규칙이 어떻게 바뀔지 알아 둘 만합니다. 글은 저자의 개인 의견이 섞인 해설이고, 규칙의 최종 명세 문구는 직접 확인한 것이 아닙니다.

### 재귀 하강 파서는 뺄셈 결합 방향을 틀리게 만들고 `42` 하나에 함수를 네 번 부릅니다

`eli.thegreenplace.net` (Eli Bendersky, Lobsters 경유) [원문](https://eli.thegreenplace.net/2009/03/14/some-problems-of-recursive-descent-parsers)

2009년에 쓴 글입니다. 문법을 BNF로 그대로 옮긴 재귀 하강 파서에서 `5 - 1 - 2`를 돌리면 2가 아니라 6이 나옵니다.

- 원인은 문법 자체입니다. 좌재귀(자기 자신으로 시작하는 규칙)는 파서를 무한 루프에 빠뜨리기 때문에 `<expr> : <term> + <expr>`처럼 오른쪽에 재귀를 두는데, 이러면 식이 오른쪽부터 만들어져 우결합이 됩니다. 실행 로그를 보면 `1 - 2 = -1`을 먼저 계산한 뒤 `5 - (-1) = 6`을 냅니다. 덧셈과 곱셈은 순서가 달라도 결과가 같아 티가 안 나고, 뺄셈과 나눗셈에서만 틀립니다.
- 해결은 규칙을 EBNF로 바꾸는 것입니다. `<expr> : <term> {+ <term>}`처럼 중괄호로 "0번 이상 반복"을 표현하면 구현이 `while` 루프가 되고, 값을 왼쪽에서 오른쪽으로 누적해 `5 - 1 - 2`가 2가 됩니다. 여전히 LL(1) 문법입니다.
- 거듭제곱처럼 원래 우결합인 연산자는 재귀 규칙을 그대로 둡니다. `2^3^2`는 `2^(3^2) = 512`이지 `(2^3)^2 = 64`가 아닙니다.
- 두 번째 문제는 효율입니다. 연산자 우선순위를 표현할 방법이 `expr`, `term`, `power`, `factor`로 규칙을 겹겹이 중첩하는 것뿐이라, 숫자 `42` 하나를 파싱하는 데 함수가 4번 호출됩니다. 저자는 이를 순수 재귀 하강의 구조적 한계로 보고, 중위 표현식을 효율적으로 파싱하는 알고리즘과 재귀 하강을 섞은 하이브리드 파서를 해법으로 예고합니다. 이 글에서는 구현을 보여 주지 않습니다.

Babel, oxc, SWC 같은 도구가 우선순위 상승 방식(precedence climbing)이나 Pratt 파서로 표현식을 파싱하는 이유의 출발점을 쉽게 보여 줍니다. 예제는 Python 2.5이고 글이 15년도 더 되었지만, 문법 구조가 결합 방향과 성능을 정한다는 논지는 그대로입니다.

### AI가 만든 코드는 오픈 소스여야 한다는 주장이 있습니다

`jakub.jankiewicz.org` (Lobsters 경유) [원문](https://jakub.jankiewicz.org/blog/ai-code-open-source/)

저자는 사람이 거의 손대지 않은 AI 생성 코드는 공개 라이선스나 CC0로 풀어야 한다고 말하며, 스스로 이를 "핫 테이크"라고 부릅니다.

- 첫째 근거는 학습 데이터입니다. 모델은 GNU 프로젝트 이후 쓰인 오픈 소스 코드를 허락과 출처 표기 없이 긁어 학습했고, 귀속 표시를 법적으로 요구하는 Creative Commons 라이선스의 Stack Overflow 글도 학습했습니다. 이를 폐쇄형 코드로 바꾸는 것은 "라이선스 세탁"이라고 합니다.
- 둘째 근거는 법입니다. 순수하게 AI가 쓴 코드는 사람이 쓴 것이 아니라 저작권이 없어야 한다는 논리인데, 원숭이 셀카 분쟁에서 비인간은 저작권을 가질 수 없다고 한 선례를 미국 저작권청이 AI에 대해 인용했다고 합니다. 같은 논리로 Wikimedia Commons는 순수 AI 이미지를 퍼블릭 도메인으로 표기하게 합니다.
- 다만 법은 나라마다 다릅니다. 영국은 컴퓨터가 만든 저작물에 제한적인 저작권을 줍니다. 그래서 저자는 법적 판단과 별개로, 관할에 상관없이 공정하게 하려면 개발자와 기업이 스스로 오픈 소스나 CC0로 공개해야 한다고 주장합니다.
- 코드가 100% 수동이거나 100% 자동인 경우는 드뭅니다. 하지만 저자는 개발자들이 점점 결과물을 검토도 하지 않고 쓰며, 프롬프트 작성 말고는 사람이 들인 노력이 적은 코드는 공개되어야 한다고 봅니다. 어디까지가 "노력이 적은" 것인지 기준은 제시하지 않습니다.

AI 코드의 저작권과 라이선스 문제는 사내 공유 라이브러리와 의존성 정책에서 곧 부딪힐 질문입니다. 다만 글은 짧은 의견문이고, 판례와 법 해석을 한두 문장으로 요약해 단정하는 수준이라 법적 근거로 삼기는 어렵습니다.
