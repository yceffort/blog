### 컨테이너 CPU 한도를 2에서 1로 줄였더니 .NET 병렬 루프가 직렬이 됩니다

`Stack Overflow` [원문](https://stackoverflow.blog/2026/11/04/your-net-parallel-loop-can-become-serial-in-a-one-cpu-container/)

컨테이너의 CPU 한도를 2에서 1로 줄였을 뿐인데 200건 처리 시간이 42.1초에서 83.6초로 거의 두 배가 됐고, 에러는 하나도 나지 않았습니다.

- `Parallel.ForEachAsync`에 `ParallelOptions`를 넘기지 않으면 동시 실행 수는 `Environment.ProcessorCount`로 제한됩니다. 취소 토큰만 담은 옵션 객체를 넘겨도 `MaxDegreeOfParallelism`이 기본값 -1로 남아 같은 결과이고, -1을 명시해도 제한은 풀리지 않습니다. 옵션 객체가 있어서 안심하기 쉬운 지점입니다.
- Linux와 macOS, 그리고 .NET 6 이후의 Windows에서 `ProcessorCount`는 논리 프로세서 수, 프로세스의 CPU 어피니티 수, CPU 사용 한도를 올림한 값 중 가장 작은 값입니다. 그래서 CPU 한도 1이면 1, 0.5여도 1이 되고, 이 값은 런타임이 시작될 때 고정됩니다. 레코드 하나가 시간 대부분을 다른 서비스의 응답을 기다리는 I/O 작업이어도 이 CPU 기반 값이 동시성 상한이 됩니다.
- 필요한 동시성은 리틀의 법칙(처리 중인 항목 수는 처리량 곱하기 항목당 소요 시간)으로 추정합니다. 저자의 예시(실측이 아닌 설명용 계산)에서는 외부 호출 세 번에 360ms, 쓰기에 30ms가 걸리고 초당 100건을 처리하려면 동시에 약 39건이 진행 중이어야 하는데, CPU 1개 기본값은 1건만 허용합니다.
- 상한만 올리면 다운스트림이 다칩니다. 저자는 보강 API는 동시 요청을 많이 받지만 기록 시스템은 동시 6건만 처리하고 6건까지 대기시킨 뒤 HTTP 503을 반환하는 시뮬레이션을 만들어 비교했습니다. 쓰기가 30ms에서 150ms로 느려진 상황에서 의존 서비스별 세마포어(보강 24, 쓰기 6)를 둔 방식은 503이 0건이었고, 의존성 구분 없이 동시성만 키운 방식은 64건, 공용 세마포어 30개를 쓴 방식은 57건이었습니다. 처리량은 35.08, 34.35, 34.01 records/s로 거의 같았습니다.
- 대가도 있습니다. 두 서비스가 모두 정상일 때는 의존 서비스별 예산 방식이 58.38 records/s로 가장 느렸고, 공용 세마포어는 65.32, 제한 없는 방식은 67.86이었습니다. 저자는 신뢰성이 더 중요하면 11~14% 감소를 받아들이겠다고 쓰고, 컨테이너가 실제로 받을 CPU 한도에서 다시 측정하라고 권합니다. 이 수치는 모두 시뮬레이션 서비스에서 5회 실행한 중앙값이라 실제 시스템의 값이 아닙니다.

쿠버네티스에서 CPU limit을 낮춰 SSR이나 배치 서비스를 운영하는 팀이라면 "런타임이 CPU 한도에서 기본 동시성을 뽑는다"는 점을 한 번은 점검해야 합니다. Go 1.25의 GOMAXPROCS도 cgroup CPU 한도를 쓴다는 대목은 Node 서버의 풀 크기 설정을 돌아보게 합니다. 다만 저자가 AI 도구로 초안과 실험 코드를 상당 부분 만들었다고 공개했고, 결론은 시뮬레이션 기반입니다.

### Zig의 libc 재작성이 `strspn`을 매번 전체 길이부터 재서 SQLite를 12,000배 느리게 했습니다

`dennisforbes.ca` (Lobsters 경유) [원문](https://dennisforbes.ca/blog/microblog/2026/10/the_accidental_12000x_sqlite_slowdown/)

JSON 4만 건을 SQLite에 넣는 데 수 분이 걸렸고, 같은 코드가 Mac에서는 멀쩡했습니다.

- 저자는 Rust로 체스 분석 서비스를 만들고 있고, 크로스 컴파일을 위해 C로 쓰인 SQLite를 `zig cc`와 cargo-zigbuild로 Linux용으로 빌드했습니다. 러너가 돌려준 JSON 묶음을 SQLite에 넣는 단계에서 CPU 한 코어가 포화된 채 수 분이 걸렸고, Mac 빌드에서는 `zig cc`를 쓰지 않아 재현되지 않았습니다.
- 원인은 Zig가 musl libc 함수를 순수 Zig로 다시 쓰는 libzigc 작업입니다. `strspn`을 다시 쓴 버전은 첫 단계에서 문자열 전체 길이를 재고, `strcspn`, `strpbrk`, `strstr`의 재작성에도 같은 패턴이 있습니다.
- 토크나이저는 거대한 문자열에서 공백을 건너뛰는 호출을 계속 반복합니다. 호출할 때마다 남은 문자열 전체 길이를 다시 재니 입력이 커질수록 시간이 제곱으로 늘고, 1.2MB 파일을 토큰화하면 약 12,000배 느려진다고 저자는 씁니다.
- 저자가 처음 쓴 우회책은 JSON의 공백을 미리 제거하는 것이었고 비용이 크게 줄었습니다. 다른 곳에 같은 문제가 숨어 있을지 알 수 없어 결국 Linux 빌드를 컨테이너로 옮겼습니다. 제목의 "Shlemiel the Painter"는 Joel Spolsky가 2001년 글에서 든 예로, 페인트 통을 옮기지 않아 선이 길어질수록 왕복 시간이 늘어나는 일꾼 이야기입니다.

빌드 도구 체인이 표준 라이브러리를 조용히 바꿔치기해도 성능 프로파일이 달라질 수 있다는 사례입니다. 번들러나 컴파일러를 갈아끼우는 공통 인프라를 다루는 사람에게 닿는 교훈입니다. 원인 분석은 저자 한 명의 진단이고 Zig 쪽 확인이나 수정 여부는 글에 없습니다.

### Lighthouse 13.6은 사이트가 그대로여도 FCP와 LCP 점수를 올릴 수 있습니다

`Harry Roberts` [원문](https://csswizardry.com/2026/11/web-perf-wednesday-016-lighthouse-13-6-can-lift-scores-without-a-faster-site/)

PageSpeed Insights가 Lighthouse 13.6으로 올라가면서 HTML, JS, 이미지, CSS가 똑같아도 점수가 좋아질 수 있습니다.

- 바뀐 것은 Lantern이라는 시뮬레이션 모델입니다. PageSpeed Insights는 페이지를 실제로 로드한 뒤, 더 느린 환경이었다면 어땠을지를 이 모델로 추정합니다. Chrome의 Web Performance 개발자 옹호자 Barry Pollard가 새 시뮬레이션이 더 정확하고 대체로 더 좋은 FCP와 LCP를 낸다고 확인했고, JavaScript가 많은 사이트가 더 영향을 받을 것이라 예상했습니다.
- 첫 번째 변경은 렌더 차단 여부를 요청 우선순위로 추정하지 않고 Chrome이 알려주는 실제 렌더 차단 상태를 쓰는 것입니다. 우선순위가 높아도 페인트를 막지 않는 모듈 스크립트가 있어, 이전에는 무관한 작업이 FCP나 LCP를 늦춘 것처럼 계산될 수 있었습니다.
- 두 번째 변경은 LCP 요소가 FCP와 같은 프레임에 그려진 텍스트일 때 두 지표에 FCP의 의존성 그래프를 쓰는 것입니다. 그 텍스트가 기다리지 않은 프리로드 같은 요청이 예전에는 LCP 계산에 끌려 들어올 수 있었습니다. HTTP/2와 HTTP/3 연결 모델링, 리디렉션 처리, RTT와 처리량 추정도 함께 개선됐습니다.
- 그래서 업그레이드 시점을 가로지르는 시계열에는 아무도 배포하지 않은 개선이 그려집니다. 저자는 모든 합성 측정 결과에 Lighthouse와 브라우저 버전을 함께 기록하고, 대시보드에 업그레이드 날짜를 표시하라고 권합니다. CrUX 같은 현장 데이터는 방문에서 수집되므로 Lantern이 바뀌어도 변하지 않습니다. Calibre는 10월 31일에 13.6으로 옮겼고 이 두 수정은 시뮬레이션 스로틀링 프로파일에만 영향을 주며, Chrome DevTools의 Lighthouse 패널은 Chrome 159에서 13.6이 되므로 한동안 PSI와 로컬 결과가 어긋날 수 있습니다.

성능 지표를 팀 목표나 리포트로 관리하는 사람에게 "점수가 올랐다"는 사실만으로 성과를 주장하지 말라는 실무적 경고입니다. 이 글은 Web-Perf Wednesday 뉴스레터 형식이라 한 주제당 분량이 짧고, 글 끝에 저자의 컨설팅 안내가 붙어 있습니다.

### PHP2Shell은 2024년에 "그냥 크래시"로 방치된 버그를 AI가 치명적 취약점으로 바꾼 사례입니다

`spectrum.ieee.org` (Hacker News 경유) [원문](https://spectrum.ieee.org/ai-in-cybersecurity-php2shell-vulnerability)

PHP2Shell의 바탕이 된 버그는 2024년에 PHP Foundation에 보고돼 있었지만, 크래시만 일으킨다는 이유로 손대지 않은 채 남아 있었습니다.

- 문제의 버그는 데이터를 담기에 할당된 메모리가 작은 메모리 부족 오류로, 보통은 프로그램이 죽는 데서 끝나서 사람들이 심각하게 보지 않습니다. 올해 보안 회사 Calif가 OpenAI의 후원을 받아 PHP를 감사했고, 2주 만에 Calif 연구원이 AI 도구의 도움으로 이 버그를 서버에서 임의 코드를 실행하는 경로로 바꿨습니다.
- 영향 범위는 WordPress나 Drupal 등 PHP로 돌아가는 사이트이고, 기사는 NASA, Wikipedia, 백악관 사이트를 예로 듭니다. 악용 전에 연구자들이 발견해 패치가 먼저 나온 것으로 알려져 있다고 기사는 씁니다.
- 컬럼비아 대학의 Suman Jana는 악용에 필요한 것이 로켓 과학이 아니라 메모리의 특정 지점으로 점프하고 어떤 비트를 어떤 순서로 덮어쓸지 정하는 아주 구체적이고 고통스러운 추론이며, AI가 이 부분을 잘 한다고 말합니다. 다만 Calif, OpenAI, 취약점을 확인하고 확장한 Wiz의 연구자들은 보안과 PHP 양쪽에 깊은 지식이 있었고, Jana도 AI가 혼자 다 할 수는 없다고 선을 긋습니다.
- 버그를 찾는 쪽과 고치는 쪽에는 비대칭이 있습니다. 패치는 공격 경로를 모두 막으면서 기존 기능을 깨지 않아야 하고, 이번에는 엔지니어 4명이 2달을 들였습니다. Jana는 LLM이 패치를 만들고 다른 LLM이 그 정확성의 증명을 만들되 증명 검사기만은 LLM이 아니어야 한다는 접근(Anthropic이 10월 22일에 공개한 것을 언급)에 낙관적이고, Johns Hopkins의 Matthew Green은 "정말 나쁜 일이 터지기 전에는 아무도 고치지 않는다"며 2027년 초를 점칩니다.

AI가 코드 리뷰와 검증 체계를 바꾼다는 맥락에서, 오래된 코드베이스와 의존성의 "그냥 크래시" 이슈를 어떻게 분류하고 있는지를 돌아보게 합니다. 인용은 대부분 학자와 보안 업계 인사의 의견이고, 구체적 공격 기법이나 재현 데이터는 기사에 없어 방향성을 보여주는 글로 읽는 편이 맞습니다.

### 검증된 결과는 지식이 아니고, 이해와 책임은 정확성과 분리되지 않는다는 논증입니다

`blog.cosmos-institute.org` (Jessica Hullman, Hacker News 경유) [원문](https://blog.cosmos-institute.org/p/verification-is-not-knowledge)

AI가 만든 암 치료제가 3상 임상까지 통과했다면 그 치료제를 왜 이해하려 드는가라는 질문에, 저자는 이해를 정확성 위에 얹은 선택 사항으로 두는 순간 논쟁에서 진다고 답합니다.

- 논쟁의 틀은 이렇습니다. Terence Tao가 "형식 증명서와 3상 시험 통과가 붙은 AI의 암 치료제를, 사람이 어떻게 찾았는지 이해하지 못한 채 쓰겠느냐"고 물었을 때, 결과가 중요하다는 쪽은 4기 환자라면 당연히 쓴다고 반박했습니다. 저자는 이해를 옹호하는 쪽이 이해와 정확성의 분리를 받아들이면 이미 졌다고 봅니다.
- 저자가 짚는 핵심은 이해가 누군가의 머릿속 상태가 아니라 무언가 잘못됐을 때 일어나는 일이라는 점입니다. Tao의 시나리오에서는 AI가 시험 자체의 약점을 악용해 통과했을 가능성이 문제이고, 저자들이 설명하지 못하는 논문은 주장이 틀렸을 때 물어볼 사람이 없습니다. 여기서 책임은 주장이 무엇에 근거하는지 설명하고 도전에 답할 수 있는 것을 뜻합니다.
- 정확성만이 과학의 가치라는 믿음은 냉전기 이후 퍼진 "가치 중립 이상"에서 나왔다고 저자는 진단합니다. 과학이 사회에 신뢰받으려면 개인의 의도와 가치에서 방법이 자유로워야 한다는 생각이었고, 과학철학자 대부분은 이제 이 이상을 기각합니다. 수학에서도 정리는 무한히 많아 어떤 문제를 흥미롭다고 고르는 데 이미 가치가 들어가고, 페르마의 마지막 정리도 증명이 있다는 주장이 남긴 흥미 때문에 중심이 됐으며 동료 심사가 오류를 잡아낸 뒤 해결로 받아들여졌습니다.
- 에이전트를 많이 써 본 사람이 아는 표류의 위험도 짚습니다. 사양이 분명한 파이프라인이라 생각해도 예상치 못한 가지에서 헤매기 쉽고, 인식적 주체성을 주장하지 않으면 질문 없는 답, 곧 "어디에도 없는 시점"만 남습니다. 비판 없이는 객관성이 없다는 Helen Longino의 논지를 빌려, 과학의 객관성은 검증 엔진이 아니라 공유된 언어와 상호 비판에서 나온다고 정리합니다.

코드 리뷰에서 "테스트가 통과했다"와 "이 변경을 이해한다"를 같은 것으로 취급하는 에이전트 시대의 습관을 정면으로 다시 묻는 글입니다. 필자는 Northwestern의 컴퓨터 과학 교수이고 이 글은 과학 연구를 다루지만, 소프트웨어 검증에도 그대로 옮겨 읽을 수 있습니다. 가져온 본문이 중간에서 끊겨 있어 글의 후반부 결론은 확인하지 못했습니다.

## 보안과 릴리스
