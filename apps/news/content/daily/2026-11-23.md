## 오늘 하나만 본다면

### AI 라우터를 거친 프롬프트의 비밀값은 중간 어디에선가 새고 있습니다

`arstechnica.com` (Dan Goodin, Lobsters 경유) [원문](https://arstechnica.com/security/2026/11/a-leaky-ai-supply-chain-is-exposing-secret-user-data-at-an-alarming-rate/)

한 연구자가 가짜 비밀값이 든 프롬프트 200만 건을 AI 서비스에 보냈더니, 일부 키가 심은 지 몇 시간 만에 공격자 손에서 수만 번의 AWS API 호출에 쓰였습니다.

- 보안 기업 Dragos의 HD Moore는 한 번도 쓰인 적 없는 AWS 액세스 키, SSH 비밀번호, 고유 URL, 비공개 git 저장소 주소를 만들어 프롬프트에 하나씩 심었습니다. 비밀값 하나는 정확히 한 제공자에게 보낸 요청 하나에만 들어 있으므로, 나중에 어디선가 쓰이면 어느 구간에서 샜는지 특정할 수 있습니다. 탄광의 카나리아 같은 탐지용 미끼라서 canary라고 부릅니다.
- 개발자가 OpenRouter나 Vercel 같은 AI 라우터(가격이나 적합도에 따라 요청을 여러 추론 서버로 나눠 보내는 중개 서비스)를 쓰면 프롬프트는 전송 중에는 암호화돼도 경유지마다 복호화됩니다. 라우터가 평문을 읽어야 어디로 보낼지 정하기 때문이고, 경유지마다 로그를 남길 수 있습니다.
- 가장 심각한 발견은 호스팅 제공자 세 곳이 침해당했다는 것입니다. 한 곳에서는 10월 말 몇 번의 짧은 시간대에 보낸 요청이 전부 탈취됐고, 모델이 돌기 전에 거부된 요청의 키까지 쓰였습니다. 공격자가 추론 엔진 깊은 곳이 아니라 입구에서 요청을 복사하고 있었다는 뜻입니다. 탈취된 키는 심은 지 몇 시간 안에 S3 버킷과 시크릿 매니저를 뒤지고 Bedrock을 켜고 IAM 사용자를 추가하는 데 쓰였고, 두 곳의 키는 같은 임대 서버에서 거의 동시에 쓰여 같은 공격자로 추정됩니다.
- 침해와 별개로 일부 재판매업자는 낮은 가격으로 트래픽을 끌어들인 뒤 요청 로깅을 켜고 프롬프트를 흘렸습니다. 같은 모델을 여러 판매자로 호출해 비교하는 방식으로 모델 제공자가 아니라 재판매업자가 범인임을 가려냈습니다. 또 한 중국 AI 연구소의 시스템은 7월부터 10월까지 받은 프롬프트의 절반 넘게에서 비밀 URL을 나중에 직접 가져갔는데, 'Zero Data Retention'이나 'no data collection' 표시가 붙은 요청도 약 3분의 2가 포함됩니다. 미국 호스팅 업체를 통해 그 모델을 호출한 요청도 같은 스크레이퍼를 불렀습니다.
- Moore의 권고는 온프레미스 자체 호스팅이 가장 안전하고, 그게 어려우면 계약과 개인정보 정책이 하나뿐인 1차 제공자에게 직접 접속하라는 것입니다. 라우터나 재판매업자의 기본 풀을 받아들이지 말고 상위 제공자를 직접 고르라고도 합니다. 11월 21일 갱신에 따르면 OpenRouter는 MiniMax 모델 엔드포인트에서 Zero Data Retention 표시를 제거했고, 일부 프롬프트가 읽혔을 수 있다고 고객에게 메일을 보냈습니다.

AI 코딩 도구와 에이전트에 시크릿이 담긴 컨텍스트가 흘러 들어가는 시대에, 프라이버시 플래그를 믿을 수 있는지에 대한 실측 데이터입니다. 다만 Ars Technica가 Moore의 글을 요약한 기사이므로 제공자 이름과 세부 수치는 원 연구를 확인해야 하고, 침해당한 세 곳의 신원은 기사에 나오지 않습니다.

### Blogger 피드는 1초짜리 캐시 앞에서만 If-Modified-Since가 통하고, ETag는 gzip을 요청해야 받습니다

`joshua.hu` (Lobsters 경유) [원문](https://joshua.hu/fixing-google-feedburner-cache-problem-atom-rss)

Chrome 릴리스 블로그의 자체 피드 주소는 모두 https로 요청해도 http로 리다이렉트되어, 보안 릴리스 공지가 평문으로 내려갑니다.

- 지난 글에서 저자는 Chrome Releases 블로그의 Atom 피드가 Feedburner(구글이 운영하는 피드 중계 서비스)로 리다이렉트되고, 그 결과가 며칠씩 낡아 있다고 썼습니다. 저자의 봇 CCBot은 이 피드를 파싱해 Chromium 취약점 수정 소식을 알려주는 용도라 낡은 피드가 곤란했습니다. 이번에 `?redirect=false` 파라미터를 붙이면 리다이렉트 없이 최신 피드를 받을 수 있다는 걸 발견했습니다. Feedburner 도움말에도 "항상 동작해야 한다"고 적힌 형식이라 완전한 비밀은 아닙니다.
- 캐시 동작은 일관되지 않습니다. Feedburner는 여전히 ETag를 안 보내고 If-Modified-Since를 무시하며 no-cache를 지시합니다. `redirect=false` 피드는 If-Modified-Since에 304를 주긴 하는데, 같은 요청을 12번 연달아 보내면 매초 첫 요청만 200이고 나머지는 `age: 0`과 함께 304가 옵니다. 응답이 `max-age=1`이라 앞단의 캐시가 1초 동안만 복사본을 들고 있고, 만료된 뒤에는 뒤의 `blogger-renderd` 서버가 If-Modified-Since를 무시하고 전체를 다시 보내기 때문입니다. 몇 분 간격으로 폴링하는 클라이언트에게는 304가 영원히 오지 않습니다.
- If-None-Match는 통하지만 조건이 있습니다. `Accept-Encoding: gzip`을 보낸 응답에만 ETag가 붙고, br이나 zstd만 요청하면 서버가 지원하지 않아 ETag 없이 비압축으로 응답합니다. 일단 ETag를 받으면 캐시 우회 파라미터를 붙여도 304가 열 번 모두 옵니다. 전체 피드는 비압축 1,725,860바이트, gzip 57,817바이트이고 304는 거의 0바이트인데, Feedburner는 매번 55,792바이트(gzip)를 보냅니다.
- 가장 눈여겨볼 것은 보안 쪽입니다. 블로그의 모든 피드 URL이 https로 요청해도 `http://feeds.feedburner.com/GoogleChromeReleases`로 리다이렉트되고, Feedburner는 https로 되돌리지 않고 평문으로 피드를 서빙합니다. 그래서 이 링크를 구독한 클라이언트는 Chrome 보안 릴리스 공지를 암호화 없이 받고, 네트워크 경로의 누군가가 가짜 릴리스 글을 끼워 넣거나 진짜 보안 업데이트를 지울 수 있다고 저자는 지적합니다. 정리하면 `?redirect=false`로 폴링하고, gzip을 요청하고, 받은 ETag를 If-None-Match로 돌려보내라는 것입니다.

조건부 요청이 서버 앞단 캐시와 원 서버 중 어느 쪽에서 처리되는지에 따라 같은 헤더가 다르게 동작한다는 사례로, CDN 뒤의 캐시를 다루는 사람에게 도움이 됩니다. 저자의 curl 관찰에 근거하고 구글 쪽 설명은 없어서, 원인(앞단 캐시가 1초만 유효)은 저자의 추정으로 읽어야 합니다.

### GitHub Actions는 YAML 명세 위반을 받아들이고, 그래서 표준 파서로는 일부 워크플로를 읽을 수 없습니다

`yossarian.net` (Lobsters 경유) [원문](https://yossarian.net/til/post/github-actions-accepts-invalid-yaml/)

공백 하나가 모자란 줄이 GitHub에서는 정상 워크플로이고 명세를 지키는 YAML 파서에서는 오류입니다.

- 1년 반 전, 워크플로 보안 정적 분석 도구 zizmor에 한 사용자가 이슈를 올렸습니다. 어떤 스텝이 멀티라인 flow 스타일 문자열(`json: '{ ... }'`)을 쓰는데 zizmor가 파싱을 거부한다는 내용이었고, 이 스텝은 GitHub에서는 문제없이 돌았습니다.
- 원인은 YAML 1.2.2 명세 8.2.3절입니다. block 스타일 부모 컬렉션 안의 flow 노드는 부모보다 최소 한 칸 더 들여써야 하는데, 문제의 스텝은 닫는 `}'` 줄을 맞추지 않았습니다. 올바른 코드와의 차이는 공백 한 칸이라 눈으로는 거의 보이지 않습니다.
- 저자는 처음에 이게 YAML 명세 위반일 줄 몰라 tree-sitter-yaml에서 파서 쪽을 고치는 PR을 열었습니다. 이번에 그 수정을 되돌리는 PR을 열었습니다. 명세를 엄격히 지키는 쪽이 맞는데, GitHub가 받아들이는 입력을 전부 읽어야 하는 도구는 선택지가 없다는 딜레마입니다.
- GitHub Actions는 대부분 비공개 코드라 확정은 아니지만, 저자는 파서가 2018년에 나온 YamlDotNet 5.3.0이라고 봅니다. 최신 18.1.0에도 같은 버그가 남아 있습니다(`!isSingleQuoted` 조건 때문입니다). 2020년 패치(YamlDotNet#467)가 큰따옴표 문자열만 고친 이유를 저자는 YAML 공식 테스트 스위트가 8.2.3절을 큰따옴표로만 검증하기 때문이라고 추측합니다.

CI 워크플로를 린트하거나 정적 분석하는 도구를 만드는 사람에게는 "GitHub가 받아주는 것"과 "명세가 허용하는 것"이 다르다는 사실이 바로 걸립니다. 글이 짧고 저자 스스로 GitHub 쪽 파서와 패치 경위를 추측이라고 밝히므로 원인 분석은 가설로 읽어야 합니다.

### 단위 테스트와 통합 테스트라는 말 대신 범위, 가설, 오라클로 테스트를 나눠 봅니다

`alperenkeles.com` (Hacker News 경유) [원문](https://alperenkeles.com/posts/vocab-for-testing/)

2025년 8월에 쓴 글입니다. "단위"가 무엇인지 정의되지 않은 채 쓰이는 단위 테스트라는 말을 버리고 테스트를 다섯 축으로 쪼갭니다.

- 저자는 기존 분류가 모호하다고 봅니다. 단위 테스트의 '단위'는 정의되어 있지 않고, 통합 테스트는 임의 범위의 모듈을 묶은 것이며, E2E는 자동 에이전트를 쓰는지 사람이 감독하는지 무작위 탐색인지를 뭉개고, 부하, 스트레스, 침투 테스트는 기준 없이 "분위기"로 갈립니다. 그래서 자원 상황에 따라 테스트를 올리거나 내릴 수 있는 실행 가능한 어휘를 제안하는데, 본인이 연구하는 무작위 테스트 쪽으로 편향되어 있다고 먼저 밝힙니다.
- 첫째 축은 범위입니다. 함수, 클래스, 모듈, 시스템 같은 언어 구조 축과 상태가 있는지 없는지의 축이 있습니다. 함수는 언어가 허용하는 임의 구조를 입력으로 받지만, 시스템은 직렬화되어 파싱과 검증을 거친 입력만 받으므로 입력 공간이 자연스럽게 좁혀집니다. 상태가 있는 함수는 상태를 입력과 출력에 포함시켜 무상태 함수로 바꿀 수 있지만, 현실적인 부하를 담은 복잡한 상태는 만들기 어려워서 그 경우 시스템을 시뮬레이션처럼 다루고 공개 API 메시지로 불변식과 사전, 사후 조건을 확인합니다.
- 입력 공간이 필요 이상으로 넓은 문제에는 계약에 의한 설계(Design by Contract)를 권합니다. 가정을 함수 주석이 아니라 런타임, 때로는 컴파일 타임에 검사되는 어노테이션으로 적는 방식입니다. 예를 들어 읽어 둔 키 목록으로 해시맵을 조회하면 모든 조회가 성공해야 하는데 언어는 매번 실패 가능하다고 보니, 언어와 싸우는 느낌이 듭니다. 표현력이 좋은 타입 시스템과 도메인 모델링이 이 긴장을 줄여 준다고 합니다.
- 둘째 축은 가설입니다. 모든 테스트는 반증 가능한 가설을 세우고 반증을 시도하는 일이고, 기능 정확성 외에 실행 시간, 보안(타이밍 사이드 채널), 장애 내성(카오스 테스트), 접근성도 각자의 가설을 가집니다. 셋째 축은 그 가설을 판정하는 오라클입니다. 사람의 판단(저자는 "tinker testing"이라 부르고 모든 자동화 테스트가 결국 이를 코드로 굳힌 것이라고 봅니다), 예시 기반(스냅샷이나 expect 테스트 포함), 인라인 어서션(사전 조건, 사후 조건, 불변식)을 차례로 설명하고, 네 번째로 속성 기반 오라클을 소개하는 대목에서 제가 읽은 본문이 끊겨 이후는 확인하지 못했습니다.

AI가 테스트와 코드를 대량으로 쓰는 시대에 "이 테스트는 무엇을 반증하려 하고, 무엇이 판정하는가"를 따지는 틀을 줍니다. 다만 분류 자체가 저자의 제안이고 합의된 용어가 아니며, 글의 앞 절반을 근거로 한 요약입니다.

## 보안과 릴리스

- [pnpm 12.23.0](https://pnpm.io/blog/releases/12.23.0) `pnpm` **보안.** `otp`를 어떤 설정 파일에서도 읽지 않고(저장소가 `otp: ${NPM_TOKEN}`을 적어 두면 publish 때 그 환경 변수가 레지스트리로 새는 경로였습니다), 레지스트리 자격 증명은 HTTPS나 루프백 HTTP로만 보내며, 레지스트리 패키지가 선언한 `file:`, `link:` 로컬 의존성을 거부합니다. `pnpm dlx`와 `pnpm create`는 작업 디렉터리의 로컬 설정을 무시하게 됐습니다. 원문은 등급을 밝히지 않았습니다. 내가 할 일: 설정 파일에 `otp`를 두었다면 `--otp`나 `PNPM_CONFIG_OTP`로 옮기고, `pnpm-lock.yaml`에 git이나 tarball 서브 의존성이 있으면 `blockExoticSubdeps` 검사가 이제 실제로 걸리니 설치 오류를 확인합니다.
- [pnpm 12.23.0](https://pnpm.io/blog/releases/12.23.0) `pnpm` 이 릴리스는 `pnpm edit`, `pnpm catalog migrate`, `pnpm link --hard`를 추가하고 `--minimum-release-age` 옵션을 install과 add, update, dlx에 붙였습니다. 플랫폼 variants는 삭제되어 플랫폼별 빌드는 각각 별도 패키지로 발행하고 `optionalDependencies`에 나열해야 하며, variants를 기록한 lockfile의 frozen 설치는 `ERR_PNPM_BROKEN_LOCKFILE`로 실패합니다.
- [pnpm 11.29.0](https://pnpm.io/blog/releases/11.29.0) `pnpm` **보안.** 11.x 계열에도 같은 `otp` 설정 파일 읽기 중단, 로컬 파일시스템 의존성 거부, HTTPS 전용 자격 증명 전송, `blockExoticSubdeps`의 lockfile 적용이 들어갔습니다. 원문은 등급을 밝히지 않았습니다. 내가 할 일: 12.x로 못 올리는 프로젝트는 11.29.0으로 올립니다. 이 버전은 Docker 빌드처럼 TTY가 없을 때 호환되지 않는 `node_modules`를 확인 없이 다시 만들고 경고만 출력하도록도 바뀌었습니다.
