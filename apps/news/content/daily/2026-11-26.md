## 오늘 하나만 본다면

### AI를 쓰느냐가 아니라 사고가 났을 때 누가 책임지느냐가 "신경 쓰는 사람"을 가른다

`iankduncan.com` (Hacker News 경유) [원문](https://www.iankduncan.com/engineering/2026-11-19-smart-people-who-give-a-shit-use-tools)

"AI를 쓰면 시스템에 신경 쓰기를 포기하는 것"이라는 주장에 대해, 저자는 정반대로 LLM이 지금까지 시간 때문에 못 하던 엄밀함을 싸게 만들어 준다고 반박합니다.

- 반박 대상은 Justin Michael의 글입니다. 결제망 같은 낡은 인프라를 몇몇 "신경 쓰는 똑똑한 사람들"이 지탱한다는 진단과, 경영진이 이들을 생성형 AI로 바꾸려다 Microsoft 365, United, 대형 은행, Apple의 장애가 났다는 지적에는 저자도 동의합니다. 다만 Michael의 글이 거기서 더 나아가 프롬프트 하나하나가 엔지니어를 시스템에서 멀어지게 하고 고민의 과정을 빼앗는다고, 즉 도구 자체가 사람을 녹인다고 말하는 대목에 이의를 제기합니다.
- 저자의 핵심 주장은 LLM이 이미 가진 성향을 증폭한다는 것입니다. 2024년 이전의 "신경 쓴다"는 대개 시간과의 싸움이었습니다. 상태 기계의 경쟁 조건을 보면 TLA+로 모델링하거나 모든 인터리빙을 두드리는 속성 기반 테스트를 쓰거나 4만 줄짜리 하위 서비스를 읽어야 한다는 걸 알았지만, 이틀이 걸려 못 했고 해피 패스 단위 테스트만 쓰고 넘어갔다고 합니다. 모델이 있으면 이런 사람이 실제로 TLA+ 스펙을 쓰고, 한 번도 제대로 못 만들던 서드파티 API 시뮬레이터를 만들고, 레거시 함수의 모든 호출자를 추적한 뒤 계약을 바꾸고, 뮤테이션 테스트까지 돌린다고 씁니다.
- 반대편 위험도 인정합니다. "accept all"을 누르고 린터만 통과한 1,500줄 PR을 올린 뒤 400번째 줄을 설명하지 못하는 사람이 실제로 있고, 컴파일러는 크게 실패하지만 모델은 매끄럽고 자신감 있는 문장으로 실패한다는 점이 게으름을 유혹합니다. 버그와 스택 트레이스를 직접 겪지 않은 초년차는 "뭔가 이상하다"는 감각을 쌓지 못한다는 우려도 있습니다. 그러나 저자는 이 사람이 10년 전에는 Stack Overflow 최상위 답을 댓글도 안 읽고 붙여 넣던 사람과 같다고 보고, LLM을 빼앗아도 갑자기 신경 쓰게 되지 않고 더 느리게 부주의할 뿐이라고 말합니다.
- 장애의 더 큰 원인은 AI가 아니라 40년간 쌓인 엄밀함 부족이라는 주장입니다. 메모리 안전하지 않은 언어로 핵심 인프라를 짓고, 명세가 부족한 프로토콜을 이어 붙이고, 형식 검증을 건너뛰고, 엣지 케이스를 한 사람 머릿속에만 둔 대가를 지금 치르고 있다고 봅니다. 잠들지 않는 자동화 버그 탐색이 오래 묵은 취약점을 한꺼번에 끌어내고 있다는 설명입니다. 경영진 책임도 면제하지 않습니다. 비싼 시니어를 월 200달러 구독으로 대체하겠다는 발상은 "핵심 플랫폼을 최저가 외주로", "QA를 없애고 개발자가 테스트하게"와 같은 오래된 환상의 새 버전이라고 합니다.
- 누가 신경 쓰는지 알고 싶다면 LLM을 썼는지가 아니라 다른 것을 물으라고 합니다. 병합한 코드가 새벽 2시에 깨지면 어떻게 되는지, 코드 리뷰에서 "모델이 썼다"가 변명으로 통하는지, VP에게 일정이 무모하다고 말할 시간과 지위와 후원이 있는지입니다. 책임과 권한을 걷어내고 배포량으로 보상하는 회사가 신경 쓰는 사람을 잃는다는 결론입니다.

AI 코딩 도구 시대의 리뷰와 검증 체계를 고민하는 독자에게, "AI 사용 여부"라는 흔한 프레임을 "검증하고 책임지는 구조가 있는가"로 바꿔 주는 글입니다. 다만 근거는 저자 본인의 경험과 논증이고 측정한 데이터는 없으며, 반박하는 원글은 이 본문에 실려 있지 않아 요약된 쪽의 주장만 확인했습니다.

### Anthropic은 5개월 만에 API를 Rust로 다시 썼고, 코드의 20%만 자세히 봤다

`The Pragmatic Engineer` [원문](https://newsletter.pragmaticengineer.com/p/how-anthropic-builds-software-in)

Anthropic의 플랫폼 엔지니어링 책임자는 Rust 전문가 없이 API를 Rust로 다시 썼고, 생성된 코드를 자세히 본 비율은 약 20%였다고 말합니다.

- 모든 Claude 토큰을 외부에 내보내는 Messages API는 인증, 토큰화, 과금, 안전 검사를 거쳐 GPU 스택을 호출하는 Python 모놀리스였습니다. 연구팀과 겹치던 2023년의 소규모 팀이 Python으로 만들었고, CPU 사용량이 문제가 되자 먼저 Python을 최적화했지만 오버헤드가 컸습니다. 결국 몇 명이 몇 달 만에, 약 5개월 동안 Rust로 다시 썼고 그중 Rust 전문가는 없었다고 합니다. 1년 전 같은 팀이 새 서비스에 Go를 고른 것은 팀원이 읽고 쓸 수 있는 언어였기 때문이고, 2026년에는 Claude가 Rust를 충분히 한다고 판단했다는 설명입니다.
- 엄격한 코드 리뷰 없이 가능했던 이유는 기존 Python API가 완벽한 테스트 하네스였기 때문입니다. 새 Rust API가 프로덕션 트래픽을 따라 받는 섀도 방식으로 돌리며 응답이 모두 같아질 때까지 고쳤다고 합니다. 인터뷰이는 "검증할 수 있는 형태로 줄일 수 있다면 모든 줄을 볼 필요가 없다"고 말합니다.
- 리뷰와 온콜에도 에이전트가 들어와 있습니다. 모든 PR에 코드 리뷰 분류기가 돌아 사람 리뷰가 필요한지, 몇 명이 필요한지, 어느 팀이 봐야 하는지를 정합니다. SDK 버전 올리기나 플래키 테스트 수정 같은 기계적이고 위험이 낮은 변경은 다른 Claude가 리뷰하고 병합과 배포까지 합니다. API 온콜은 몇 달간 Claude가 사람을 따라 학습한 뒤, 이제 알림이 진짜인지 노이즈인지를 사람보다 먼저 분류합니다. 장애 자체를 사람 없이 처리하는 것은 아직 목표 단계입니다.
- 바뀌지 않은 것도 있다고 합니다. 여러 팀과 맞춰야 하는 기획과 합의에 드는 시간은 AI 이전과 비슷하고, 팀은 여전히 5~8명 규모로 시스템을 소유하고 온콜을 선다고 합니다. 바뀐 것은 코딩 면접을 폐지한 점(직접 코드를 쓰지 않아 다른 면접은 잘 보는 후보가 코딩 면접에서 떨어졌다고 합니다)과, 1년 걸릴 프로젝트가 며칠에서 몇 주로 줄어 승진 평가에서 완료 시간 대신 절약한 CPU와 줄어든 지연과 막은 장애 같은 영향을 본다는 점입니다.

생성 코드의 리뷰를 "줄 단위로 읽기"에서 "검증 가능하게 만들기"로 옮기는 구체적 사례여서, 팀의 리뷰 체계를 고민하는 리더에게 닿습니다. 다만 팟캐스트 요약 뉴스레터이고 20%라는 수치는 인터뷰이의 추정이며 전부 회사 쪽 자체 보고입니다. 기술적 상세는 Anthropic이 따로 낸 마이그레이션 글에 있다고 하니 그쪽을 확인해야 합니다.

### 이전 버전을 사전으로 삼으면 번들이 Brotli 단독보다 90% 작아지지만, 전달 경로 전체가 맞아야 합니다

`Harry Roberts` [원문](https://csswizardry.com/2026/11/web-perf-wednesday-019-firefox-ships-dictionary-compression/)

Firefox 161이 Compression Dictionary Transport를 지원하면서, 유튜브 플레이어 번들의 주 단위 업데이트가 Brotli만 쓴 것보다 90% 작아진 사례가 다시 주목받고 있습니다.

- 원리는 브라우저가 이미 가진 이전 버전 리소스를 사전으로 삼고, 서버가 다음 버전에서 바뀐 부분 위주로 보내는 것입니다. 첫 응답이 `Use-As-Dictionary` 헤더로 사전으로 쓸 수 있다고 선언하고, 이후 같은 종류의 요청에서 브라우저가 사전 해시를 `Available-Dictionary`로, 지원 방식을 `dcb`(Brotli) 또는 `dcz`(Zstandard)로 알립니다. 적절한 사전이 없으면 평소의 Brotli, Zstandard, gzip으로 돌아갑니다.
- 근거 수치는 프로젝트가 공개한 예시입니다. 유튜브 플레이어 번들의 주 단위 업데이트가 Brotli 단독 대비 90% 작았고, 오래된 CNN의 React 번들은 63% 작았습니다. 저자는 특정 과거 리소스로 낸 수치이므로 예측치가 아니라 자기 릴리스를 직접 측정해 보라는 근거로 읽으라고 단서를 답니다.
- 모든 자산에 맞는 기술은 아닙니다. 용량이 크고, 배포가 잦고, 재방문이 많고, 버전 사이 변경이 작은 파일이 후보입니다. 일회성 캠페인 번들이나 매번 처음부터 다시 빌드되는 파일은 재사용할 바이트가 적습니다. 배포 주기와 캐시 수명이 겹쳐야 어제의 바이트가 쓸모가 있고, 이미 사전을 가진 방문자에게만 효과가 있습니다.
- 서빙 조건이 까다롭습니다. IETF 표준은 보안 컨텍스트를 요구하고, 브라우저의 사전은 응답의 캐시 신선도에 묶입니다. MDN 구현 가이드에 따르면 `no-store`, `no-cache`, `max-age=0, must-revalidate`는 응답이 사전으로 쓰이는 것을 막고, 캐시되는 응답은 `Accept-Encoding`과 `Available-Dictionary`로 Vary해야 하며 교차 출처 리소스는 CORS 응답이 필요합니다. 제안은 크고 자주 바뀌는 동일 출처 자산 하나에서 시작해, 빌드 때 사전 압축 변형을 만들고 일반 압축 응답도 남긴 뒤, CDN이 새 요청 헤더를 키로 쓰고 전달하는지 확인하고 재방문 전송량을 비교하는 것입니다.

번들 크기와 재방문 성능을 다루는 독자에게, 새 압축 방식이 "켜면 되는" 기능이 아니라 캐시 헤더와 CDN과 배포 주기를 함께 설계해야 하는 기능임을 보여 줍니다. 브라우저 지원이 아직 제한적이고 MDN도 실험적 기능으로 표시하며, 글 끝은 자문 서비스 홍보이므로 점진적 개선으로 파일럿을 돌려 보는 정도가 알맞습니다.

### 단돈 3달러로 미국 재무부 서브도메인을 탈취했습니다. AWS Elastic IP를 계속 받고 반납한 것이 전부입니다

`intruder.io` (Lobsters 경유) [원문](https://www.intruder.io/research/taking-over-us-treasury-subdomains-for-3-each)

보안 업체 Intruder는 48시간 동안 AWS Elastic IP 45만 개를 돌려 받아, 전체 주소 공간의 1%도 안 보고 `treasury.gov` 서브도메인 5개를 포함해 28개 탈취에 성공했습니다.

- 공격 대상은 "DNS는 아직 가리키는데 서버는 없어진" 댕글링 레코드입니다. Elastic IP는 AWS에서 누구나 받을 수 있는 공인 IP이고, 한 번 반납된 주소는 다른 계정에 무작위로 다시 할당됩니다. 전체 풀은 최대 약 8천만 개(실제로는 절반쯤)라 원하는 주소를 지정할 수는 없지만, 반복해서 받고 반납하며 내 대상 목록의 A 레코드와 맞는지 확인하면 됩니다.
- 자동화 루프는 이렇습니다. 공개 버그 바운티 범위에서 서브도메인을 모아 A 레코드를 DynamoDB에 저장해 두고, 리전마다 Elastic IP 25개를 할당해 일치하는 것만 남기고 나머지는 반납한 뒤 다음 리전으로 넘어갑니다. 기본 한도는 리전당 5개지만 25개로의 증액은 지원 요청 없이 자동 승인되었습니다. 같은 리전에서 반납 직후 다시 받으면 같은 주소가 나오는 경향이 있어, 리전을 돌려야 새 주소가 나왔습니다.
- 결과는 48시간에 45만 개 주소, 28건의 실제 탈취(절반 가까이가 정부 기관)입니다. 이후 AWS가 모든 리전에서 Elastic IP 할당과 연결을 막았지만, 같은 조직 안에 새 계정을 만들고 이미 잡은 IP를 옮기는 것은 막히지 않았습니다. 계정 제한만으로는 의미가 약하다는 뜻입니다. 시간당 약 9,400개 속도면 계정 하나로 전체를 도는 데 1년, 10개 계정이면 5주 정도로 추산하며, 특정 조직(예: eu-west-2의 약 220만 개)을 노리면 범위가 줄지만 같은 리전에서 반복 할당하면 중복이 늘어 더 느려진다고 합니다.
- 영향은 단순한 피싱에 그치지 않습니다. `.gov`와 HTTPS를 신뢰하는 사용자를 속일 수 있고, 도메인 소유 검증을 통과해 정식 TLS 인증서를 받을 수 있으며, 옛 자동화가 아직 이 주소로 보내는 자격 증명도 가로챌 수 있습니다. 상위 도메인 쿠키를 `Domain=treasury.gov`로 설정했다면 탈취한 서브도메인이 그 쿠키를 받아 다른 앱의 세션 탈취로 이어질 수 있습니다.
- 대응은 아직 열려 있습니다. 저자들은 월간 Elastic IP 할당 한도와 계정이 아닌 조직 단위 제한을 AWS에 제안했지만, AWS는 이를 고객 쪽 DNS 레코드 문제로 보고 변경 계획이 없다고 답했고(2026-11-17), 신속한 할당과 반납은 정책 위반으로 통제하고 있다고 했습니다.

클라우드 위에서 서비스를 운영하는 독자에게, 서비스를 내릴 때 DNS 레코드를 함께 지워야 한다는 점과 상위 도메인 쿠키 범위의 위험을 구체적 수치로 보여 줍니다. 실험은 업체 자체 보고이고 AWS의 입장은 다르며, 45만 개 표본에서 전체를 추정한 값이라는 한계가 있습니다.

### 스타일 쿼리는 요소 자신을 못 보지만, 조건과 스타일이 서로 다른 곳에 있을 때 모디파이어보다 낫습니다

`CSS-Tricks` [원문](https://css-tricks.com/css-style-queries-as-conditional-modifiers/)

`.card`에 `--card-layout`을 지정하고 같은 `.card`를 스타일 쿼리로 조회하면 동작하지 않습니다. 스타일 쿼리는 조상만 봅니다.

- 기존 모디파이어(`.card--compact` 같은 클래스나 `data-` 속성)는 요소에 직접 붙입니다. 사이드바의 카드를 전부 compact로 하고 싶으면 템플릿 반복문 안에서 모든 카드에 붙여야 합니다. 또 디자이너가 페이지 아래쪽에서는 작은 패딩이 오히려 어색하다고 하면 컨텍스트에 따라 바뀌어야 하는데, 모디파이어는 이를 표현하기 어렵습니다.
- 컨테이너 스타일 쿼리(`@container style(--theme: high-contrast)`)는 가장 가까운 컨테이너의 커스텀 프로퍼티 값을 조건으로 삼습니다. 모든 요소가 기본으로 스타일 컨테이너라 `container-type`을 선언할 필요가 없고, 지금은 커스텀 프로퍼티만 조회할 수 있습니다. `style(display: flex)` 같은 일반 프로퍼티 조회는 명세에 있지만 아직 어디서도 지원되지 않습니다. 같은 요소를 조회하지 못하는 한계는 곧 나올 `if()`가 보완하지만, `if()`는 프로퍼티 하나에만 쓸 수 있고 스타일 쿼리는 여러 프로퍼티를 한 규칙에 묶을 수 있습니다.
- 이점은 스위치가 열린다는 것입니다. 스타일을 한 번 쓰고 나면 미디어 쿼리, 컨테이너 쿼리, `:has()`, 부모 섹션 어디서든 커스텀 프로퍼티만 바꾸면 켜집니다. CMS에서는 작성자가 옵션을 고르면 섹션의 값 하나만 바뀌어 맞는 스타일이 적용됩니다. 700px보다 넓을 때 사이드바에만 `--card-density: compact`를 주는 식입니다.
- 예시는 오버플로 그리드입니다. 방향을 `--overflow-grid-direction`(기본 `column`) 설정값으로 열어 두고, 분할 섹션이 2열로 바뀔 때 이 값을 `row`로 바꿉니다. 그러면 그리드가 `@container style(--overflow-grid-direction: row)`로 변화를 "듣고" 단일 열과 `max-block-size: 50vb`로 스스로 조정합니다. 부모가 자식을 직접 스타일링하지 않고 설정값만 바꾸므로 코드가 덜 깨지기 쉽다는 설명입니다.
- 모디파이어를 대체하는 것은 아닙니다. 버튼을 accent나 pill로 만드는 것처럼 요소 자신의 변형은 여전히 모디파이어가 낫고, 스타일 쿼리는 자기 자신을 못 보기 때문입니다. 일반 미디어/컨테이너 쿼리나 내재적 패턴으로 충분하면 그쪽이 맞습니다.

공유 컴포넌트 라이브러리를 만드는 팀에게, 컴포넌트가 "어디에 놓이든 스스로 적응"하게 하는 설계 기준으로 참고할 만합니다. 다만 글이 저자의 유료 강의 한 챕터를 각색한 것이고 "Baseline Newly Available"이라는 주장 외에 브라우저 지원 수치는 없으며, 실제 프로덕션 사례가 아니라 데모 수준 예제입니다.

## 보안과 릴리스

- [Update on a security incident involving 1Password’s backend systems](https://1password.com/blog/update-on-nov-2026-security-incident) `1password.com` (Lobsters 경유) **보안.** 11월 19일 직원 GitHub 계정 탈취로 소스 코드와 CI/CD에 접근하고 백엔드에 악성 코드를 올려, 일부 고객의 이름, 이메일, 계정 식별자와 초대와 복구 메일의 토큰을 내려받았다고 합니다. 볼트 내용과 이를 보호하는 키는 영향이 없다고 하며, 복구 코드는 숫자 6자리에서 영숫자 10자리로 늘렸습니다. 내가 할 일: 1Password를 사용 중이면 이 이름을 사칭한 초대나 복구 메일과 전화에 주의하고, 암호와 Secret Key는 앱이나 직접 입력한 공식 주소에서만 입력합니다.
- [Slow Ubuntu security response times](https://www.openwall.com/lists/oss-security/2026/11/25/9) `openwall.com` (Hanno Böck, Lobsters 경유) **보안.** Hanno Böck가 11월 16일 공개된 원격 TCP 메모리 손상 취약점 NoisyTCP(CVE-2026-99288)에 Ubuntu가 9일이 지나도 수정을 내지 않았고, 11월 18일 공개된 AMD 가상화용 KVM 호스트 탈출(CVE-2026-99312)도 미수정이라고 지적합니다. 그는 Ubuntu가 kernel.org 장기 지원 커널 대신 오래된 버전에 백포트하기 때문이라고 보고, 장기 지원 릴리스 기반을 권합니다. 내가 할 일: Ubuntu 서버나 컨테이너 호스트를 운영한다면 두 CVE 페이지의 수정 상태를 확인하고 노출 범위를 점검합니다. 등급은 원문이 밝히지 않았습니다.
- [Firefox 161 릴리스 노트](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/161) `developer.mozilla.org` (Frontend Focus 경유) Compression Dictionary Transport와 CSS `random()` 함수를 지원합니다. `random()`은 이제 Chrome, Safari, Firefox에서 모두 쓸 수 있습니다.
- [Workflow is 10x faster, again](https://vercel.com/changelog/workflows-speculative-execution) `Vercel Blog` Workflow SDK 5.8이 새 실행 엔진으로 단계 간 지연 p75를 85ms에서 7ms로 줄였고, 병렬 256단계 팬아웃의 오버헤드는 13.5초에서 2.5초가 되었습니다(자체 벤치마크). 멱등한 단계는 투기적으로 먼저 실행될 수 있어, 재시도하면 안 되는 단계는 `maxRetries = 0`으로 표시해야 합니다.
