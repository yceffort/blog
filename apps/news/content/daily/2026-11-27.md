## 오늘 하나만 본다면

### CSS 믹스인은 마크업을 공개 API로 만들지 않고도 테마를 열어 준다

`patrickbrosset.com` (Lobsters 경유) [원문](https://patrickbrosset.com/articles/2026-11-25-the-beauty-of-css-mixins/)

값 하나가 아니라 선언 묶음 전체를 이름 붙여 재사용하는 `@mixin`이 곧 Chromium에 들어오는데, 저자는 이것이 CSS Zen Garden식 테마의 고질병인 "내 HTML이 곧 공개 API가 되는 문제"를 푼다고 봅니다.

- 믹스인은 `@mixin --이름 { ... }`으로 정의하고 `@apply --이름;`으로 씁니다. 커스텀 프로퍼티는 값 하나, CSS 함수는 속성 값 안에서만 쓰이는 반면 믹스인은 선언 여러 개와 중첩 규칙까지 담습니다. `--button(--bg <color>: royalblue, --fg <color>: white)`처럼 타입과 기본값이 있는 매개변수도 받고, 인자를 매개변수보다 많이 넘기면 `@apply`는 아무 일도 하지 않습니다.
- `@contents`는 호출하는 쪽이 넘긴 CSS 블록이 들어갈 자리를 표시합니다. 이것과 `@media`를 묶어 `--mobile`, `--tablet`, `--desktop` 같은 이름 붙은 브레이크포인트를 한 곳에서 정의하고 `@apply --mobile { display: none; }`처럼 쓸 수 있습니다. `@private` 블록에 둔 변수는 믹스인을 적용한 요소에서 보이지 않습니다.
- 저자가 실험한 테마 구조는 이렇습니다. 사이트는 의미 있는 HTML과 기본 CSS를 갖고, `--page`, `--masthead`, `--site-title` 같은 정의되지 않은 믹스인을 논리적인 위치마다 적용해 둡니다. 정의가 없으면 아무 일도 없고, 고객이 스타일시트에서 그 믹스인을 정의하면 그 자리에 디자인이 들어갑니다. 고객이 셀렉터로 마크업 구조에 의존하게 되면 HTML을 바꾸지 못하게 되는데, 이 구조는 HTML을 마음대로 바꿀 수 있게 둡니다. CSS 변수만 노출하는 방식은 안전하지만 레이아웃 같은 영역은 열 수 없는데, 믹스인은 선언, 의사 요소, 미디어 쿼리, 애니메이션까지 넣을 수 있는 진입점이 됩니다.
- 직접 만든 Mixin Zen Garden 데모에서 얻은 교훈은 믹스인 이름을 모양이 아니라 역할로 짓는 것(`--sidebar-heading`)과, 정의되지 않은 믹스인은 무해하니 디자인이 필요한 것만 정의해도 된다는 점입니다. 한계도 밝힙니다. 믹스인 안에서 `& h2 { ... }` 같은 중첩 셀렉터를 쓰면 마크업이 다시 계약이 되므로, 실제로 쓰려면 허용된 셀렉터만 쓰는지 검증해야 합니다. 그리고 지금은 Chromium의 실험 기능 플래그 뒤에서만 동작합니다.

저자는 Microsoft에서 Chromium의 믹스인 구현을 맡은 팀 소속이라 낙관적인 입장이고, 다른 브라우저의 지원은 아직 없습니다. 공유 라이브러리나 디자인 시스템을 운영하는 입장에서는 "무엇을 외부 계약으로 열 것인가"를 CSS 문법 수준에서 다시 생각하게 하는 글입니다. 이름 붙은 브레이크포인트와 접근성 규칙을 믹스인 한 곳에 모으는 활용도 읽어 볼 만합니다.

### 브라우저 탭 하나가 컨테이너 하나가 되면 Mac에서 Linux VM이 필요 없습니다

`fzakaria.com` (Lobsters 경유) [원문](https://fzakaria.com/2026/11/25/browser-tabs-as-a-container-runtime)

`docker run --runtime tabc alpine`이 동작하고 1초 안에 뜨는데, 컨테이너가 호스트 커널에 닿지 않고 Chromium 탭 안에서 WebAssembly로 컴파일된 Linux 커널 위에서 돕니다.

- 기존 컨테이너 런타임 runc는 호스트 Linux 커널의 네임스페이스와 seccomp로 격리합니다. 그래서 Mac의 Docker Desktop, Colima, OrbStack은 먼저 Linux VM을 띄웁니다. tabc는 OCI 런타임(Docker가 컨테이너를 실제로 실행하라고 맡기는 규격)을 구현해 컨테이너마다 브라우저 탭을 하나씩 열고, 격리는 Chromium의 렌더러 샌드박스와 V8의 WebAssembly가 맡습니다.
- 가능해진 이유는 Pooya Parsa의 unkernel입니다. Linux 커널 자체를 WebAssembly로 컴파일해서, 기존의 JSLinux나 v86처럼 머신 전체를 에뮬레이션하지 않고 컨테이너 안의 프로그램 코드만 에뮬레이터를 거칩니다. 나머지 커널 동작은 거의 네이티브 속도로 돕니다.
- 저자의 Ryzen 7 7840U Linux 노트북에서 Alpine의 `echo hi`는 명령부터 종료까지 약 0.87초였고, 그중 503ms가 Chromium을 여는 시간이었습니다. 이미 떠 있는 브라우저를 `--open`이나 `--link`로 쓰면 이 비용은 사라집니다.
- 비용은 분명합니다. 프로그램은 여전히 에뮬레이션되므로 `find`, 5M 제곱합 파이썬, 32MB gzip 해제 같은 작업이 네이티브 runc 대비 11배에서 36배 느렸습니다. 유휴 컨테이너 하나가 호스트 메모리를 약 540MiB 쓰는데, 저자가 비교용으로 든 Firecracker는 microVM당 오버헤드가 5MiB 미만, 부팅이 125ms입니다.
- Docker가 없는 Mac에서는 tabc가 이미지를 직접 받고, compose는 자체 경량 데몬 tocker가 처리합니다. 컨테이너의 페이지가 pty라서 터미널과 탭에서 같은 셸을 같이 만질 수 있습니다.

컨테이너 격리를 커널이 아니라 브라우저 샌드박스가 맡는다는 발상은 SSR 서비스 컨테이너를 운영하는 독자에게 격리 모델을 다시 따져 보게 합니다. 다만 개인 블로그의 실험 프로젝트이고 보안 성질은 주장 수준이며, 속도와 메모리 수치는 저자 한 대의 노트북 측정입니다.

### 에러를 불투명하게 돌려주면 호출한 쪽이 폭탄 돌리기를 하게 됩니다

`amit.prasad.me` (Lobsters 경유) [원문](https://amit.prasad.me/blog/ambiguous-errors)

호출자가 실패에 대해 할 수 있는 일은 재시도, 입력 수정, 포기, 남 탓하기 넷뿐인데, 대부분의 에러 타입은 그 넷 중 무엇인지조차 알려 주지 않습니다.

- 소프트웨어의 경계(라이브러리, OS, 원격 서비스)를 넘으면 호출자가 가진 정보는 돌려받은 에러가 전부입니다. HTTP 500, `-EINVAL`, gRPC의 `Status.INTERNAL`, `{"status": "error"}` 같은 불투명한 에러만 받으면 선택지는 두 가지입니다. 에러를 역공학해서 Hyrum의 법칙(관찰 가능한 동작은 누군가 의존하게 된다는 법칙)을 부추기거나, 모든 `catch`와 `?`를 터질 폭탄처럼 그냥 위로 넘기는 것입니다.
- 불투명함은 전염됩니다. 한 번 받아 버리면 무엇이 잘못됐는지 되살리는 비용이 그냥 넘기는 비용보다 커서 호출자도 넘기고, 그 위의 호출자도 같은 문제를 떠안습니다. 강한 타입의 에러를 지원하는 Rust도 예외가 아닙니다. `io::Error`는 OS의 errno를 감싼 "신 에러"이고, `fs::remove_file`의 `NotFound`는 대부분의 호출자에게 사실상 성공인데도 다른 에러와 함께 `?`로 올라갑니다. 애플리케이션용 `anyhow`, 라이브러리용 `thiserror`라는 통념도, 모든 애플리케이션이 누군가의 라이브러리가 될 수 있다는 점에서 한계가 있다고 봅니다.
- 저자가 일하는 Modal의 강화학습 사례가 구체적입니다. 롤아웃 중 샌드박스가 실패하면 트레이너가 어떻게 실패했는지 알아야 합니다. 인프라 실패는 학습을 왜곡하지 않도록 버려야 하는데, 보상을 노리는 모델이 불리해지면 일부러 샌드박스를 죽여 벌점을 피하는 법을 배울 수도 있기 때문입니다. 에러 계약이 있으면 트레이너가 둘을 구분해 처리할 수 있습니다.
- 주장은 타입이 있는 에러를 API의 일부로 보고 새 에러 변형 추가를 호환성 깨짐으로 취급하자는 것입니다. 계약을 쓰다 보면 인터페이스가 암시한 방식으로는 사실 실패할 수 없다는 것이나 상위 실패에 더 탄력적으로 대응할 수 있다는 것을 발견하게 됩니다. 에이전트 코딩 도구가 있으니 실행 그래프의 잎에서 위로 올라가며 모든 에러를 나열해 정리하는 작업도 현실적이라고 덧붙입니다.

공유 라이브러리와 API 경계를 설계하는 독자에게 "에러도 계약"이라는 관점은 바로 적용되는 이야기입니다. 글이 짧아 구체적인 설계 패턴이나 비용 분석은 없고, 사례도 Rust와 Modal 내부에 치우쳐 있어 프런트엔드로 옮겨 올 때는 스스로 번역해야 합니다.

### 에이전트가 풀어 낸 디버깅 과정이 사라지면 패치만 남고 지식은 남지 않습니다

`Stack Overflow`

에이전트가 에러를 만나 검색하고 여러 처방을 시도해 동작하는 길을 찾은 뒤 조용히 넘어가면, 개발자에게는 바뀐 파일과 안심시키는 요약만 도착합니다.

- 글쓴이는 주니어 시절 선배가 PHP를 명령줄에서 실행해 작은 변경을 확인하는 법을 가르쳐 준 일을 떠올립니다. 팀은 대화, 코드 리뷰, 트러블슈팅 노트로 "무엇이 잘못됐고 어떤 진단이 오도했고 무엇이 먹혔는지"를 쌓아 왔는데, 에이전트가 비공개 세션에서 문제를 풀면 검색할 수 없는 곳으로 사라진다는 우려입니다. 2026 개발자 설문에서 단순한 질문으로 Stack Overflow를 찾는 빈도가 줄었다는 응답이 64.1%, 질문 수 자체가 줄었다는 응답이 28.9%라고 인용하지만, 자체 보고이며 AI가 원인이라는 증거는 아니라고 직접 단서를 답니다.
- 구체 사례는 공개 저장소 grader-issue-lab의 PR #10입니다. 린트, 단위 테스트, 통합 테스트는 통과했는데 인가 인수 테스트만 실패했습니다. 존재하지 않는 주문 ID에는 `KeyError`가 나고 남의 주문에는 접근 거부가 나서, 호출자가 ID의 존재 여부를 알아낼 수 있었기 때문입니다. 에이전트는 두 경우를 모두 `AccessDenied("order not found")`로 바꿔 통과시켰고, 최종 성공 보고만 있었다면 "다른 검사가 걸러내지 못한 동작 차이를 인수 테스트가 잡았다"는 사실이 묻혔을 것입니다.
- 에러 문자열만으로는 부족합니다. "connection timed out"은 무관한 원인 여러 개에 해당할 수 있어서, 드라이버, 런타임, 이미 시도한 진단 명령 같은 맥락 없이는 의미 검색이 그럴듯하지만 다른 장애의 답을 찾아 줍니다. 그래서 저자가 구상 중인 방식은 에이전트 세션에서 실패 사실을 모으고, 권한 범위 안에서 기존 지식을 먼저 검색해 출처와 해결 상태와 함께 보여 주며, 맞는 것이 없을 때만 검토용 질문 초안을 만드는 것입니다. 단, 아직 개발 중인 방향이며 완성된 제품 사례가 아닙니다.
- 경계도 분명합니다. 에이전트가 앱과 테스트 단언을 같이 고쳐 놓고 원래 문제를 해결했다고 결론낼 수 있으므로, 회복된 세션을 전부 문서로 만들면 그럴듯하지만 틀린 결론이 쌓입니다. 그래서 "그럴듯한 생각", "한 번 관찰된 우회", "독립적으로 재현된 수정", "전문가가 승인한 답"을 구분하고 사람이 고치게 하자고 합니다. 성공 지표도 만든 질문 수가 아니라 다음 세션의 에이전트가 답을 찾았는지, 반복 조사가 줄었는지, 같은 에러가 재발했는지입니다.

에이전트가 만든 변경을 "무엇이 증거인가"로 검증해야 한다는 문제의식은 AI 코딩 시대의 리뷰 체계를 고민하는 독자에게 닿습니다. 다만 Q&A 제품을 파는 회사의 글이라 결론이 제품 방향과 맞닿아 있고, 구상 중인 시스템의 효과를 보여 주는 데이터는 없습니다.

### LLM 시대의 소프트웨어 위기에는 형식 검증이 주류 언어에 들어와야 한다는 주장입니다

`blainehansen.me` (Lobsters 경유) [원문](https://blainehansen.me/post/mainstream-verifiable-language/)

저자는 "LLM이 증명도 써 줄 테니 사람은 몰라도 된다"는 기대를 "순전한 자기기만"이라고 부르며 못 박습니다.

- 출발점은 LLM 때문에 소프트웨어 엔지니어링의 품질이 곤두박질치고 있다는 진단입니다. 원래도 허술하고 숙고가 부족했던 관행을 이제 모두가 LLM 속도로 가속하고 있다는 것입니다. 해법은 만들 수 있는 것은 사후 검증하고 나머지는 다시 쓰는 형식 검증의 전면 수용이지만, 기존 검증 도구는 사용성과 이해 가능성 문제로 업계 문화에 영향을 주지 못했다고 봅니다.
- 증명 도구와 LLM만 좋아져도 충분하지 않은 이유는 세 가지입니다. 브라우저부터 임베디드까지 어디서든 돌아가는 코드를 검증할 수 있어야 하고, 현업 엔지니어가 증명된 코드가 가능하다는 것을 알고 LLM에게 그렇게 쓰라고 시킬 만큼 익숙해야 하며, 올바른 것이 증명되고 있는지 판단할 만큼 정확성 속성을 추론할 수 있어야 합니다. Lean의 Leonardo de Moura가 한 말을 인용해, 정리의 진술이 의도한 것을 담았는지 확인하는 것은 자동화로 없앨 수 없는 "사람의 계약"이라고 강조합니다.
- 저자의 프로젝트 Magmide는 원래 새 증명 보조기와 어셈블리 수준 언어까지 만들려 했다가 Lean이 빠르게 발전하고 어셈블리 수준은 채택에 불필요하다는 점, 사업 모델이 맞지 않는다는 점을 깨닫고 접었습니다. 지금 시작한다면 WebAssembly GC로 컴파일하고, 차용 검사기 없이 Rust에 영감받은 타입 시스템에, SMT 기반의 리퀴드 타입과 흐름 효과로 시작해 나중에 Lean을 증명 계층으로 붙이는 "아래에서 위로" 설계를 하겠다고 합니다. 채택 모델로는 "그냥 JS/TS"인데 런타임 권한 검사를 더해 샌드박스를 신경 쓰는 엔지니어들이 받아들인 Deno를 듭니다.
- 결론은 ASI가 모든 문제를 해결해 주기를 기다리며 미래를 걸지 말고, 소프트웨어 엔지니어링 전체가 모든 코드에 최소한 "증명 가능한 안전"을 요구하며 성숙해야 한다는 것입니다.

에이전트 시대에 검증 체계를 어디까지 끌어올릴지 고민하는 독자에게 극단의 한 입장을 보여 주는 글입니다. 다만 아직 존재하지 않는 언어에 대한 제안이고 실증 데이터는 없으며, 프런트엔드 현장에서 형식 검증이 얼마나 현실적인지는 글이 다루지 않습니다. 쓸 수 있는 부분은 "무엇을 증명할지는 사람이 판단한다"는 지점입니다.

### Google은 2027년 2월부터 AI 에이전트가 Workspace를 MCP 서버로만 쓰게 하는데, Gmail MCP에는 메일 보내기가 없습니다

`techstackups.com` (Hacker News 경유) [원문](https://techstackups.com/articles/google-workspace-ai-agents-mcp/)

Gmail MCP 서버는 검색, 스레드 읽기, 초안 작성은 되지만 전송, 답장, 전달, 초안 수정은 "파트너 접근이 필요하고 일반 제공되지 않는다"고 Google의 쿼터 문서가 밝힙니다.

- 11월 24일 Google이 Workspace MCP 서버 8개를 정식 출시하면서 API 약관에 조항을 추가했습니다. 2027년 2월 1일부터 "AI 에이전트이거나 AI 에이전트가 구동하는" 도구는 Gmail, Drive, Calendar 등에 이 서버를 통해서만 접근해야 합니다. 에이전트가 REST API를 직접 부르면 유료 티어와 상관없이 Standard 쿼터가 적용되고, 약관 위반이 되어 접근 제한이나 계정 정지가 가능합니다. AI가 없는 백업 작업이나 결정적 스크립트는 영향이 없다고 합니다.
- 데이터 규칙도 있습니다. Workspace 데이터는 사용자가 승인한 활성 작업에만 처리해야 하고, 연결이 끊기면 삭제해야 합니다. 벡터 임베딩, 메모리 인덱스, 사용자 프로필 같은 "Google 기술 정보"는 보관을 30일로 제한할 수 있고, 학습, 파인튜닝, 평가, 증류는 금지됩니다. 지난해 계약서를 묻는 어시스턴트가 받은편지함의 장기 인덱스를 두면 매달 다시 만들거나 버려야 합니다.
- 범위는 고르지 않습니다. Docs, Slides, Tasks는 REST와 거의 동등하지만 Drive는 이동, 이름 변경, 공유, 휴지통이 빠져 있습니다. 반면 Anthropic의 Google Workspace 커넥터는 메일 전송과 Drive 파일 이동을 광고하고 있어, 큰 AI 업체의 에이전트는 승인된 경로로 하는 일을 독립 개발자의 에이전트는 같은 OAuth 권한으로도 못 하게 됩니다. 파트너 자격 기준과 일반 공개 시점은 Google이 밝히지 않았습니다.
- 한도는 프로젝트당, 제품당 하루 5,000 MCP 요청이고 Gmail의 `search_threads`나 `list_drafts`는 10으로 계산되어 검색만 하면 하루 500번입니다. 2027년 4월 1일부터 유료 Scaled 티어가 시작되는데 MCP는 첫 요청부터 과금, REST는 큰 무료 한도(Gmail 경량 요청 하루 7천만 건)가 있어 REST에 유리한 구조입니다. 단가는 공개되지 않았습니다.
- Google의 논리는 "유효한 토큰이 곧 사용자 의도"라는 OAuth의 가정이 기계 속도의 에이전트에는 맞지 않는다는 것입니다. 메일이 "송장 열 건을 이 주소로 전달하라"고 쓰는 프롬프트 인젝션이 있는데, `gmail.modify` 토큰이 있으면 에이전트가 실행할 수 있습니다. 한 게이트웨이를 거치게 하면 관리자가 행동 범주를 차단하고, 승인을 요구하고, 감사할 수 있습니다. 글쓴이는 같은 설계가 어떤 에이전트가 무엇을 하고 어떤 데이터를 얼마나 보관하고 Google 제품과 경쟁할 수 있는지를 Google이 통제하게 해 준다고 지적합니다.

에이전트에 외부 서비스 권한을 어떻게 줄 것인가는 에이전트 보안과 도구 설계의 핵심 문제이고, 플랫폼이 "AI인가"를 기준으로 접근 경로를 가르는 첫 사례로 읽을 만합니다. 약관 해석과 일부 판단(취미용 스크립트가 에이전트에 해당하는지 등)은 글쓴이의 해석이며 Google의 공식 답이 없는 부분이 많고, 블로그 성격상 제품 비교 사이트의 글이라는 점을 감안해야 합니다.
