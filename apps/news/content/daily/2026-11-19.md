### SPA 소프트 내비게이션을 세면 코어 웹 지표 통과율이 4%p 오르지만 사이트가 빨라진 것은 아닙니다

`Harry Roberts` [원문](https://csswizardry.com/2026/11/web-perf-wednesday-018-soft-navigations-lift-the-crux-pass-rate/)

사이트는 하나도 빨라지지 않았는데 세 가지 핵심 지표를 모두 통과하는 오리진의 비율이 56.3%에서 60.3%로 오릅니다.

- 2026년 10월 CrUX(Chrome 사용자 실측 데이터) 데이터셋은 1,807만 개 오리진을 담고 있습니다. 현재 방식에서는 LCP 양호가 68.8%, CLS 양호가 81.6%, INP 양호가 85.2%이고 셋 모두 통과가 56.3%입니다. SPA의 소프트 내비게이션(페이지 새로고침 없이 클라이언트에서 경로만 바꾸는 이동)을 포함한 실험 지표로 보면 각각 73.6%, 85.0%, 87.0%, 60.3%가 됩니다. 통과율은 4%p, 상대값으로 7.1% 오릅니다.
- 저자는 이 상승이 SPA 사이트가 빨라졌다는 뜻이 아니라고 말합니다. 첫 로드 이후의 화면 전환은 이미 받아 둔 리소스와 애플리케이션 상태를 재사용하므로 빠르게 나오는 경향이 있습니다. 게다가 CLS와 INP는 세션 전체에 누적되지 않고 인식된 내비게이션 단위로 따로 평가됩니다. 같은 지표 이름이어도 모집단이 달라지는 것입니다.
- 이번 릴리스에서 CrUX API에 `experimental_first_contentful_paint_with_softnavs`와 `experimental_navigation_types_with_softnavs`가 추가되었고 CrUX Vis에도 같은 보기가 생겼습니다. 내비게이션 유형 비율을 보면 소프트 내비게이션이 모집단에서 얼마나 차지하는지 가늠할 수 있습니다. BigQuery에는 다음 월간 릴리스에 들어옵니다.
- Google은 이 실험 지표를 2027년 5월에 정식 전환하는 것을 목표로 하며(피드백에 따라 바뀔 수 있음), 그 뒤에 Search Console이 이를 쓸 것으로 예상됩니다. 지금은 기존 시리즈가 공식 코어 웹 지표입니다. 저자의 권고는 같은 URL과 폼 팩터에서 두 시리즈를 모두 뽑아 차이의 크기와 방향을 기록하고, 차이를 만드는 경로를 찾고, RUM 제공자가 같은 내비게이션을 인식하는지 확인하라는 것입니다.

5월에 숫자가 움직였을 때 사이트가 바뀐 것인지 측정이 바뀐 것인지 구분하려면 지금부터 두 시리즈를 같이 기록해 두어야 합니다. 웹 성능 실측을 다루는 독자에게 바로 닿는 글입니다. 다만 저자가 컨설팅을 제공하는 사람이라 글 끝이 서비스 안내로 이어지고, 수치는 모두 CrUX 공개 데이터 기준입니다.

- "인간 코드 리뷰는 죽었다"는 말은 사람이 검토하지 않겠다는 뜻이 아닙니다. 개별 PR 대신 계획과 최종 결과물, 곧 여러 PR을 묶은 릴리스를 리뷰합니다. 또 "리뷰 면제 목록"에 든 개발자는 리뷰 없이 프로덕션에 올릴 수 있지만, 장애를 낸 PR을 추적해 '스트라이크'가 쌓이면 동료 리뷰를 받도록 되돌립니다.

신뢰는 주되 장애를 내면 회수하는 책임 구조와, 검증 층을 에이전트에게 맡기는 설계는 AI 시대 코드 리뷰 체계를 고민하는 독자에게 참고가 됩니다. 한계도 분명합니다. 진행자 스스로 이 방식이 AI 비용을 줄이는 추세 속에서 소수 사례로 남을 것이라고 말하고, 수치는 길 본인의 자체 보고이며 팟캐스트 요약본이라 구체 검증 방법의 세부는 없습니다.

### 번들러 없이 `npm install`과 bare specifier를 쓰게 해 주는 Nudeps의 설계 선택입니다

`Lea Verou` [원문](https://lea.verou.me/blog/2026/nudeps/)

Nudeps는 내 코드는 건드리지 않고 의존성 파일만 `client_modules/`로 복사하며, 한 번 설정하면 감시 프로세스도 필요 없습니다.

- 브라우저는 `import { createApp } from "vue"` 같은 bare specifier(패키지 이름만 쓴 import)를 URL이 아니라서 해석하지 못하고, `node_modules/`는 배포용으로 만들어지지 않았습니다. 그래서 의존성을 쓰려고 번들러가 필요해지고, 번들러는 모든 파일을 처리하며 추상화 층을 만들어 소스와 배포 결과가 어긋나기도 합니다. 저자는 State of JS 2025에서 "의존성 관리"가 불편한 점 3위, "빌드 도구"가 6위였다고 인용합니다.
- 동작 원리는 기존 조각을 이은 것입니다. import map(bare specifier를 URL에 매핑하는 브라우저 기능)은 Baseline Widely Available이고, 의존성 그래프를 추적해 import map을 만드는 JSPM의 엔진을 가져다 씁니다. import map은 지금 각 페이지의 HTML에 인라인으로 넣어야 해서, 작은 스크립트가 맵을 주입하는 방식으로 외부 파일처럼 흉내 냅니다.
- `npx nudeps install`을 하면 `devDependencies`에 추가하고 `package.json`에 `dependencies`와 `prepare` 스크립트를 넣습니다. 그러면 `npm install`과 `uninstall`마다 자동으로 다시 돌고 새로 clone한 저장소도 바로 준비됩니다. 파일을 `client_modules/`에 복사하면서 `vue@3.5.45`처럼 버전을 디렉터리 이름에 넣어 중복 제거와 캐시 무효화를 세밀하게 합니다.
- 한계도 분명히 적었습니다. JSX나 TypeScript, Svelte 같은 컴파일은 하지 않고, 지금은 npm만 지원하며(pnpm, yarn은 로드맵 최상단), 번들러와의 성능 비교 벤치마크도 아직 없습니다. 작은 모듈이 많은 패키지는 번들하지 않아 초기 로드가 느릴 수 있고, Node 전용 API(`process.env` 등)에 기대는 패키지나 CJS 전용 패키지는 맞지 않을 수 있습니다. 워커는 아직 specifier를 지원하지 않고, CSS 같은 비 JS 의존성은 specifier가 아닌 실제 URL로 써야 합니다.

번들러를 빼고 의존성만 따로 다루는 "가벼운 빌드"라는 방향은 의존성 관리와 공유 라이브러리 배포를 고민하는 독자에게 생각할 거리를 줍니다. 다만 이 도구의 저자가 직접 소개하는 글이고 성능 데이터가 없으며, 실제 앱 규모의 검증은 테스터 몇 명의 사례에 그칩니다.

### Optimizely를 뚫은 공격자가 고객 사이트 178곳의 방문자에게 악성 JS를 내려보냈습니다

`Socket` [원문](https://socket.dev/blog/optimizely-supply-chain-attack)

공격받은 쪽은 BBC와 CNN, Zoom, GitLab, IKEA, HSBC 같은 회사 자신의 서버가 아니라 그들이 믿고 임베드한 A/B 테스트 서비스였습니다.

- 2026년 11월 16일 공격자가 Optimizely Web Experimentation의 계정 가입 흐름에 있던 취약점을 악용했습니다. 이 서비스는 고객이 CDN의 JS 스니펫을 사이트에 넣어 쓰는데, 스니펫에는 임의의 코드를 실행할 수 있는 "Project JavaScript" 필드가 있습니다. 공격자는 여기에 악성 코드를 넣었고, 그 코드가 Optimizely의 신뢰받는 인프라로 서빙되었습니다. 고객사의 웹사이트나 서버는 뚫릴 필요가 없었습니다.
- Report URI의 스콧 헬메가 178개 조직과 연관된 감염 스니펫 188개를 찾았습니다. Optimizely는 취약점을 패치하고 주입된 코드를 지웠으며 토큰을 폐기하고 해당 계정의 접근을 초기화했고, 관측된 스니펫은 11월 16일 23:11 UTC까지 모두 정리됐다고 Report URI가 확인했습니다.
- Socket이 분석한 `track.js`(19,513바이트, 실행하지 않고 정적 분석)에는 역순으로 base64 인코딩된 두 모듈이 `new Function()`으로 실행됩니다. 첫째는 이더리움, 트론, 비트코인 주소를 공격자 주소로 바꿔치기하는 클립보드 변조기로, copy 이벤트를 가로채고 Clipboard API의 `readText()`와 `writeText()`를 감싸며 50ms 간격과 MutationObserver로 화면을 계속 훑습니다. 둘째는 iOS 기기에서만 외부 도메인의 `boot.js` 로더를 불러옵니다.
- 이후 버전에는 카드 정보 탈취 모듈이 있었다고 보도되지만 Socket이 분석한 샘플에서는 이 모듈이 확인되지 않았습니다. 또 StepSecurity는 URL을 base64로 숨기거나 페이로드를 인라인으로 넣은 변종을 따로 문서화했습니다.

서드파티 스크립트는 사이트 자신의 코드와 같은 권한으로 돌기 때문에 공급망 위험의 한 축이 됩니다. Socket의 권고처럼 실험, 개인화 스크립트를 결제와 계정 같은 민감한 페이지까지 전 사이트에 실을 필요가 있는지 점검할 계기입니다. 다만 3분 분량의 분석 요약이고, 감염 기간과 실제 피해 규모, 26개 빌드 시점과의 관계는 글에서도 확인되지 않았다고 적습니다.

### 인터프리터에 프로그램을 부분 평가로 먹이면 컴파일된 프로그램이 나옵니다

`jimmyhmiller.com` (Lobsters 경유) [원문](https://jimmyhmiller.com/magic-of-partial-evaluation)

brainfuck 인터프리터에 프로그램을 넣고 부분 평가를 돌리면, 인터프리터가 완전히 사라지고 그 프로그램을 컴파일한 JS 함수만 남습니다.

- 부분 평가는 빌드 시점에 알 수 있는 부분만 계산하고 나머지는 남기는 일입니다. `power(process.argv[2], 5)`는 재귀 호출이 모두 펼쳐져 `argv[2] * (argv[2] * ...)` 형태만 남고, 산술 인터프리터 `calculate`에 모르는 값을 넣어도 아는 부분만 줄어들어 `Number(process.argv[2]) + 6`이 됩니다.
- brainfuck 인터프리터에 입력이 필요한 프로그램을 주고 돌리면 `process.argv[2]`를 읽어 문자 코드를 계산하는 짧은 함수가 나옵니다. 저자는 이것이 세 가지 후타무라 투영(Futamura projections) 가운데 첫째, 즉 `partial_eval(interpreter, prog) -> compiled_prog`라고 설명합니다.
- 인터프리터는 계측하기 쉽고 기능을 바꾸기도 쉬운 반면 컴파일러는 그렇지 않습니다. 또 스키마 검증기처럼 컴파일러를 직접 짜지는 않을 대상도 인터프리터 모양을 하고 있습니다. 스키마가 런타임에만 존재해서 손으로 특화 함수를 쓸 수 없을 때 부분 평가가 컴파일과 인터프리트를 둘 다 유지하는 부담을 줄이며, 객체가 복잡해지면 5배 성능이 나올 수 있다고 합니다.
- 범용 패턴 매처 `matches(pattern, text)`를 특정 패턴 하나에 특화해 `matchesAStarBStarC(text)` 같은 코드로 만드는 것처럼, 부분 평가는 범용 프로그램을 하나의 입력에 맞게 "특화"하는 과정으로 볼 수 있습니다. 이 관점이 후타무라 투영의 나머지 단계로 이어집니다.

번들러, 컴파일러, 스키마 검증기 라이브러리에서 쓰는 "빌드 시점에 아는 것을 미리 계산하는" 발상을 가장 단순한 형태로 풀어 주는 글입니다. 다만 사용자가 자신의 부분 평가기를 소개하는 글이라 실전 성능 근거는 약하고, 이 글은 투영의 둘째와 셋째 단계 설명에 이르기 전에 본문이 잘려 읽을 수 있었습니다.

## 보안과 릴리스

- [Unauthenticated remote code execution in Nginx](https://www.wiz.io/blog/nginx-http2-rce-vulnerabilities) `wiz.io` (Hacker News 경유) **보안, Critical.** HTTP/2를 켠 NGINX에서 인증 없이 원격 코드를 실행할 수 있는 CVE-2026-123007과 CVE-2026-123633이 고쳐졌습니다(둘 다 CVSS 4.0 9.2, 123007은 2015년 1.9.5부터 영향). 내가 할 일: 1.30.7 stable 또는 1.31.9 mainline으로 올리고, 당장 못 올리면 `http2 off;`로 HTTP/2를 끈 뒤 reload하고 이전 워커가 종료됐는지 확인합니다.
- [nginx2root](https://xint.io/blog/nginx2root-remote-code-execution) `xint.io` (Lobsters 경유) **보안, Critical.** Xint가 같은 릴리스에서 NGINX의 RCE 5건을 찾았고, 그중 HTTP/2 취약점을 리눅스 커널 SCTP 취약점과 엮어 Docker 컨테이너를 탈출해 호스트 root까지 얻었습니다. 내가 할 일: HTTP/2를 끄는 것으로는 5건 중 2건만 막히므로 HTTP/3와 메일 프록시, resolver 설정을 점검해 해당하면 업그레이드하고, 배포판은 버전 문자열이 아니라 전체 패키지 버전으로 백포트 여부를 확인합니다. 업그레이드 후에는 reload가 아니라 재시작이 필요합니다.
- [How Cloudflare WAF helps protect against Java4Shell (CVE-2026-114938)](https://blog.cloudflare.com/java4shell-waf-protection/) `Cloudflare` **보안, Critical.** OpenJDK 17.0.6 이상의 Base64 디코더(AVX-512 인트린식)에서 메모리가 덮어써져 원격 코드 실행으로 이어질 수 있고(CVSS 4.0 9.2), ARM64는 영향이 없습니다. 내가 할 일: 패치된 JDK로 올리고 번들 JDK를 쓰는 앱과 컨테이너 이미지는 각각 재빌드하고 재시작하며, 당장 못 하면 `-XX:-UseBASE64Intrinsics` 플래그로 시간을 법니다.
- [Speed Insights now measures soft navigations](https://vercel.com/changelog/speed-insights-now-measures-soft-navigations) `Vercel Blog` Speed Insights가 소프트 내비게이션의 LCP, FCP, INP, CLS를 기본으로 수집해 Real Experience Score에 포함합니다. 지표 구성이 바뀌므로 `@vercel/speed-insights` 2.1.0 이상에서 `softNavs: false`로 끌 수 있고, 12월 1일 이전에는 기존 Plus 프로젝트에 과금하지 않습니다.
- [MITRE Acknowledges Inaccurate Publication Timestamps in 87% of Its Recent CVE Records](https://socket.dev/blog/mitre-cve-timestamp-issues) `Socket` 최근 1년간 MITRE가 발행한 CVE의 87%가 발행 시각이 정확히 00:00:00 UTC로 찍혀 있었고, MITRE는 해당 레거시 시스템을 2027년 1분기에 퇴출하겠다고 밝혔습니다. CVE 공개 지연을 시계열로 분석하는 곳은 이 값을 그대로 믿지 않아야 합니다.
