## 오늘 하나만 본다면

### AI로 PR이 11배 늘자 병목은 코드 작성에서 리뷰로 옮겨 갔고, 한 스타트업은 사람 리뷰를 없앴다

`The Pragmatic Engineer` [원문](https://newsletter.pragmaticengineer.com/p/how-software-engineering-is-changing)

PostHog에서 한 달에 8건에서 20건이던 PR이 AI 네이티브 스타트업에서는 200건이 넘고, 대부분의 PR에는 사람이 붙인 리뷰가 없습니다.

- 필자 Neil Kakkar는 Bloomberg(직원 2만 명), PostHog(입사 때 약 10명, 지금 200명), AI 네이티브 스타트업 Tano(첫 엔지니어, 현재 약 10명)를 거쳤고, 월 PR 수를 직접 집계했습니다. Tano에서는 PostHog보다 11배, PostHog는 Bloomberg보다 2.4배 많은 PR을 냅니다. PR 수는 조작하기 쉬운 지표라는 점을 필자도 인정하고, 자신은 숫자를 부풀리지 않았다고 밝힙니다. PostHog 수치는 AI 이전 기준선이고 지금은 그쪽도 크게 늘었다는 단서도 붙어 있습니다.
- 11배가 전부 AI 덕은 아니라는 논증이 핵심입니다. 리뷰가 필수인 2026년 이전의 PostHog에 AI 도구를 혼자 들고 가는 시간 여행자를 가정하면 생산성은 1배에서 2배쯤 오를 뿐입니다. 코드를 빨리 써도 다른 사람이 리뷰해 줘야 머지되므로 병목이 작성에서 PR 승인으로 옮겨 가고, 내 PR이 늘수록 남의 리뷰 대기열만 길어지기 때문입니다.
- Tano는 이 병목을 구조로 없앴습니다. 한 사람이 디자인과 프런트엔드, 백엔드를 끝까지 소유해 서로 맞추는 소통 비용을 줄이고, 코드 리뷰는 코드베이스에 익숙해지면 선택 사항이 됩니다. 필자는 3주 만에, 사람에 따라서는 8주까지 걸린다고 합니다. 대신 Claude Code GitHub Actions로 만든 리뷰 에이전트가 모든 PR에서 CI로 돌고 대부분은 이것이 유일한 리뷰입니다. 위험한 변경에는 더 강한 에이전트를 필요할 때 따로 돌립니다.
- 이 선택의 대가도 사례로 나옵니다. 에이전트가 소수 통화 단위를 실수로 파싱해 100을 곱했는데, 바레인 디나르는 1디나르가 1,000 fulūs라서 틀립니다. 이미 통화 계산 유틸리티가 있었으므로 사람 리뷰어라면 잡았을 실수입니다. 배포 직후 리포트 숫자가 맞지 않는 것으로 발견했고 한 시간 안에 앞으로 고치는 방식(forward fix)으로 수정했습니다. 팀은 이 정도의 사고를 감수하고 속도를 택했다고 밝힙니다.
- 새로 생긴 제약으로는 여러 작업을 오가며 생기는 컨텍스트 전환(thrashing), 팀이 공유하던 맥락의 상실, 페이스 조절의 어려움, 설계에 쓰는 시간 감소, AI 플랜 사용 한도를 꼽습니다. 에이전트 하나가 기능 하나를 끝까지 만드는 데 1시간에서 2시간이 걸려서 필자는 3개에서 5개를 동시에 돌립니다. 에이전트가 PR마다 만들어 주는 HTML 요약으로 결과를 훑어봅니다.

AI 시대의 코드 리뷰와 검증 체계를 고민하는 독자에게 수치와 실패 사례가 같이 나오는 드문 1인칭 기록입니다. 다만 필자 한 명의 경험이고, 직원 10명 규모의 스타트업이라 14명 팀이나 금융 서비스에 그대로 옮기기는 어렵습니다. 글의 후반부(Postgres 테이블이 커진 사고 등)는 제가 읽은 본문에서 잘려 있어 다루지 않았습니다.

### 논문이 말하는 "가중치만 보고"는 10개 실험 중 3개에서만 성립한다

`honnibal.dev` (Matthew Honnibal, Hacker News 경유) [원문](https://honnibal.dev/blog/astra-read-write-misleading)

Qwen의 수학 점수를 7.9%에서 48.1%로 올렸다는 실험은 "가중치 원본만 보고" 한 일이 아닙니다. 모델을 최대 50배치 실행해 가며 파이썬 코드를 짰습니다.

- 대상은 "Astra가 가중치를 읽고 써서 Qwen을 개선했다"는 글입니다. 초록은 GPT-6 Astra가 원본 가중치만 보고 신경망이 무엇을 학습했는지 알아내고, 가중치 0.016%를 고쳐 Qwen3.5-0.8B의 MATH-500을 7.9%에서 48.1%로 올렸다고 요약합니다. 필자인 spaCy 저자 Honnibal은 무대 마술사가 같은 묘기를 매번 다른 수법으로 보여 주며 관객의 가설을 하나씩 깨는 것과 같은 구조라고 비유합니다.
- 필자가 만든 표에 따르면 실험은 10줄(7a, 7b, 8b 포함)이고, 가중치 원본을 컨텍스트에 넣고 도구도 없이 푼 것은 1번, 2번, 4번뿐입니다. 크기도 17K개에서 172K개 가중치의 작은 네트워크입니다. 실제 언어 모델이 나오는 실험은 모두 파이썬을 씁니다.
- 헤드라인인 Qwen 실험은 모델을 최대 50배치의 연습 문제에 돌려 보며 파이썬으로 분석하고 수정한 결과입니다. 필자는 이를 "프롬프트를 받은 Astra가 사람 ML 엔지니어가 하는 일을 해낸 것"이라고 평가합니다. 이것도 가볍지 않은 능력이고 한두 해 전 모델은 못 했을 일이지만, 가중치를 직접 읽는 능력의 증거는 아닙니다.
- 표에는 논문 초록에 안 나오는 실패와 단서도 있습니다. Gemma 3 270M에서 아첨하는 모델을 찾는 실험(7a)과 같은 모델로 수학을 고치는 실험(8b)은 실패했습니다. 게임 네트워크를 처음부터 쓰는 실험은 PPO 100M 스텝 네트워크를 이겼다고 하지만, 각주에 따르면 PPO 500M 스텝 기준으로는 Breakout(517 대 25)에서만 이기고 Seaquest(53 대 89)와 Asterix(53 대 55)에서는 졌습니다.
- 필자의 결론은 서로 다른 기법을 한 글에 묶어 "작은 게임 네트워크를 처음부터 쓴다"와 "큰 모델을 개선한다"가 한 기법의 능력인 것처럼 보이게 했다는 것입니다. 한 기법이었다면 깊은 능력을 시사했겠지만 사실이 아닙니다.

LLM이 할 수 있는 일과 도구를 쥐여 줘야 할 수 있는 일을 구분하는 법을 보여 주는 글이고, 벤치마크 요약을 읽을 때 조건란을 확인하게 만듭니다. 다만 반박문이어서 원 논문의 모든 실험을 재검증한 것은 아니고, 표의 분류는 필자 한 명의 해석입니다.

### 에이전트 비용을 줄이려면 출력 토큰 상한이 아니라 thinking 수준을 직접 조절해야 한다

`Google Developers` [원문](https://developers.googleblog.com/cost-per-task-using-cheap-classifiers-to-route-across-gemini-models-and-thinking-levels/)

`maxOutputTokens`를 300으로 낮춰도 쉬운 작업에서 쓰는 thinking 토큰은 거의 줄지 않았고, 어려운 작업 25개 중 7개만 깨졌습니다.

- 출발점은 토큰 단가는 계속 떨어지는데 코딩 에이전트 청구서는 오른다는 관찰입니다. 그래서 단가 대신 성공한 작업당 비용을 지표로 삼습니다. 반복, 도구 호출, 재시도, 내부 추론을 모두 더한 지출을 검증을 통과한 작업 수로 나눈 값입니다. 미세한 판단마다 추론을 오래 하는 설정을 쓰면 가벼운 설정으로도 맞힐 질문에 비싼 값을 내게 됩니다.
- 라우팅에는 TypeSafe의 Jev라는 분류기를 썼습니다. 텍스트를 생성하지 않고 한 번의 순전파로 선택지 고르기, 점수, 참 거짓 확률(Noul)을 돌려주는 모델입니다. "단순한가 복잡한가"를 한 번에 묻자 거의 전부 단순으로 분류했고, "순차 계산이 두 단계 이상 필요한가"처럼 원자적인 질문 하나로 쪼개자 분리가 됐습니다.
- 정규식과 프롬프트 길이 휴리스틱은 만든 데이터에서 93.8%(16개 중 15개)였지만, 코드를 고치지 않고 처음 보는 34개에 돌리자 70.6%로 23.2%p 떨어졌습니다. 쿠버네티스 YAML에서 포트를 뽑는 쉬운 작업은 35단어가 넘어 비싼 쪽으로 보냈고, 짧은 다단계 추적은 키워드가 없어 싼 쪽으로 보냈습니다. Jev는 같은 34개에서 모두 맞췄습니다.
- 가장 강한 라우터 없는 기준선은 Gemini 3.8 Flash의 thinking을 low로 둔 설정이었고 50개를 전부 풀었습니다. Flash-Lite로 먼저 보내고 Jev가 복잡하다고 한 것만 올리는 라우터도 50개를 전부 풀었지만, 짧은 프롬프트라 비용 차이는 작고 이점은 대기 시간 쪽이 큽니다. 처음 보는 사람에게는 라우터를 만들기 전에 `thinkingLevel: "LOW"`부터 시도하라는 권고입니다.
- 라우팅은 캐싱과 충돌합니다. 저장소 지도와 도구 정의 같은 큰 컨텍스트를 매 턴 보내는 에이전트는 컨텍스트 캐싱으로 재전송 비용을 75%에서 90% 줄이는데, 캐시는 모델 하나에 속하므로 턴마다 모델을 바꾸면 캐시가 둘이 되거나 할인이 사라집니다. 짧고 독립적인 작업만 라우팅하고 긴 컨텍스트 작업은 한 모델에 두라고 합니다. Pro 설정이 짧은 코드 보안 리뷰 프롬프트 2건을 거부했고 Flash는 답했다는 관찰도 있습니다.

토큰 경제를 설계할 때 어떤 손잡이가 실제로 효과가 있고 어떤 것은 없는지(출력 상한은 천장일 뿐 다이얼이 아닙니다) 수치로 보여 줍니다. 한계는 분명합니다. 설정당 1회 실행, 난이도를 사람이 붙인 50개 프롬프트, 단순한 자동 채점이고, 특정 분류기 제품 사례를 Google 블로그가 실었습니다(글은 제휴가 없고 보증이 아니라고 밝힙니다).

### Postman이 코딩 에이전트 설정을 조용히 바꾸고 자기 훅을 스스로 승인하려 했다는 보고

`github.com` (Hacker News 경유) [원문](https://github.com/postmanlabs/postman-app-support/issues/14370)

API 클라이언트 앱을 켰을 뿐인데 Codex와 Claude Code에 플러그인이 설치됐고, 설치 프로그램은 자기 훅을 신뢰 목록에 올리는 코드까지 갖고 있었습니다.

- 보고자는 맥에서 오래 안 쓰던 Postman 데스크톱(12.33.4)을 열었더니 Codex가 계속 MCP(에이전트가 외부 도구에 붙는 규약) 인증 경고를 내고 API 작업마다 Postman 스킬을 불러왔다고 합니다. Postman의 `main.log`에는 `source: auto-existing-upgrade`, 결과 `claude-code:installed, codex:installed`가 남아 있었습니다.
- Codex의 전역 설정 `~/.codex/config.toml`에는 Postman 마켓플레이스와 플러그인이 켜진 항목, 세션 시작 훅의 `trusted_hash`가 추가됐습니다. 훅은 세션 시작마다 "API를 설계, 구현, 모킹, 테스트, 문서화하는 사소하지 않은 작업 전에 `postman:api-engineer` 스킬을 불러오라"는 지침을 컨텍스트에 넣습니다. 사용자가 Postman을 쓰겠다고 한 경우보다 훨씬 넓은 범위입니다.
- 공개된 플러그인 소스의 `installer/src/hosts/codex-hooks.ts`는 훅 해시를 조회해 설정에 `trusted_hash`로 써 넣는 `approvePostmanHook`을 호출합니다. 사용자가 에이전트에서 직접 훅을 승인하는 절차를 설치 프로그램이 대신하려 한 셈입니다. 원격 MCP(`mcp.postman.com`)는 인증이 없어 "Auth required"로 매번 시작에 실패했고, Claude Code에도 플러그인이 켜졌으며 `~/.local/bin`에 Postman CLI가 설치됐습니다.
- 보고자가 쓴 단서가 중요합니다. 이 이슈는 원치 않은 통합과 지침 변경을 입증할 뿐 데이터 유출을 주장하지 않고, 신뢰 기록을 누가 만들었는지는 증명하지 못한다고 명시합니다. 깨끗한 맥에서 재현하지도 않았습니다. 제목의 "모든 API 데이터를 공유하려 한다"는 본문 증거보다 센 표현입니다. 요구 사항은 자동 설치 중단, 훅 자기 승인 제거, 롤백 경로 제공입니다.

에이전트의 설정 파일과 훅이 새로운 공급망 표면이라는 점을 보여 주는 사례여서, 팀 개발 환경에서 에이전트 권한을 어떻게 관리할지 생각하게 합니다. 한계는 맥 한 대의 한 사람 보고이고 Postman의 응답이 본문에 없다는 것입니다. Hacker News 996점이라는 반응은 관심의 크기이지 사실 검증은 아닙니다.

### GitHub Actions 공급망 공격은 악성 패키지가 아니라 정상 프로젝트의 릴리스 파이프라인으로 들어온다

`Socket` [원문](https://socket.dev/blog/hardening-github-actions-against-outside-threats)

tj-actions/changed-files가 뚫렸을 때 SHA로 고정한 저장소는 모두 안전했고, 태그로 고정한 약 2만 3천 개 저장소는 다음 빌드에서 공격자 코드를 실행했습니다.

- 필자 Karlo Zanki는 2025년과 2026년의 대형 사고가 타이포스쿼팅(비슷한 이름의 가짜 패키지)이나 새 악성 패키지로 오지 않았다고 말합니다. 메인테이너가 악성 코드를 쓰지 않았는데도, 정상 패키지의 릴리스 과정에서 코드가 들어갔고 대개 그 릴리스가 GitHub Actions에서 돌았습니다. 어떤 사고는 프로젝트 자동화가 직접 악성 산출물을 빌드했고, Nx처럼 자동화에서 발행 자격증명을 훔쳐 직접 발행한 사고도 있습니다.
- 버전 태그는 npm 버전처럼 불변이 아니라 옮길 수 있는 포인터입니다. 2025년 3월 공격자는 tj-actions/changed-files의 v1부터 v45.0.7까지 태그를 악성 커밋 하나로 다시 가리키게 했고(CVE-2025-30066), 페이로드가 러너 프로세스 메모리의 자격증명을 빌드 로그에 찍었습니다. 공개 저장소의 로그는 누구나 읽습니다. 2026년 3월 TeamPCP 캠페인은 trivy-action의 76개 태그 중 75개를 강제 푸시했습니다.
- 대안으로 `gh actions-lock`이 만드는 워크플로 락파일이 있습니다. 전이 의존 액션까지 커밋을 기록하고 실행 때 그 커밋이 원 저장소의 지정한 브랜치나 태그에서 도달 가능한지, 저장소 ID가 같은지 다시 검사합니다. 한계도 같이 적혀 있습니다. 재사용 워크플로 호출, 로컬 `./` 액션, 컨테이너 이미지, 입력과 시크릿은 대상이 아니고 GitHub Enterprise Server에서는 아직 지원하지 않으며, 락파일은 커밋을 고정할 뿐 검증은 해 주지 않습니다.
- SHA 고정에도 구멍이 있습니다. 포크 네트워크는 커밋 객체를 공유하므로 포크에만 있는 커밋(impostor commit)이 `actions/checkout@<sha>`로 실행될 수 있습니다. 또 SHA는 복합 액션의 `action.yml` 안에서 호출하는 하위 액션을 고정하지 못해 오늘 `actions/setup-node@v4`가 가리키는 것이 그대로 실행됩니다. 고정은 배포 직후 업데이트까지의 공백도 못 막으므로, Wiz는 7일에서 14일의 지연이 공급망 공격의 80%에서 90%를 거를 거라고 추정합니다. Renovate는 `minimumReleaseAge`, Dependabot은 `cooldown`(github.com에서는 3일이 기본)이 있고 둘 다 보안 업데이트에는 적용되지 않습니다.
- 2023년 2월 이전에 만든 조직은 `GITHUB_TOKEN`이 기본으로 읽기와 쓰기 권한을 갖습니다. 워크플로에 한 군데만 주입이 되어도 기본 브랜치에 푸시할 수 있다는 뜻이므로, `permissions` 키를 아예 생략하지 말고 기본을 없음으로 두라고 합니다.

npm 공급망과 CI 운영을 깊게 다뤄 온 독자라면 쿨다운, 고정, 최소 권한이 왜 한 묶음인지 사고 사례로 정리해 볼 수 있습니다. 제가 읽은 본문은 24분짜리 글의 앞부분(챕터 2 초반)까지이고 나머지 챕터(`pull_request_target`, 표현식 주입, 캐시, 자체 호스팅 러너 등)는 목차로만 확인했습니다. 보안 업체 블로그라는 점과 내부자 위협은 2부에서 다룬다는 점도 알아 두세요.

### Composer가 쿨다운을 넣으면서 보안 수정조차 자동으로 예외로 두지 않은 이유

`Socket` [원문](https://socket.dev/blog/composer-dependency-cooldowns)

쿨다운을 우회하는 가장 쉬운 방법은 발행 날짜를 거짓으로 적는 것이었습니다. Composer가 이 기능을 내는 데 1년 가까이 걸린 이유입니다.

- Composer 2.11은 `config.policy.cooldown`으로 새로 발행된 패키지 버전을 시간, 일, 주 단위로 기다린 뒤에야 설치 후보로 삼습니다. 기본은 꺼져 있고 `composer update`와 `composer require`의 의존성 해석에 적용되며 이미 있는 락파일 설치는 영향을 받지 않습니다. Private Packagist를 쓰면 조직 전체에 강제할 수 있습니다.
- 기능 요청은 2025년 11월에 열렸고 12월에 초기 구현이 나왔지만 2.10에는 못 들어갔습니다. 메타데이터를 믿을 수 없었기 때문입니다. 기존 `time` 필드는 Git 커밋 날짜나 `composer.json`에서 오므로 둘 다 발행자가 조작할 수 있고, 공격자가 악성 릴리스의 날짜를 과거로 돌려 쿨다운을 통과할 수 있습니다.
- 해법은 Packagist가 6월에 추가한 `published-time` 필드(레지스트리에 버전이 처음 올라온 시각)입니다. 2.11은 발행자가 준 날짜 대신 이것을 씁니다. 이 메타데이터가 없는 저장소에서는 명시적으로 폴백을 설정하지 않으면 의존성 해석이 실패합니다.
- 보안 수정을 자동 면제하지 않는 것도 의도입니다. 면제를 두면 공격자가 어드바이저리를 직접 만들거나 기존 취약점을 이용해 악성 릴리스를 쿨다운 밖으로 빼낼 수 있다고 메인테이너가 판단했습니다. 급한 수정은 `--no-cooldown`으로 그 설치만 우회하고, 믿는 패키지는 `ignore`로 영구 예외를 줄 수 있습니다.
- 다른 생태계와의 비교도 담겨 있습니다. pnpm은 2025년 9월 최소 릴리스 나이를 도입해 11 버전에서 24시간을 기본으로 했고, Yarn은 기본으로 켰으며 npm과 Bun은 설정으로 제공합니다. Dependabot 버전 업데이트는 7월부터 3일이 기본이고, Bundler는 6월에, Cargo는 Rust 1.100(11월 12일)에서 안정화될 예정입니다. 이 중 Composer만 기본을 꺼 둔 것은 기존 워크플로를 깨뜨릴 우려를 논의한 결과입니다.

pnpm과 npm 쿨다운을 이미 쓰는 독자에게는 설정 자체보다 "발행 시각을 누가 증명하는가"라는 설계 쟁점이 참고가 됩니다. 쿨다운이 설정 한 줄이 아니라 레지스트리 메타데이터 신뢰 문제라는 점이 드러납니다. 보안 업체 Socket의 뉴스 기사 성격이며 PHP 생태계 이야기라서 직접 적용할 곳은 제한적입니다.

### CSS에서 `:nth-child(An + B)`를 변수로 다시 만들면 `A`와 `B`를 실시간으로 바꿀 수 있다

`CSS-Tricks` [원문](https://css-tricks.com/re-implementing-nth-child-with-modern-css/)

`:nth-child(5n + 8)`의 5와 8은 CSS 변수로 바꿀 수 없지만, `if()`와 `sibling-index()`로 같은 선택을 다시 구현하면 바꿀 수 있습니다.

- 가장 단순한 `:nth-child(B)`는 `background: if(style(sibling-index() = --B): red; else: lightblue)`가 됩니다. 요소의 순서 번호를 돌려주는 `sibling-index()`를 `style()` 조건에 넣고, 조건이 참이면 값을 고르는 `if()`가 그 결과를 속성 값으로 바꿉니다. 같은 조건을 `var(--B)`나 `--B = sibling-index()`로 써도 동작합니다.
- `n + B`와 `-n + B`는 비교 연산자만 `>=`와 `<=`로 바꾸면 되고, 두 개를 합친 범위 선택은 `if(style(--X <= sibling-index() <= --Y): red)`로 한 줄입니다. 필자는 이 쪽이 `:nth-child()` 표기법보다 해독하기 쉽다고 봅니다.
- `An`은 `mod(sibling-index(), var(--A)) = 0`으로 배수를 판별합니다. 함정이 있습니다. A가 음수면 선택이 없어야 하는데 `mod()`가 음수에서도 0을 반환할 수 있어 일부 요소가 선택됩니다. `and (var(--A) > 0)` 조건을 하나 더해 막습니다.
- 일반형 `An + B`는 `n = (index - B) / A`가 0 이상의 정수여야 한다는 정의를 그대로 옮깁니다. 정수 조건은 `mod(index - B, A) = 0`, 0 이상 조건은 나눈 값이 `>= 0`입니다. A가 0이면 `mod()`의 둘째 인자가 0이라 NaN이 나오므로 필자는 선택 여부를 1과 0으로 담는 변수 `--g`를 따로 두는 방법을 쓰고, 어떻게 동작하는지는 독자에게 숙제로 남깁니다.
- 필자는 속성마다 `if()`를 반복해야 해서 코드가 중복되는 것이 이 방식의 단점이라고 인정하고, 실무에서 동적 `:nth-child()`가 필요할 일은 거의 없을 것이라고 말합니다. 목표는 `sibling-index()`와 `if()` 두 가지 새 기능을 익히는 것입니다. `:nth-last-child()`는 `sibling-count()`로 해 보라는 과제로 끝납니다.

CSS가 조건문과 산술을 갖게 되면서 선택자가 하던 일을 값 계산으로 옮길 수 있다는 감각을 줍니다. 디자인 시스템을 만드는 사람에게는 상태를 CSS 변수로 제어하는 패턴의 연장선입니다. 글에는 브라우저 지원 현황이 없어 실제 도입 전에 별도로 확인해야 하고, 성능 비교도 없는 개념 실험입니다.
