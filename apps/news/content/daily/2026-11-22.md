## 오늘 하나만 본다면

### LLM은 디스어셈블러 없이 hex 덤프만 보고 실행 파일을 읽고 고치고 새로 써 낸다

`sgiannopoulos.github.io` (Hacker News 경유) [원문](https://sgiannopoulos.github.io/blog/machine-code-programming/)

컴파일러, 어셈블러, 디스어셈블러 없이 바이트만 넘겼는데, 모델이 심볼을 지운 FreeBSD 바이너리에서 원본 소스에도 있던 실제 버그를 찾아냈습니다.

- 저자들은 이를 "Machine Code Programming"이라 부릅니다. LLM이 실행 파일의 바이트만 보고 추론하고, 그 사이에 컴파일러, 어셈블러, 디스어셈블러, 실행이 끼지 않는 설정입니다. 직접 짠 프로그램 세 개와 FreeBSD의 통계 도구 ministat 하나, 총 네 개의 hex 덤프를 주고 무슨 프로그램인지 물었더니 모두 맞혔습니다.
- 가장 어려운 ministat은 musl로 정적 링크하고 -O3로 빌드한 뒤 심볼과 자체 텍스트를 지우고, 마지막 문자열 셋은 각 바이트의 최상위 비트를 세워 가렸습니다. 모델은 디코딩 루프를 찾아 옵션 목록을 복원했고 여덟 개 옵션을 모두 설명했습니다. 테이블을 64비트 부동소수점으로 읽어, 99.5% 신뢰수준이라고 적힌 옵션이 실제로는 약 99.8%의 임계값을 쓴다는 버그도 짚었고, 저자들은 원본 소스에서 이를 확인했다고 합니다.
- 프로그램마다 기능 하나를 추가해 달라고 요청하면 모델은 원래 바이트와 같은 길이의 바이트 수정 목록으로 답했습니다. 사람이 바이너리를 패치하듯 빈 패딩을 찾아 세그먼트 헤더를 고쳐 실행 가능하게 만들고, 거기에 새 코드를 쓰고, 기존 명령어를 그쪽으로 가는 call로 덮어썼습니다. 숨겨진 테스트 세 가지(기존 동작, 새 기능, 긴 입력)를 세 프로그램 모두 통과했고, 기능 확장은 처음부터 쓰는 것보다 출력 토큰이 1.8배에서 3.7배 적게 들었습니다. 명세만 주고 헤더까지 포함한 ELF64 파일 전체를 쓰게 한 실험도 세 파일 모두 기준 구현과 모든 케이스에서 일치했습니다.
- 악성코드 샘플 실험에서는 4,608바이트 PE32+ 파일을 힌트 없이 주었습니다. 눈에 보이는 import는 Sleep 하나뿐이고 나머지 API는 이름 해시 뒤에 숨어 있으며 문자열은 스택에서 조립됩니다. 모델은 211초 만에 "기계어를 내려받아 메모리에서 실행한다"고 결론 내렸고 하드코딩된 서버 165.154.205.34의 443 포트를 짚었습니다. 같은 파일에 대한 공개 VMRay 동적 분석과 비교하니 같은 주소와 같은 URL이었습니다. 다만 이 비교는 실행 후에 했고, 샘플 하나와 실행 한 번이며, 재시도 간격과 XOR 키는 샌드박스로 확인되지 않았습니다. rotate-right-13 해싱은 공개 도구에도 흔해서 모델이 알아본 덕일 가능성도 저자들이 인정합니다.
- 한계는 컨텍스트입니다. hex 덤프는 바이트당 약 2.4 토큰이라 67KB 바이너리가 약 163,000 토큰이었고, 10MB 프로그램이면 약 2,400만 토큰이 필요합니다. 가장 큰 테스트가 67KB여서 그 한계 근처에서 품질이 어떻게 되는지는 모릅니다. 가중치가 공개된 DeepSeek V4.1 Flash로 같은 샘플을 돌린 예비 실험도 있는데, 같은 결론에 도달하되 추론 토큰이 약 17배 들었고 함수 이름 13개 중 9개를 맞혔습니다.

LLM에게 "읽기 쉬운 중간 표현"이 꼭 필요한지를 묻는 글이어서, 에이전트가 빌드 산출물이나 번들을 직접 들여다보는 시대에 검증 체계를 어떻게 세울지 생각할 때 닿습니다. 다만 작은 프로그램 몇 개와 샘플 하나에 근거한 초기 결과이고, 저자들도 선행 연구 조사가 완전하지 않다고 밝힙니다.

## 읽을 만한 것

### 완전 정적 사이트 대신 "서버에서 렌더링하고 30일 캐시, 쓰기 때마다 전부 무효화"를 택한 이유

`klauria.tech` (Hacker News 경유) [원문](https://klauria.tech/klauria-art/)

글쓴이는 캐시 무효화를 정교하게 하는 최적화를 알면서도 일부러 포기했습니다. 의존 관계가 코드 어디에도 적혀 있지 않아 틀리기 쉽기 때문입니다.

- 출발점은 그림 수백 점을 지도 위 마커로 보여 주는 개인 사이트입니다. 하루 평균 0.3점 미만, 많아야 4점이 올라오니 내용이 거의 바뀌지 않아 정적 사이트가 맞다고 봤습니다. 그런데 태그와 위치를 편집하려면 웹 UI가 필요하고, 웹 UI가 내용을 바꾸면 더는 정적 사이트가 아니라는 모순이 생깁니다. 목표는 "다른 사람에게는 정적이고 나에게만 동적인" 사이트였습니다.
- 해법의 핵심은 모든 HTML을 서버(Cloudflare Worker)에서 렌더링하되 Cloudflare CDN이 30일간 캐시하도록 헤더를 주는 것입니다. 작품을 올리거나 태그를 바꾸는 쓰기 요청의 핸들러가 캐시된 페이지를 전부 무효화합니다. 정적 파일에 가까운 속도와 비용으로 CRUD UI를 쓰는 구조이고, 인도에 있는 부모님이 접속해도 가까운 엣지에 캐시된 결과가 나갑니다.
- 이미지는 업로드할 때 작은 크기 세 가지를 업로더의 브라우저에서 미리 만들어 원본과 함께 Cloudflare R2에 올립니다. 쓰는 크기를 이미 알고, 업로더가 본인 하나뿐이라서 요청 시점에 리사이즈해 주는 이미지 서비스를 쓰지 않습니다. 원본이 훨씬 커서 축소본이 늘려 놓는 저장 용량은 크지 않다고 합니다. 모든 작품의 메타데이터는 R2의 JSON 파일 하나에 두고, 지도와 타임라인 같은 클라이언트 컴포넌트도 이 JSON만 읽어 초기화하므로 데이터베이스가 없습니다.
- 전부 무효화하는 이유가 가장 흥미롭습니다. 새 작품이 `#evening` 태그 페이지만 바꾼다는 걸 알아도, 페이지 생성 코드는 그냥 실행될 뿐 의존성이 명시돼 있지 않아 메타데이터 어느 부분이든 어느 페이지의 출력이든 바꿀 수 있습니다. 의존성을 손으로 적으면 미래에 틀려서 일부만 갱신된 사이트, 즉 정합성 버그가 생기기 쉽다고 봤습니다. 일반적인 정적 사이트 생성기라면 CDN이 산출물 해시가 같을 때 갱신을 건너뛰는 최적화를 할 수 있다고도 덧붙입니다.

프레임워크의 증분 재검증(ISR 같은 것)이 풀려는 문제를 개인 규모에서 가장 단순한 형태로 풀어 본 사례라, "정확한 무효화 대신 전부 무효화"가 언제 합리적인지 가늠하는 기준이 됩니다. 트래픽이 거의 없는 개인 사이트이고 성능 수치를 제시하지 않으므로, 규모가 있는 서비스에 그대로 옮길 수는 없습니다.

## 보안과 릴리스

- [RCE in Gnupg](https://lists.gnupg.org/pipermail/gnupg-announce/2026q4/000517.html) `lists.gnupg.org` (Werner Koch, Hacker News 경유) **보안, Critical.** 아주 긴 user id를 가진 OpenPGP 키로 GPGME의 이중 해제(double free)를 일으킬 수 있고, 서명된 데이터를 보내 애플리케이션의 데이터를 빼내거나 RCE까지 갈 수 있다고 원문이 밝힙니다(CVE-2026-129975). 내가 할 일: GPGME를 쓰는 메일 클라이언트와 Samba, Flatpak 같은 의존 소프트웨어를 2.3.1 이상으로 올리고, 정적 링크한 바이너리는 2.3.1로 다시 빌드합니다.
- [Upload2Shell (CVE-2026-125396)](https://pwn.ai/upload2shell) `pwn.ai` (Hacker News 경유) **보안.** Ghostscript의 Type 1 폰트 로더 use-after-free로 `-dSAFER` 샌드박스를 벗어나 렌더링 프로세스 권한으로 명령을 실행할 수 있고, ImageMagick을 거치면 `.png`나 `.jpg` 이름의 파일도 Ghostscript에 닿습니다. 원문은 등급을 밝히지 않았고, WordPress 코어(CVE-2026-65640), Roundcube 등 업로드와 미리보기 경로의 영향을 보고합니다. 내가 할 일: 업로드 이미지를 ImageMagick이나 Pillow로 처리하는 서비스가 있다면 Ghostscript를 10.08.0 이상으로 올리거나 배포판의 수정 패키지(Debian 13은 10.05.1~dfsg-1+deb13u3)를 적용하고, 처리 가능한 이미지 형식을 제한합니다.
