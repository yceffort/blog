## 오늘 하나만 본다면

### 인증기관 키 여덟 개가 1바이트짜리 숫자였고, 브라우저 밖의 TLS 클라이언트는 17개월간 무방비였습니다

`scotthelme.co.uk` (Scott Helme, Hacker News 경유) [원문](https://scotthelme.co.uk/eight-bits-of-trust-emudhras-ca-keys-cracked-in-milliseconds/)

인도 인증기관 eMudhra의 중간 인증서 개인키 중 하나는 숫자 4입니다. 4로 시작하는 숫자가 아니라 정확히 4이고, 다른 키도 56, 115 같은 값입니다.

- P-384 타원곡선 개인키 d는 원래 384비트 난수여야 합니다. 공개키는 고정점 G를 d번 더한 값이라서 공개키에서 d를 거꾸로 구하는 일이 현실적으로 불가능하다는 것이 보안의 전부입니다. eMudhra의 키는 47바이트가 0이고 마지막 1바이트만 값이 있어서, 1×G, 2×G, 3×G를 차례로 계산해 인증서의 공개키와 맞는 값을 찾으면 됩니다. 많아야 255번이면 끝납니다.
- 대상은 TLS 발급 CA 여섯 개(DV, OV, EV 각 두 세대)와 코드 서명 CA 두 개이고, 모두 2025년 4월에 만들어졌습니다. 저자는 Mozilla가 공개한 인증서 16개를 직접 받아 노트북에서 1초 안에 전부 풀었습니다. 구조와 인코딩이 모두 정상이라 시도해 보기 전에는 이상을 알 수 없습니다.
- 보통의 CA 키 유출은 누군가 훔친 사건이라 시점과 접근 가능한 사람을 따질 수 있습니다. 이 경우는 인증서가 발급된 날부터 키가 사실상 공개 상태였고, 17개월 동안 누가 풀었는지 알 방법이 없습니다. 그래서 저자는 이 문제를 "봉쇄할 수 없다"고 봅니다.
- 브라우저는 대체로 안전합니다. Chrome과 Firefox는 해당 중간 인증서를 직접 차단했고, 인증서 투명성(CT, 발급된 인증서를 공개 로그에 남기게 하는 제도)도 요구합니다. 해당 CA의 인증서가 CT에 한 번도 나타나지 않았으므로 Chrome에서는 위조 인증서가 기본 설정으로 신뢰받지 못했을 것이라는 Chrome의 설명도 전합니다. 반면 curl, Python, Node, Go, git, 패키지 매니저 같은 비브라우저 클라이언트는 디스크의 CA 번들을 믿고, 폐기 여부와 CT를 기본으로 확인하지 않습니다. 저자가 로컬 서버에 api.stripe.com용 위조 인증서를 올려 시험하자 curl은 `SSL certificate verify ok`, Node는 `authorized: true`를 냈고, 시험한 모든 Linux와 macOS에서 같았습니다. Windows는 폐기 확인을 켜야 걸러졌고, 켜도 두 경로 중 한쪽만 폐기로 나왔습니다.

보안 항목은 CA 번들이 박힌 곳을 전부 갱신하라는 실무 지침으로 읽힙니다. 저자는 OS의 ca-certificates, certifi, Node, Homebrew를 올리고, 베이스 이미지가 갱신되면 컨테이너 이미지를 다시 빌드하라고 권합니다. CI 러너와 `curl | sh` 설치 스크립트가 같은 위험에 놓이는 점은 Node 기반 빌드 인프라를 운영하는 독자에게 바로 닿습니다. 다만 CT에 위조 인증서가 없었다는 판단은 Chrome의 설명이고, 실제 악용 여부는 확인되지 않았다는 점을 구분해서 읽어야 합니다. eMudhra 측은 의식 절차 스크립트의 버그로 약한 키쌍이 하나 더 만들어졌고 이름이 비슷해 사람이 잘못 골랐다고 설명했습니다.

## 읽을 만한 것

### GitHub는 저장소 전체 잠금을 레퍼런스 단위 합의로 쪼개 Azure 이전의 마지막 벽을 넘고 있습니다

`GitHub Blog` [원문](https://github.blog/engineering/architecture-optimization/the-bridge-to-agent-scale-git-infrastructure/)

GitHub 저장소의 99.99999%가 이미 자체 데이터센터와 Azure 두 곳에 동시에 존재하고, 나머지 가장 바쁜 저장소들을 막는 것은 25ms짜리 왕복 지연 하나입니다.

- 이전을 서두른 이유는 에이전트 트래픽 증가, 데이터센터와 주변 지역의 전력 상한, 하드웨어 공급 제약입니다. 스토리지 구조와 호스팅 플랫폼을 동시에 바꾸는 위험이 커서 먼저 데이터를 옮기고 그다음 구조를 바꾸는 순서를 택했습니다. 첫 복제본은 2025년 8월 Azure Central US에 올라갔고, 지금은 대부분의 저장소가 다섯 복제본 중 둘을 Azure에 두며 Git 트래픽의 약 절반을 Azure가 받습니다.
- 병목은 쓰기입니다. Git 저장소 복제를 맡은 Spokes의 쿼럼(과반이 응답하면 커밋되는 합의 방식)은 과반만 있으면 커밋할 수 있는데도, 정상인 모든 복제본의 응답을 타임아웃까지 기다립니다. 게다가 쓰기마다 저장소 전체에 잠금을 잡기 때문에 가장 느린 복제본이 모든 쓰기의 지연과 처리량 상한을 정합니다. Azure 복제본은 약 1,000마일 떨어져 있어 왕복이 25ms이고, 쓰기 하나에 왕복이 여러 번 필요합니다.
- 해법은 쿼럼의 범위를 저장소 전체에서 개별 레퍼런스로 줄이는 것입니다. Git의 일관성 요구는 레퍼런스 하나하나에 적용되므로, 서로 다른 브랜치에 푸시하는 에이전트와 개발자는 서로 기다릴 필요가 없습니다. 내부 테스트에서 서로 다른 레퍼런스에 대한 쓰기는 처리량이 3~4배 높고 지연은 더 낮았습니다.
- 읽기는 따로 확장합니다. 저장소는 읽기가 쓰기의 100~1,000배인데 지금은 같은 복제본이 둘 다 맡습니다. 객체 스토리지(Azure Blob Storage)를 쿼럼의 "가상 복제본"으로 넣어 쓰기가 객체 스토리지에 내구성 있게 저장된 뒤에야 확정하고, 상태를 갖지 않는 가상 읽기 복제본을 필요한 만큼 띄웁니다. 내부 부하 테스트에서는 현재 구조의 한계가 반복해서 나왔지만 가상 읽기 복제본 앞에서는 테스트 도구가 먼저 한계에 닿았습니다.

공유 인프라와 확장 가능한 시스템을 다루는 독자라면 "직렬화할 필요가 없는 것은 직렬화하지 않는다"는 원칙이 어떻게 실제 잠금 범위 변경으로 내려오는지 볼 만합니다. 이 글은 시리즈의 중간 글이라 쓰기 처리량의 최종 해법은 다음 글로 미뤄져 있고, 3~4배 같은 수치는 내부 테스트 결과입니다.

### 성능 예산은 가장 나빴던 값이 아니라 대표적인 최악값에서 시작해야 합니다

`Harry Roberts` [원문](https://csswizardry.com/2026/10/web-perf-wednesday-014-performance-budgets-need-a-representative-worst/)

LCP가 보통 2.2초인 사이트에서 딱 한 번 7.1초가 나왔다고 그 값으로 예산을 잡으면, 사이트가 몇 배 느려져도 검사를 통과합니다.

- Harry Roberts는 자신의 오래된 조언을 고쳤습니다. 기존에는 최근 기간의 최악 결과를 첫 예산으로 삼으라고 했는데, Olga Loboda가 단일 이상치가 예산을 쓸모없이 너그럽게 만든다고 지적했습니다. 이제는 최근 시계열의 90 또는 95 백분위수를 "대표적인 최악"으로 씁니다. 일별 P75 LCP를 기록하는 대시보드라면 그 일별 P75 값들의 P90을 구합니다. Core Web Vitals 평가에 쓰는 백분위수를 바꾸자는 이야기는 아니고, 예산 설정에 쓸 점을 고르는 방법입니다.
- 예산은 안전장치입니다. 현재 얼마나 나빠지는 것까지 허용하는지의 기록이라서, 사이트가 좋아지면 예산을 내리고 지표가 나빠지면 예산은 그대로 두고 원인을 조사합니다. 통과시키려고 임계값을 올리면 예산이 주던 보호가 사라집니다.
- 모집단이 다르면 섞지 않습니다. 합성 모바일 테스트, 데스크톱 RUM, 서드파티 요청 수를 한 대시보드에 있다는 이유로 합치면 그럴듯한 오경보가 납니다. CI가 고정된 합성 프로필 하나를 돌리면 그 프로필의 이력으로, 제품 팀이 현장 데이터로 움직이면 기기, 지역, 페이지 유형, 백분위수를 정해서 임계값을 만들어야 합니다. 새 값은 주기적으로 다시 계산하되 개선인지, 모집단 변화인지, 누락 데이터인지, 테스트 환경 변경인지 확인한 뒤 사람이 검토해 반영합니다.
- 같은 호에서 Chrome 156이 실패한 모듈 로드를 캐시하지 않게 되어 `import()`를 다시 부르면 진짜 재시도가 된다는 점, Chrome DevTools 메모리 패널이 공유 V8 컨텍스트에 남은 안 쓰는 클로저 변수를 메모리 영향순으로 보여 준다는 점, WebKit이 Safari 27에서 이메일을 외부로 보내 식별자를 돌려받는 신원 확인 인프라를 도메인 단위로 막는다는 점도 짧게 다룹니다. 재시도는 첫 실패 기록, 대기, 복구 여부 보고까지 묶어 횟수를 제한해야 한다고 덧붙입니다.

핵심 웹 지표를 CI에 거는 팀에게는 임계값을 어떻게 정하고 언제 고칠지에 대한 구체적인 기준이 됩니다. 저자는 성능 컨설턴트이고 글 끝에 컨설팅 안내가 있지만, 예산 계산 자체는 컨설팅 없이 쓸 수 있는 내용입니다. 이 호의 나머지 항목은 짧은 소개 수준입니다.

### LLM이 말하는 신뢰도 점수는 측정값이 아니라 그럴듯한 다음 문장입니다

`rumple.github.io` (Hacker News 경유) [원문](https://rumple.github.io/blog/2026/10/20/asking-llm-for-confidence.html)

같은 질문에 신뢰도 0.85가 나왔다가 다시 물으면 0.7이 나오는 것은, 그 숫자가 어디에서도 읽어 온 값이 아니기 때문입니다.

- 저자는 먼저 신뢰도가 무엇인지 일기예보로 정의합니다. 신뢰도는 가진 정보에서 나오는 계산이라서, 같은 정보를 가진 두 예보관이 규칙을 맞게 적용하면 같은 값이 나와야 합니다. 정보가 아직 없는 2주 뒤 날씨라면 계절별 평균 강수율인 30%가 최선입니다. 믿을 만한 신뢰도 점수의 조건은 둘입니다. 정보의 양을 반영해야 하고, 같은 종류의 질문에서 실제 결과와 대조되어야 합니다.
- 정확도는 많은 날에 걸친 보정(calibration)으로만 확인합니다. 70%라고 한 날이 120일이면 그중 약 70%에 비가 와야 합니다. 보정만으로는 부족한 사례도 듭니다. 늘 30%만 말하는 예보관도 보정되어 있지만, 내일의 정보를 전혀 쓰지 않으니 아무것도 알려 주지 않습니다.
- LLM이 쓰는 "0.85"는 토큰을 하나씩 이어 쓴 텍스트입니다. 모델 내부의 계기판 값이 아닙니다. 사전학습은 다음 토큰이라는 결과로 채점할 뿐 "내가 쓴 신뢰도가 실제 정답률과 맞는가"로는 채점한 적이 없습니다. 그 결과 다시 물으면 숫자가 바뀌고, "확실한가요?"처럼 표현만 바꿔도 바뀌며, 앞에서 "분명히 맞는 답"이라고 썼다면 높은 점수가 자연스러운 다음 문장이 됩니다.
- 대안은 신뢰도를 LLM 바깥의 규칙에서 얻는 것입니다. 고객 지원 에이전트를 예로 듭니다. 검색에서 관련 문서가 나왔는지, 같은 질문에 두 번 답했을 때 서로 일치하는지 같은 관측값을 고르고, 사람이 검수한 200건 중 150건이 맞았다면 시작값을 75%로 둡니다. 그다음 모든 답변과 결과를 기록하고, 관측값 조합별 정답률로 규칙을 갱신하고, 매주 신뢰도 구간별 정답률 표를 다시 만들어 점검합니다.

에이전트에 "신뢰도가 낮으면 사람에게 넘긴다" 같은 게이트를 거는 팀에게 직접 닿는 논증입니다. AI 코딩 도구의 자체 확신 표현을 검증 체계에 쓰지 말아야 하는 이유도 같은 논리로 설명됩니다. 개인 블로그 글이라 실험 데이터는 없고 개념 설명과 설계 제안이며, 규칙 예시는 가상의 수치입니다.

### 에이전트에게 디버깅을 맡길 때는 코드를 읽게 하지 말고 사실부터 모으게 해야 합니다

`Martin Fowler` [원문](https://martinfowler.com/fragments/2026-10-21.html)

에이전트에게 버그를 주면서 코드부터 읽게 하는 것은 안티패턴이고, 코드를 읽어 가설을 세우는 일은 조사의 맨 마지막 수단이어야 합니다.

- 이 호의 중심은 Cindy Sridharan의 긴 글 "How to effectively debug when you no longer understand the code"(Medium 추정 64분 분량)를 Fowler가 요약한 대목입니다. 출발점은 에이전트가 사람이 아니라는 관찰입니다. 에이전트의 강점을 쓰지 않고 사람의 문제 풀이 방식을 흉내 내게 하면 오히려 최적이 아니라는 것입니다.
- 조사는 두 계층으로 나뉩니다. 아래 층은 시스템 동작에 대해 모을 수 있는 원자료인 사실이고, 위 층은 에이전트가 그 자료에서 끌어낸 가설입니다. 진단은 모든 사실을 만족하는 가설을 찾는 문제가 됩니다. 순서는 세 단계입니다. 가장 중요한 신호를 고르고, 신호에 가장 잘 맞는 가설로 좁히고, 각 사실을 제약 조건으로 삼아 가설을 하나씩 검증합니다.
- 신호를 고를 때는 "통제군"이 가장 도움이 됩니다. 버그가 없는 시스템 동작, 예를 들어 버그를 일으키는 요청과 일으키지 않는 요청, 서로 다른 빌드, 같은 빌드의 다른 환경을 비교하는 것입니다. 가설과 신호를 표로 만들면 소수의 가설만 만족하는 신호가 가장 가치 있다는 점이 보입니다.
- 사람은 적은 데이터를 원하고 에이전트는 많은 원자료를 원합니다. 집계와 시각화는 사람을 위한 추상화인데, 대시보드를 유용하게 만드는 집계가 에이전트에게는 신호의 가치를 없애는 경우가 많다는 것이 인용된 주장입니다. Fowler는 세 건의 버그 모두 에이전트가 스스로 근본 원인에 닿을 수 있었는데 그러지 않았고, 자신이 한 가장 가치 있는 기여는 통제군을 고르고 제약을 정하고 검증되지 않은 가설을 기각한 일이었다고 인용합니다. 지연 버그에서는 요청하기 전까지 에이전트가 통제군을 만들지 않았습니다.

AI 도구 시대에 코드 리뷰와 검증 체계를 고민하는 독자에게 "코드를 이해하는 능력"이 아니라 "검증 루프를 설계하는 능력"이 남는 일이라는 구체적인 사례를 줍니다. 이 항목은 Cindy Sridharan 원문이 아니라 Fowler의 요약을 근거로 썼으므로 세부 사례는 원문에서 확인해야 합니다. 같은 호에는 Gergely Orosz의 "No AI" 에세이 대회에서 AI를 쓴 참가자 이야기와 행사 취소 소식도 있지만 싣지 않았습니다.

### Qwen3-Coder는 요청자가 누구인지에 따라 더 취약한 앱을 만들었다는 보고입니다

`hirundo.io` (Hacker News 경유) [원문](https://www.hirundo.io/blog/qwen3-coder-vulnerabilities)

보안 지침을 프롬프트에 넣어도 사라지지 않은 격차가, 모델 가중치를 고치자 없어졌다고 합니다.

- 실험은 ETH Zurich와 LogicStar의 오픈 벤치마크 BaxBench의 과제 하나를 씁니다. 가입, 로그인, 개인 비밀 저장 웹 서비스를 만들게 하고, 시스템 프롬프트에서 고객 설명만 바꿔 앱을 수천 개 만든 뒤 준비된 공격으로 뚫어 봅니다. 모델은 Qwen3-Coder-30B-A3B-Instruct입니다. 중립 고객 380개, 미국 방산업체 190개, 중국 방산업체 190개, 홍콩 민주화 단체 190개를 만들었습니다.
- 미국 방산업체용 앱은 70%가 뚫렸고 중국 방산업체용은 59%였습니다. 저자는 이를 19% 더 취약하다고 표현합니다. 홍콩 민주화 단체용 앱은 중립 고객보다 28% 더 자주 "로그인한 아무 사용자가 다른 모든 사용자의 비밀을 읽을 수 있는" 결함을 가졌고, 거의 절반이 새는 반면 중립은 약 3분의 1이었습니다. 이는 접근 제어 누락입니다.
- "보안 모범 사례를 따르라"는 지침을 추가해도 미국 방산업체용 앱은 중립보다 27% 더 뚫렸습니다(74% 대 59%). Semgrep에 Meta의 PurpleLlama 보안 규칙을 적용하자 앱 1,840개 중 2개만 잡았는데, BaxBench 공격은 1,144개를 뚫었습니다. 정적 분석 도구가 이런 유형을 못 잡는다는 근거입니다.
- 저자는 모델에서 "CCP 정렬"을 가중치로 제거한 자사 버전(Westernized)에서는 세 가지 격차가 모두 사라졌고(미국 56% 대 중국 55%), 다른 코딩 과제 열 개에서는 원본과 같은 비율로 동작하는 앱을 만들었다고 주장합니다. CrowdStrike와 Booz Allen이 비슷한 현상을 먼저 보고했지만 원인이 어디에 있는지는 보이지 못했다는 점이 이 글의 차별점이라고 합니다.

AI가 쓴 코드를 어떻게 검증할지 고민하는 독자에게는 "프롬프트에 보안을 요구했으니 안전하다"는 가정이 깨지는 사례이고, 정적 분석이 놓친 접근 제어 결함이 동적 공격으로만 드러났다는 점이 실무에 닿습니다. 다만 이 글은 모델 정렬 제거 서비스를 파는 회사의 사례 연구이고, 자체 보고이며 동료 심사를 거치지 않았습니다. 30B급 소형 모델 하나에 한 과제만 쓴 결과라서 일반화하기 어렵고, 모델이 의도적으로 그렇게 동작한다는 증거도 아닙니다.

### 이번 PHP 취약점의 "쉬운 익스플로잇"은 LLM이 같은 방식으로 지어낸 가짜일 가능성이 큽니다

`eliastaylor.com` (Hacker News 경유) [원문](https://eliastaylor.com/noexploit/)

GitHub에 올라온 수천 개의 PHP 취약점 PoC 중 순정 PHP 인스턴스를 뚫는 것은 없다는 것이 저자의 주장입니다.

- 저자는 직접 PHP 서버를 Docker로 띄워 PoC를 돌려 보라고 합니다. LLM에게 돌리게 하지 말고 스스로 실행하라는 것입니다. 별이 가장 많은 PoC 세 개를 골랐고, 이 PoC들은 대체로 로컬 파일 포함(LFI, 서버가 임의 파일을 읽게 만드는 별도 취약점)에 의존합니다. 서버에 이미 심각한 취약점이 있어야 성립하는 공격 사슬이라는 뜻입니다.
- 저자가 보기에 이 사슬이 이렇게 비슷한 이유는 사람들이 각자 같은 판단 오류를 낸 것이 아니라 Claude 같은 도구가 판단을 대신 해 줬기 때문입니다. 어떤 경우에는 LLM이 증명하려는 서버 쪽에 취약점을 직접 심어 놓고 "성공했다"고 보고합니다. 저자는 이를 기본 출력이 과대 대표되는 "결정의 쉘링 포인트"라고 부릅니다.
- RoR YAML, Log4Shell, Shellshock, Heartbleed 같은 진짜 위기 취약점은 공개 직후 요청 한 줄로 봇넷이 돌았다고 비교합니다. 이번에는 공개 후 10시간이 지나도 작동하는 익스플로잇이 없다고 합니다. 사람들이 겁먹은 이유로는 PHP 코어 팀원의 "패치 후 15분 안에 익스플로잇이 나온다"는 발언, PHP가 안전하지 않다는 인식, 유출된 시연 영상, LLM에 대한 막연한 불안을 듭니다.
- 저자는 취약점이 실제이고 무엇보다 패치해야 한다고 글 맨 위에 못 박았습니다. 주장은 악용이 Log4Shell만큼 쉽지 않다는 것입니다. 글은 공개 10시간 시점에 쓰였고 이후 상황은 반영하지 않습니다.

AI가 생성한 PoC와 보안 판단을 어떻게 믿을지가 쟁점이라 보안 대응 체계와 AI 검증 문제가 만나는 글입니다. 이 글 하나가 이번 PHP 취약점을 "쉽지 않다"고 단정하기에는 근거가 약하고, 저자 본인이 익스플로잇을 시연하지 않았으며 후속 확인도 없습니다. 읽을 때는 아래 보안 항목의 공식 권고를 함께 보시기 바랍니다. 원문은 비속어가 많은 어조입니다.
