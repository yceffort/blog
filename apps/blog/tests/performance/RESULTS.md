# Tailwind → StyleX 전체 전환 성능 비교

> 이 보고서는 리팩토링 전 Full StyleX 버전의 측정 기록이다. 현재 리팩토링 결과와 크기 비교는 [스타일 리팩토링 검증](../styles/REFACTOR.md)을 참고한다. 현재 버전의 FCP·LCP는 다시 측정하지 않았다.

**이번 전체 전환은 이 환경에서 로딩 시간과 전송량을 늘렸다. 성능 개선을 이유로 적용하기는 어렵다.** 컴포넌트 스타일의 소유 위치와 작성 방식을 통일한 결과이며, 아래 수치는 이 블로그 구현과 측정 조건에 대한 것이다.

원본 `7c4fa58e`와 최종 작업 트리의 프로덕션 빌드를 새로 비교했다. 유틸리티 전환 이후 남아 있던 컴포넌트 CSS, Markdown 타이포그래피, 테마, 키프레임, About/Resume SCSS까지 StyleX로 옮기고 불필요한 Markdown 클래스 연결을 제거한 상태다. 브라우저 리셋·`@property` 등 전역 경계는 `browser.css`에 남는다.

## 조건과 재현

- Chrome for Testing `Chrome/153.0.8010.12`, macOS arm64 / Apple M5. 실제 Chrome DevTools Protocol 스로틀링을 사용했다.
- Node 24.20.0, pnpm 12.1.0, Next.js 16.3.1. Tailwind 4.3.3과 StyleX 0.19.0.
- 모바일 390 × 844, DPR 2, 터치, 라이트 모드. 애니메이션과 캔버스 정상 실행.
- CPU 20× 감속, 다운로드·업로드 400 Kbps, 최소 지연 400 ms.
- 경로 2개 × 버전 2개 × 5회 = **20회**. AB/BA 순서를 번갈아 실행했다.
- 매번 새 Chrome 프로세스·프로필. HTTP 캐시 비활성화/초기화, 서비스 워커 차단, GA/Tag Manager 차단. 서버 경로·이미지 캐시는 사전 방문으로 준비했다.
- `load`, 폰트 준비, network idle 이후 5초까지 관찰했다. 실패·캐시·예상치 못한 네트워크 오류가 있는 실행은 유효한 측정으로 처리하지 않는 코드다. 최종 20회는 모두 검사를 통과했다.
- Next.js의 정상 RSC 요청과 링크 prefetch를 포함했다. jsDelivr의 기존 KaTeX CSS도 양쪽에서 실제로 요청했다.
- 빌드·시각 검사가 종료된 뒤 측정했다. 원본은 자체 잠금 의존성을 설치한 깨끗한 별도 worktree이며, 원본 소스와 Next.js 설정을 수정하지 않았다. 양쪽 빌드/서버는 `GA4_PROPERTY_ID=''`를 사용했다.

측정: `2026-09-13T10:26:09.778Z` ~ `2026-09-13T10:36:47.216Z` (UTC).

[실행 코드](../../scripts/compare-performance.mjs), [재현 방법](README.md), [20회 데이터](results.json). 상세 리소스·스크린샷·20개 trace는 `apps/blog/.cache/performance/full-stylex/`에 있다. Document/Fetch 전송량은 저장된 CDP 리소스의 `type`별 `encodedBytes` 합계다.

## 해석

FCP 중앙값은 홈 4.80→7.64초(+59.25%), 글 5.94→8.83초(+48.52%)로 늘었다. 두 경로 모두 실행 범위가 겹치지 않았다. CSS 전송은 약 28.2→65.7 KiB로 늘었고, HTML과 RSC prefetch 응답도 커졌다. 전체 전송량은 홈 +9.43%, 글 +22.47%다. 글 페이지의 전체 전송량에는 본문 HTML뿐 아니라 다른 글·태그·시리즈의 prefetch 응답도 포함된다.

**LCP 대상이 달랐다.** 원본 홈은 썸네일 이미지, 원본 글은 제목 `h1`이 마지막 후보였다. 전환 후 두 경로는 하단 공지의 텍스트 `span`이 마지막 후보였다. 각 버전의 5회 모두 같은 대상이 관찰됐다. 표의 LCP는 각 페이지가 보고한 최종 후보를 비교한 값이다. 동일 이미지나 동일 제목의 렌더링 시간 차이로 해석할 수 없으므로 FCP·전송량과 함께 판단해야 한다.

스타일 재계산과 메인 스레드 작업 중앙값도 늘었다. 레이아웃 시간과 CLS는 일부 줄었지만, 로딩 지연과 전송량 증가를 상쇄하지 않았다. 메인 스레드 누적 시간은 각 페이지의 로드 후 관찰 종료까지의 값이므로 관찰 구간의 전체 길이와 정상 애니메이션 작업도 영향을 준다. `loadBlockingMs`는 FCP부터 관찰 종료까지 50 ms를 넘긴 long task의 초과시간 합이며 Lighthouse TBT가 아니다. INP나 실사용자 지표를 측정한 실험도 아니다.

기존 선택자·상태·반응형 결과를 유지하면서 스타일을 원자적 클래스로 옮겨, 조건부 CSS와 HTML/RSC의 클래스 표현이 커졌다. 코드 토큰과 수식에 불필요하게 붙던 간격·시리즈 메뉴 클래스는 제거했으며 화면 결과는 유지됐다. 현재 구현은 성능보다 스타일 작성 방식 통일을 선택한 결과로 판단하는 것이 맞다.

## 화면 검증과 이전 기록

- 기존 168개 스타일 그룹 × 10개 너비 × 2개 테마 × 2개 모션 설정 × 4개 상태 = **26,880개 조합 통과**.
- 13개 경로의 모바일/데스크톱·라이트/다크 및 메뉴/검색/설정 **62개 조건에서 계산 스타일, 가상 요소, 내용, 위치, 픽셀 차이 0**. 마지막 다크 모드 수정과 Markdown 클래스 정리 후에는 영향 범위를 재검사했다. [조건별 기록](../styles/page-results.json).
- 정상 모션의 홈·소개·글, 두 화면 크기·두 테마 **12개 조건에서 CSS 애니메이션 키프레임과 재생 설정 일치**. [검사 코드](../../scripts/check-page-motion-parity.mjs), [기록](../styles/motion-results.json).
- 정지 화면 검사는 애니메이션을 고정하고 캔버스 픽셀을 마스킹한다. 정상 모션 검사는 CSS 효과의 설정을 비교한다. WebGL/JavaScript 애니메이션 픽셀의 동일성을 주장하지 않는다.
- 유틸리티만 전환했던 첫 측정은 [ROUND-1.md](ROUND-1.md)와 [round-1.json](round-1.json)에 보관했다. 이번 표의 원본 수치도 새로 측정했으므로 이전 실행과 섞지 않았다.
- 전체 전환 후 첫 측정 도중 불필요한 Markdown 클래스 연결을 발견해 중단했다. 해당 중간 자료는 `.cache/performance/full-stylex-unfiltered/`에 남겼고 최종 20회에는 포함하지 않았다. 클래스 정리·시각 재검증 후 최종 코드로 20회를 처음부터 다시 실행했다.
