## 01. 이 발표의 목적이 구성을 결정한다

**청중이 자기 프로젝트에 적용할 수 있는 진단과 검증의 판단 기준을 통해, 카카오페이증권의 기술 역량을 보여준다.**

역량을 보여주는 근거는 작업의 진입장벽보다 판단 과정이다. 원인 후보를 실험으로 구분하고, 잘못된 예측을 산출물로 뒤집고, 보존할 동작과 허용할 차이를 구분하며, 테스트가 놓친 경로를 다시 검증했다는 것을 보여준다.

조건 분기로 제거될 것이라 믿었던 사례와 grep으로 의존성을 예측했다가 틀린 사례를 본문에 남긴다. 실패는 장식이 아니라 판단이 바뀐 근거다. 원본과의 차이와 검증 한계도 결과와 함께 제시한다.

위 표는 GitHub `d894381`의 2026-09-05 기록이다. 2026-09-15 수정한 검사기로 재검증한 결과는 아래 검토 기록에 별도로 남긴다. 블로그의 초기 실험과 이전 로컬 체크아웃의 수치를 갱신본에 섞지 않는다. **화면의 크기·개수는 사용자 요청에 따라 의도적으로 대략값을 유지한다.** 정확한 값·단위·버전·계산 기준은 이 메모와 발표자 노트에서 관리한다. KB는 1,000B, KiB는 1,024B다. 반올림은 허용하되 서로 다른 버전·호출 시나리오를 같은 전후 비교처럼 배치하지 않는다.

### 보존 범위와 알려진 차이

- 보존·대조 대상: 평가·버킷팅 로직, 준비한 입력의 평가 결과, 대조 대상으로 정한 이벤트 필드.
- 변경: 조립, 엔트리, 폴리필, `flat`/`flatMap` 치환, UUID·base64 구현.
- 의도적 차이: `/track`과 `/webview`의 일반 웹 폴백은 워크스페이스를 받지 않는다. 이벤트 `internalProperties`가 비고 초기화 동기화 API도 제공하지 않는다. track 전용 경로의 라이프사이클 시작 시점이 빠르다.
- 빌드 스모크는 원본의 `internalProperties`와 전송용의 `{}`를 각각 단언한 다음 해당 필드를 제외하고 나머지를 비교한다. “이벤트 전체가 같다”는 근거로 쓰지 않는다.
- 미검증: 실제 브라우저의 전송 타이밍·쿠키 동작, 실제 네이티브 앱 응답, 대시보드 집계 영향. 알려진 차이와 아직 확인하지 않은 영향은 구분한다.
- Node는 최소 20을 선언했지만 기록된 검증 환경은 Node 24.14.0이다. ES2017 빌드 타깃만으로 브라우저 지원 하한을 단정하지 않는다.
- 12.1.0의 시간대 수집 결함은 벤더가 12.1.1에서 수정했다. 최신 구현은 그 수정을 반영했다. 모든 결함을 계속 보존한다는 표현은 쓰지 않는다.

## 04. DAN 24와의 경계

2024년 발표는 「여러분의 웹서비스에는 꼭 필요한 것만 있나요? 번들사이즈 최소화를 통한 웹 성능 개선」이었다. 이번에는 외부 SDK의 원인 진단과 재구성에 집중한다.

### 겹치는 내용 — 서비스 실측 장에서 목록으로만 언급

- 사용하지 않는 리소스 식별 및 제거
- 서버 전용 로거와 mock 제거
- SVG·Lottie 등 자산 최적화와 지연 로딩
- 의존성 정리와 dedupe
- 서비스 성능 개선 결과

### 이번 발표의 본편

- 최소 import와 초기화 시나리오에서 PURE 힌트의 효과를 비교
- 소스맵과 타입 선언에서 원본 복원
- 런타임 플래그로 끊지 못한 import 경로를 엔트리 분리로 제거
- grep 예측을 번들 산출물로 정정
- 폴리필 사용처 조사와 실행 환경 요구사항
- 차분·변이 테스트, 알려진 차이, 검증 범위
- React 바인딩 전체를 만들지 않기로 한 판단

“내 라이브러리와 남의 라이브러리”의 대비만으로 차별성을 설명하지 않는다. **SDK 하나에서 원인을 실험하고, 필요한 기능과 검증 범위를 다시 정한 과정**이 이번 발표의 경계다.

## 05. 다른 세션 사이에서의 자리

준비 당시 확보한 19개 세션 목록은 AI·디자인, React Native, 디자인 시스템, 마이크로프론트엔드, 테스트 주제가 많았다. 당시 검토한 소개에서는 이번 SDK 진단·재구성과 직접 겹치는 발표를 찾지 못했다. 제목과 소개만으로 다른 발표에 실험이나 실패 분석이 없다고 단정하지 않는다.

거리와 차이를 설명할 세션:

- 「조합이 폭발하는 디자인 시스템, 이걸 눈으로도 테스트하라고요?」 — 비주얼 회귀
- 「절대 지워지지 않는 E2E 테스트를 위해 필요한 것들」 — E2E·디바이스 팜
- 「Lighthouse는 100점인데 왜 느릴까?」 — 런타임 성능과의 접점

위 목록의 최종 제목·소개·편성과 트랙 이름은 다시 확인한다. 다른 발표와의 경쟁을 근거로 주제의 가치를 단정하지 않는다. 제목은 구체적인 행동과 결과를 앞에 둔다.

## 06. CFP 제출안

### 발표 제목

외부 SDK를 뜯어 다시 만들었습니다: 전송용 번들을 69% 줄이고, 검증의 빈틈 찾기

대안: 상수 하나를 import했더니 gzip 91KiB가 따라왔습니다

“로직은 한 줄도 건드리지 않고”, “쓰지도 않는 코드가 번들의 97%”는 변경 범위와 측정 의미를 과장하므로 사용하지 않는다.

### 발표를 들으면 좋은 사람

번들을 줄이려다 트리셰이킹이 안 먹혀 막혀본 프론트엔드 개발자, 외부 SDK가 번들에 미치는 영향을 통제하고 싶은 개발자, 테스트가 전부 통과해도 안전한 교체인지 판단하기 어려웠던 개발자

### 간략한 소개

상수 하나를 import했는데 gzip 91KiB가 따라왔습니다. 원인을 실험으로 가르고, 배포된 소스맵과 타입 선언에서 SDK를 복원해 전송용 번들을 69% 줄였습니다. 조건 분기와 의존성 예측에서 틀린 과정, 원본 대조와 변이 테스트로 확인한 동작과 남은 차이를 공유합니다.

**공백 포함 155자** · 제출 폼의 실제 제한과 계산 방식은 제출 시 확인한다.

벤더와 구현 저장소는 CFP에 노출하지 않는다. 실명 공개 여부가 확정되기 전에는 현재 슬라이드의 가명 표기를 유지한다. FCP 44.4%는 SDK 단독의 성과로 소개하지 않는다.

### 검사기 수정

원래 검사기는 `crashed || failed > 0`으로 리포트가 생성되지 않은 실행 실패까지 검출로 집계했다. 리포트 유효성·실제 단언 실패·프로세스 종료 상태를 확인하는 분류기로 바꾸고, 실행 오류는 실패 처리하되 검출 수에는 넣지 않는다. 실제 실패 테스트 이름을 JSON으로 보관한다.

분류기 회귀 검사는 단언 실패, 리포트 누락·손상, 프로세스 장애, 종료 상태 불일치, 테스트 수집 오류, 전체 건너뛰기를 포함한다. 이 검사기는 변이의 의도와 실제 실패 테스트가 의미상 일치하는지 자동으로 보장하지는 않는다. 개별 결과를 함께 확인한다.

재검증은 원본 소스를 건드리지 않은 최신 커밋의 별도 worktree에서 진행한다. Node 25 환경에서는 localStorage 관련 기준선 오류가 발생해 이를 검출로 세지 않고 중단했다. Node 24.20.0에서 기준선을 다시 확인했다. 테스트를 깨뜨리는 실행 동안 다른 빌드가 변이 소스를 읽지 않도록 빌드·크기 검사는 변이 검사 종료 후 수행한다.
