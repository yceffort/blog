# 1. 왜 안 줄어드는가

## 원인이 둘인데, 처방이 다릅니다

<!-- 발표 10초 · 누적 02:30–02:40. -->

## 후보가 둘입니다

트리셰이킹은 번들러가 "이 코드는 아무도 안 쓴다"고 판단되면 빼 주는 최적화입니다
그게 거의 작동하지 않았습니다

<br>

**1. 번들러가 확신을 못 한다 (안전성)**
배포본의 클래스가 즉시 실행 함수(IIFE)로 바뀌어, 호출을 지워도 안전한지 증명하기 어려웠습니다
`sideEffects`는 모듈 단위, [PURE](https://esbuild.github.io/api/#pure)는 호출 단위의 부수효과 힌트입니다

**2. 애초에 진짜로 쓰인다 (도달 가능성)**
초기화 경로가 여러 기능을 참조하면, 번들러가 사용하지 않는 기능을 가려내기 어렵습니다

<!-- 발표 80초 · 누적 02:40–04:00. -->

---

## 그래서 강제로 주입해서 각각 쟀습니다

```js
// /*#__PURE__*/ = "이 호출은 부작용이 없으니 안 쓰면 지워도 된다"
const module = /*#__PURE__*/ createModule()
```

배포본의 클래스 IIFE에 [PURE 주석](https://esbuild.github.io/api/#pure)을 주입해, 부수효과 힌트의 영향을 비교했습니다
호출을 지워도 안전한지는 따로 검증해야 합니다

| 시나리오                           | gzip    | 변화        |
| ---------------------------------- | ------- | ----------- |
| 상수 하나만 import (원본)          | 90 KB대 |             |
| 상수 하나만 import + **PURE 주입** | 20 KB대 | **약 -74%** |
| 실사용 (`createClient` 호출, 원본) | 90 KB대 |             |
| 실사용 + **PURE 주입**             | 90 KB대 | **약 -1%**  |

## 2. 원본 로직을 확보해 재구성하기

**필요한 기능은 전송인데, 초기화하면 다른 기능도 따라왔습니다**
PURE 힌트만으로는 초기화 번들이 약 1%밖에 줄지 않았습니다

그래서 전송 경로를 **따로 조립할 수 있는지** 확인하기로 했습니다

## 소스맵에 원본이 통째로 들어 있었습니다

배포된 SDK의 소스맵을 열었더니 `sourcesContent` 에 **원본 TypeScript 전문**이 있었습니다

> `sourcesContent` 는 소스맵에 원본 소스를 문자열로 담는 선택 필드입니다

**브라우저 소스맵 + Node 소스맵 + 타입 선언**으로 수백 개 파일을 복원했습니다
갱신본 복원 스크립트가 각 단계의 파일 수를 확인합니다

로직을 다시 짤 필요가 없습니다
그 로직 자체를 씁니다
**핵심 알고리즘을 처음부터 똑같이 재현해야 하는 위험을 피합니다**

핵심 도메인 로직은 유지하고, 조립, 엔트리, 의존성과 일부 유틸리티를 바꿨습니다

## 소스맵에서 원본 소스를 꺼내는 순서

1. 배포된 JS의 `sourceMappingURL`을 따라 **해당 빌드의 소스맵**을 찾습니다
2. JSON의 `sources`와 `sourcesContent`를 **같은 인덱스끼리** 짝짓습니다
3. 경로를 정리해 파일로 저장하고, 빠진 타입은 배포된 `.d.ts`로 보충합니다

```bash
# 원본 내용이 모두 포함된 맵: -p는 디렉터리 구조 유지
npx shuji@0.8.0 sdk.js.map -o restored -p
```

**`sourcesContent`가 없거나 `null`이면 원본 파일을 별도로 확보해야 합니다**
위치 정보인 `mappings`만으로 원본 코드 전문을 되살릴 수는 없습니다

[shuji 사용법](https://github.com/paazmaya/shuji#command-line-options) · [소스맵 규격 — ECMA-426](https://tc39.es/ecma426/#sec-source-map-format)

<!-- 일반적인 sources/sourcesContent 형태의 맵을 설명한다. sourceMappingURL은 외부 .map 또는 인라인 data URL일 수 있고, HTTP 배포본은 sourcemap 응답 헤더도 확인한다. 원본 URL은 sourceRoot와 맵 URL을 기준으로 해석한다. 저장할 때는 번들러의 가상 경로와 상위 경로를 정리해 출력 디렉터리 안에만 기록하고 경로 충돌·누락을 확인한다. sections가 있는 인덱스 맵은 하위 맵별로 같은 절차를 적용한다. .d.ts는 타입 보충용이며 빠진 런타임 구현을 대신하지 않는다. 추출 후에도 import 경로·의존성·빌드 설정 정리와 검증은 별도다. -->

<!-- shuji는 청중이 시도할 수 있는 일반적인 추출 도구 예시이며, 이번 SDK를 복원할 때 사용한 도구라는 뜻은 아니다. 실제 복원은 브라우저·Node 맵과 타입 선언을 함께 다루는 스크립트로 진행했다. npm 배포 버전 0.8.0의 CLI 예시다. 이 버전은 모든 소스의 내용이 있어야 추출하며 일부가 빠진 맵은 별도 처리가 필요하다. -p로 저장하기 전에 sources의 경로를 확인하고, 추출 후 파일 수와 내용을 검증한다. -->

## 그런데 한 가지 놓친 게 있었습니다

원본 SDK에는 **플래그에 따라 선택 기능을 등록하는 구조**가 있었습니다

```ts
// 원본 SDK의 조립 구조를 요약한 예시
static create({ optional }: { optional: boolean }) {
  if (optional) registry.register(new OptionalModule(...))
  // OptionalModule 참조는 여전히 남아 있다
}
```

이 빌드에서는 플래그가 항상 `false`라고 접히지 않아 **선택 기능의 참조가 남았습니다**

이 구조에서는 **기능을 꺼도 코드 참조는 남을 수 있었습니다**

<!-- 플래그 분기는 원본 SDK에 있던 구조다. 발표자가 플래그를 추가했다가 실패한 과정으로 설명하지 않는다. 원본 구조를 분석하면서 기능 비활성화와 코드 참조 제거를 따로 확인해야 한다는 점을 짚는다. 빌드 시점에 조건을 확정해 코드를 제거할 수 있는 경우와 구분한다. -->

## 기능별 조립을 다른 엔트리로 옮겼습니다

```ts
// 원본 SDK: 코어가 선택 기능을 import 해서 직접 조립한다
import {OptionalModule} from './optional/OptionalModule'
static create({optional}) { if (optional) registry.register(new OptionalModule()) }

// 재구성 후: 조립은 바깥 모듈이 하고, 코어는 완성품만 받는다
static create(assembled: Assembled) { /* 이미 조립된 것을 받기만 */ }
```

조립 코드를 코어 바깥의 **별도 파일**로 옮기고 `create()` 를 뒤집었습니다

## 판정을 망가뜨려도 통과했습니다

조건이 맞으면 후속 동작을 실행하는 경로가 있었습니다

```ts

shared.handler = function (...args) {

```

## 잘못된 입력에도 양쪽 결과는 같았습니다

2. 원래 검사하려던 설정이 입력에서 사라졌습니다. 에러는 없습니다
3. 양쪽 SDK가 똑같이 "설정 없음"을 돌려주니 비교 결과는 **일치**입니다

## 백업: base64 구현과 원본 대조

```ts
// 우리 구현. 플랫폼 내장 TextEncoder와 btoa만 쓴다
export function encodeBase64Url(input: string): string {
  const bytes = new TextEncoder().encode(input) // btoa는 latin1 밖이면 예외
  let bin = ''
  for (const b of bytes) bin += String.fromCharCode(b)
  return btoa(bin).replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '')
}
```

이 결과는 **외부로 전송되는 값**입니다. 인코딩 결과가 원본과 같아야 합니다

```ts
import {Base64} from 'base64-lib' // 걷어낸 원본 라이브러리(가명). devDependency로만 남긴다
for (let n = 0; n <= 64; n++) {
  expect(encodeBase64Url('x'.repeat(n))) // 우리 구현
    .toBe(Base64.encodeUrl('x'.repeat(n))) // 원본 라이브러리
}
// 0~64는 패딩 경계(길이 % 3) 전수. 시드 고정 난수 유니코드 2000건도 같은 방식으로 대조
```

## 백업: UUID 형식을 유지하며 바꿨습니다

```ts
export function v4(): string {
  const c = globalThis.crypto
  if (typeof c.randomUUID === 'function') return c.randomUUID()

  // 없으면 직접 조립한다: 랜덤 16바이트를 받아서
  const b = new Uint8Array(16)
  c.getRandomValues(b)
  b[6] = (b[6] & 0x0f) | 0x40 // 7번째 바이트 상위 4비트 = 버전(4)
  b[8] = (b[8] & 0x3f) | 0x80 // 9번째 바이트 상위 2비트 = 변형(RFC 4122)
  /* ...hex 문자열로 조립... */
}
```

**왜 폴백이 필요한가?** `randomUUID` 에는 `[SecureContext]` 제약이 있습니다
보안 컨텍스트가 아닌 환경에서는 사용할 수 없어, `getRandomValues` 기반 폴백을 뒀습니다

## 백업: 소스맵이 없다면 어떻게 할까

**확보할 수 있는 코드와 유지 비용에 맞춰 최적화 방법을 고릅니다**

| 상황                       | 검토할 방법                                                               |
| -------------------------- | ------------------------------------------------------------------------- |
| 원본 소스를 확보할 수 있다 | 공개 저장소·패키지에 포함된 소스의 버전을 맞추고 재빌드·엔트리 분리 검토  |
| 배포된 JavaScript만 있다   | 비압축 배포본이나 포맷팅한 번들의 호출 경로를 분석하고 제한적인 패치 검토 |
| 내부를 바꾸기 어렵다       | 벤더에 경량 엔트리 요청, 지연 로딩·사용 화면 제한·대체 SDK 비교           |

포맷팅은 원본 TypeScript·이름·파일 구조의 복원을 보장하지 않습니다
지연 로딩은 로딩 시점을 바꾸므로, 초기 수집·필수 동작이 빠지지 않는지 확인합니다

[배포 코드와 소스맵 — Chrome DevTools](https://developer.chrome.com/docs/devtools/javascript/source-maps) · [코드 분할과 지연 로딩 — web.dev](https://web.dev/articles/optimizing-content-efficiency-javascript-startup-optimization)
