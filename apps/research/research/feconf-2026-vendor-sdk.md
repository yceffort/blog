## 이야기는 이 두 줄에서 시작합니다

```ts
import {AssignReason} from '@vendor/js-sdk'

console.log(AssignReason.NO_RULE_MATCH)
```

> 실험 플랫폼 SaaS의 웹 SDK입니다. `AssignReason` 은 **"이 유저가 왜 A군에 배정됐는지"** 를
> 알려주는 열거형이고, 문자열 상수 몇 개가 전부입니다.

SDK를 초기화하지도 않았습니다. **문자열 상수 하나를 읽었을 뿐입니다.**

그런데 이 파일이 이상하게 무거웠습니다.

## 이 SDK가 어떻게 생겼냐면

```text
웹 SDK
├── 평가 엔진       타겟 조건을 비교하고 유저 ID로 A/B 배정
├── 메시지 UI       배너, 팝업, 리다이렉트
└── 이벤트 전송     track: 유저 행동을 서버로 전송

별도 React 바인딩 패키지
└── 웹 SDK를 감싸는 Provider, Context, 훅
```

**홈이 쓰는 기능은 이벤트 전송입니다.**
웹 SDK의 초기화 경로에는 평가와 메시지 기능까지 연결되어 있었습니다.

## 보존할 동작과 허용할 차이를 먼저 나눴습니다

- **보존:** 평가·버킷팅 로직, 대조 대상으로 정한 이벤트 필드

# 1. 왜 안 줄어드는가

## 원인이 둘인데, 처방이 다릅니다

---

## 후보가 둘입니다

트리셰이킹은 번들러가 "이 코드는 아무도 안 쓴다"고 판단되면 빼 주는 최적화입니다.
그게 거의 작동하지 않았습니다.

<br>

**1. 번들러가 확신을 못 한다 (안전성)**
배포본의 클래스가 IIFE로 컴파일되어, 호출을 지워도 안전한지 증명하기 어려웠습니다.
`sideEffects`는 모듈 단위, `PURE`는 호출 단위의 부수효과 힌트입니다.

**2. 애초에 진짜로 쓰인다 (도달 가능성)**
초기화 경로가 여러 기능을 참조하면, 번들러가 사용하지 않는 기능을 가려내기 어렵습니다.

---

## 그래서 강제로 주입해서 각각 쟀습니다

```js
// /*#__PURE__*/ = "이 호출은 부작용이 없으니 안 쓰면 지워도 된다"
const evaluator = /*#__PURE__*/ createEvaluator()
```

배포본의 클래스 IIFE에 PURE 주석을 주입해, 부수효과 힌트의 영향을 비교했습니다.
**원인 분리를 위한 실험입니다. 이 결과만으로 동작 보존까지 확인되지는 않습니다.**

| 시나리오                           | gzip     | 변화       |
| ---------------------------------- | -------- | ---------- |
| 상수 하나만 import (원본)          | 약 94 KB |            |
| 상수 하나만 import + **PURE 주입** | 약 25 KB | **-73.6%** |
| 실사용 (`createClient` 호출, 원본) | 약 97 KB |            |
| 실사용 + **PURE 주입**             | 약 96 KB | **-1.2%**  |

<!-- 초기 분석 스냅샷의 실험. 최종 갱신본의 재실험 결과로 제시하지 않는다. -->

## 읽는 법

<br>

**상수만 쓸 때는 73.6% 줄어듭니다.** 부수효과 힌트가 제거 여부에 큰 영향을 줬습니다.

**그런데 실제로 SDK를 쓰기 시작하면 1.2%밖에 안 줍니다.**
실사용 초기화 경로에서는 많은 기능의 참조가 남아, 같은 힌트만으로는 줄지 않았습니다.

PURE 주입의 효과를 `sideEffects` 설정 한 줄의 효과로 해석하지는 않습니다.

# 2. 어떻게 다시 만드는가

## 다시 짜지 않고 복원했습니다

---

## 소스맵에 원본이 통째로 들어 있었습니다

배포된 SDK의 소스맵을 열었더니 `sourcesContent` 에 **원본 TypeScript 전문**이 있었습니다.

> `sourcesContent` 는 소스맵이 원본 소스를 문자열로 담는 선택 필드입니다. 많은 패키지가 켜 둡니다.

**브라우저 소스맵 300여 개 + Node 소스맵 몇 개 + 타입 선언 70여 개, 합쳐 400여 파일**

갱신본 복원 스크립트가 각 단계의 파일 수를 확인합니다.

로직을 다시 짤 필요가 없습니다. 그 로직 자체를 씁니다.
**버킷팅 해시를 비트 단위로 똑같이 재현해야 하는 위험을 피합니다.**

핵심 도메인 로직은 유지하고, 조립, 엔트리, 의존성과 일부 유틸리티를 바꿨습니다.

---

## 그런데 여기서 한 번 틀렸습니다

평가 엔진을 안 쓰는 소비자에겐 빼 주려고 플래그를 뒀습니다.

```ts
// 안 빠진다. 플래그로 "만드느냐"만 막았을 뿐
static create({ evaluator }: { evaluator: boolean }) {
  if (evaluator) registry.register(new VariantEvaluator(...))
  //                                   ^^^^^^^^^^^^^^^^ 이 이름이 파일에 남아 있다
}
```

이 빌드에서는 플래그가 항상 `false`라고 접히지 않아 **평가 엔진 참조가 남았습니다.**

빌드 시점에 조건을 확정할 수 있는 경우와 구분해야 합니다.

---

## 기능별 조립을 다른 엔트리로 옮겼습니다

```ts
// Before: 코어가 평가 엔진을 import 해서 직접 조립한다
import {VariantEvaluator} from './evaluation/VariantEvaluator'
static create({evaluator}) { if (evaluator) registry.register(new VariantEvaluator()) }

// After: 조립은 바깥 모듈이 하고, 코어는 완성품만 받는다
static create(assembled: Assembled) { /* 이미 조립된 것을 받기만 */ }
```

조립 코드를 코어 바깥의 **별도 파일**로 옮기고 `create()` 를 뒤집었습니다.

코어 파일의 평가 엔진 `import` 가 **0개**가 되고 나서야
타겟 매칭 코드(압축 전 약 41KB)가 실제로 빠졌습니다.

**전송용 엔트리에서 평가 엔진으로 이어지는 import 경로를 끊었습니다.**

---

## 결과: 엔트리, 빌드, 의존성을 바꾼 뒤

700줄짜리 단일 엔트리를 기능별로 나눠 엔트리 8개로 만들었습니다.

| 가져가는 엔트리                              | gzip (KiB) | 벤더 대비  |
| -------------------------------------------- | ---------- | ---------- |
| **`./send`** (이벤트 전송만. 우리가 쓰는 것) | **약 30**  | **-68.9%** |
| `./eval` (A/B 평가까지)                      | 약 47      | -51.0%     |
| `.` (전체 엔트리)                            | 약 66      | -30.4%     |
| 벤더 원본                                    | 약 95      | 기준       |

**2026-09-05 갱신본**을 패키지 이름으로 import해 측정했습니다.
**엔트리 분리, 빌드, 폴리필, 의존성 변경을 함께 반영한 결과**입니다.

# 3. 라이브러리 대신 플랫폼

## 외부 런타임 의존성을 0으로 만들기까지

---

## 엔트리가 이렇게 폴리필을 심고 있었습니다

```ts
import 'core-js/features/promise'
import 'core-js/features/array'
```

> `features/*`로 가져온 범위에 실제로 쓰지 않는 메서드까지 포함되어 있었습니다.
> **폴리필이 무엇을 추가하는지와 SDK가 무엇을 쓰는지를 따로 조사했습니다.**

소스맵의 압축 전 원본 소스 기준으로 core-js 유래 코드가 약 200KB였습니다.

제거 여부를 판단하기 위해 **실제 사용처와 필요한 실행 환경부터 조사했습니다.**

---

## 쓰는 메서드와 필요한 플랫폼을 따로 봤습니다

| 조사 대상             | 결과                                        |
| --------------------- | ------------------------------------------- |
| Promise / async·await | 90회 이상. API 지원과 문법 타깃을 각각 확인 |
| `flat` / `flatMap`    | 3곳을 `reduce`로 치환                       |
| 추가 주입 메서드 10종 | 조사한 사용처 0회                           |

폴리필 import를 제거하고 **빌드 문법 타깃을 ES2017**로 맞췄습니다.
다만 `TextEncoder`, `btoa`, Web Crypto는 실행 환경이 제공해야 합니다.

**ES2017로 빌드했다는 사실만으로 브라우저 호환성이 보장되지는 않습니다.**
실제 브라우저·웹뷰의 지원 하한과 실행 검증은 남아 있습니다.

<!-- Node는 최소 20을 선언했으나 기록된 검증 환경은 Node 24.14.0이다. 실제 Chrome/Safari/Firefox에서의 전송 타이밍, visibilitychange, 쿠키 처리는 검증 범위 밖이다. -->

---

## base64도 다섯 줄. 단, 원본과 대조합니다

```ts
// 우리 구현. 플랫폼 내장 TextEncoder와 btoa만 쓴다
export function encodeBase64Url(input: string): string {
  const bytes = new TextEncoder().encode(input) // btoa는 latin1 밖이면 예외
  let bin = ''
  for (const b of bytes) bin += String.fromCharCode(b)
  return btoa(bin).replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '')
}
```

이 결과가 **요청 헤더에 실려 서버가 파싱** 합니다. 한 바이트도 달라선 안 됩니다.


## 안 걸린 것 하나. URL 판정을 망가뜨려도 통과했습니다

이 SDK에는 "URL이 조건에 맞으면 다른 페이지로 보낸다"는 기능이 있습니다. 그 판정 함수를 **무조건 true**로 바꿨는데, "조건에 안 맞으면 보내지 않는다"를 확인하는 테스트가 그대로 통과했습니다.

원인은 테스트끼리 격리가 안 된 것이었습니다.

```ts
// SDK가 켜질 때, 브라우저의 pushState를 자기 함수로 한 겹 감싼다
const original = history.pushState
history.pushState = function (...args) {
  original.apply(this, args)
  notifyUrlChange()
}
// 그런데 close()는 이 겹을 벗기지 않는다
```

**앞 테스트에서 만든 SDK가 `close()` 뒤에도 남아서, 계속 URL 변화를 듣고 있었습니다.**

## 앞 테스트의 SDK가 먼저 움직여서, 이번 테스트는 판정문을 아예 안 탔습니다

앞 테스트가 남긴 SDK를 **좀비**, 이번 테스트가 만든 SDK를 **이번 SDK**라고 부르겠습니다.

1. 이번 테스트가 시작하며 URL을 바꿉니다. 좀비도 그 신호를 받습니다
2. 좀비는 망가진 판정문(무조건 true) 때문에 리다이렉트를 실행하고, "이미 보냈음" 표시(쿠키)를 남깁니다
3. 이번 SDK는 그 표시를 보고 **아무것도 하지 않고 끝냅니다.** 판정문을 타지 않으니 망가진 줄도 모릅니다
4. 테스트는 "이번 SDK가 리다이렉트하지 않았다"만 확인하므로 **통과**합니다

**통과한 이유가 "코드가 맞아서"가 아니라 "앞 테스트가 남긴 상태 때문"이었습니다.**

교훈 둘. 전역(`history`, `fetch`, 타이머)을 건드리는 라이브러리는 **테스트마다 원래대로 되돌릴 것.** 초록불은 그 코드를 지나갔다는 뜻이 아니니 **일부러 망가뜨려 확인할 것.**

그리고 되돌리려면 **SDK가 켜질 때 무엇을 건드리는지 알아야 합니다.** 복원한 원본 소스가 있었기에 `pushState`를 감싼다는 걸 찾아 벗길 수 있었습니다.

## 백업. uuid를 네이티브로, 단 그냥 바꾸면 깨집니다

```ts
export function v4(): string {
  const c = globalThis.crypto
  if (typeof c.randomUUID === 'function') return c.randomUUID()

  // 없으면 직접 조립한다: 랜덤 16바이트를 받아서
  const b = new Uint8Array(16)
  c.getRandomValues(b)
  b[6] = (b[6] & 0x0f) | 0x40 // 7번째 바이트 상위 4비트 = 버전(4)
  b[8] = (b[8] & 0x3f) | 0x80 // 9번째 바이트 상위 2비트 = 변형(RFC 4122)
  /* ...hex 문자열로 조립... */
}
```

**왜 폴백이 필요한가?** `randomUUID` 에는 `[SecureContext]` 제약이 있습니다.
보안 컨텍스트가 아닌 환경에서는 사용할 수 없어, `getRandomValues` 기반 폴백을 뒀습니다.

---

## 백업. 여기서 함정이 둘 있었습니다

**지원 버전뿐 아니라 실행 환경의 제약까지 확인해야 합니다.**
MDN 본문과 스펙에 secure context 제약이 명시되어 있습니다.
사용 환경에서 `crypto.getRandomValues`도 제공되는지 확인해야 합니다.

<br>

**"더 가벼운 라이브러리로 바꾸자"도 답이 아니었습니다.**
`nanoid` 안이 있었는데, 세션 ID가 `uuid.slice(0, 8)` 형식이었습니다.
uuid는 소문자 16진수라 앞 8자가 `a3f9c1d2` 같은 모양인데,
기본 nanoid는 문자 집합이 달라서 **그대로 교체하면 기존 형식 계약이 바뀝니다.**

<br>

이 작업에서는 **플랫폼 내장과 UUID 형식을 유지하는 폴백**을 선택했습니다.
