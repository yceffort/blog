# 빌드와 첫 방문 벤치마크

## 실제 페이지 경로 비교 (2026-09-14)

주요 측정은 전체 프로덕션 빌드 시간과 글 한 편의 콜드 방문 시간이다. 예열한 전체 글의 HAST 변환은 뒤에 별도로 보존한다. 원시 기록과 요약은 [experience-results.json](experience-results.json), 실행 코드는 [scripts/experience/run.mjs](scripts/experience/run.mjs), 비교 구성 복원은 [prepare.mjs](scripts/experience/prepare.mjs)에 있다.

`feat/blog-performance`의 `f27162bd` 작업 트리를 복사해 세 구성을 만들었다. 글, 현재 앱, `getAllPosts`의 모듈 메모이즈는 동일하다. 렌더러와 그에 필요한 CSS, 수식 자원은 각 구성에 맞춘다. 기존 브랜치를 통째로 체크아웃한 비교가 아니다.

환경은 Apple M1, macOS arm64, Node 24.20.0, Next.js 16.3.1, Chromium 153.0.8010.12다. 개발 서버를 종료하고 빌드와 방문을 순차 실행했다. GA4 자격증명을 비워 인기글 API 결과의 영향을 제외했다. 의존성은 설치된 잠금 버전을 공유하며, 복사한 앱의 워크스페이스 패키지는 각 복사본으로 연결한다. 원본 `.env` 파일은 복사하지 않는다. 재실행에 필요한 `next-mdx-remote-client`는 개발 의존성에 고정했고, 이 패키지를 복원하며 추가된 간접 의존성도 `cb40957f`의 잠금 버전으로 맞췄다.

### 전체 빌드

매회 `.next`를 제거한 뒤 `next build`의 프로세스 실행부터 종료까지 잰다. 의존성 설치와 WASM 재컴파일은 제외한다. 세 구성의 실행 순서 여섯 가지를 모두 써서 구성마다 순서별 위치가 두 번씩 나오게 했다. 구성별 6회, 총 18회이며 실패한 빌드를 포함한 평균으로 계산하지 않았다. 기록된 18회는 모두 성공했다.

| 구성                  | 중앙값 | 최솟값 | 최댓값 |
| --------------------- | -----: | -----: | -----: |
| JS                    | 20.88s | 20.68s | 22.69s |
| 파싱 WASM + JS 후처리 | 20.62s | 19.98s | 23.68s |
| 전체 WASM             | 20.33s | 19.77s | 20.72s |

JS와 전체 WASM의 중앙값 차이는 0.55초였다. 각 구성의 실행 범위가 겹치므로 이 여섯 번의 로컬 측정만으로 빌드가 뚜렷하게 빨라졌다고 말하기는 어렵다. 적어도 여기서는 첫 방문에서 확인한 차이가 전체 빌드 시간에 그대로 나타나지는 않았다.

### 콜드 방문

매회 빌드 직후의 `.next`를 복원하고 새 `next start`와 새 Chromium 프로세스를 실행한다. 서버 준비 로그만 기다리며, 준비 확인용 HTTP 요청과 사전 방문은 하지 않는다. 브라우저는 새 프로필, 1280×900 라이트 화면, 일반 Chrome 사용자 에이전트, HTTP 캐시 비활성, 서비스 워커 차단을 사용한다. 로컬 루프백 네트워크에서 감속 없이 접속하며 Google Analytics 요청은 차단했다. 운영체제 파일 캐시와 외부 CDN 캐시는 비우지 않는다.

대상은 코드가 있는 `/2026/08/k8s-for-frontend-1`과 수식 31개가 있는 `/2020/07/math-for-programmer-chapter1-2-set`이다. 두 경로가 `.next/prerender-manifest.json`의 완성된 경로 목록에 없는지 확인했다. 실제 요청에서 목표 글의 `renderPost`가 정확히 한 번 실행되는지도 검사했다. 방문마다 오류 없는 HTTP 응답과 브라우저 실행, 코드 줄 또는 수식 노드를 확인했다.

아래는 각 조합을 6회 방문한 중앙값이다. 방문 순서도 빌드와 같은 여섯 가지를 사용했다. 첫 화면 스크린샷은 각 조합의 첫 실행에서 관찰 구간이 끝난 뒤 저장했다.

`renderPost` 타이머는 정적 import가 끝난 뒤 함수 호출을 감싼다. 이미지 크기 처리와 React 요소 생성은 포함하지만 순수 파서 초기화 전체를 뜻하지 않는다. TTFB와 본문 도착 시간에는 첫 요청 중 발생하는 경로와 모듈 로딩, 글 목록 메타데이터 계산, Next.js 렌더링이 함께 들어간다. 서버 프로세스 실행부터 준비 로그까지의 시간은 별도 필드로 기록했으며 브라우저 탐색 시간에는 포함하지 않았다.

본문 도착은 스켈레톤을 제외한 `article.post-article`을 MutationObserver가 처음 확인한 시점이다. PPR 껍데기의 도착과 구분한 DOM 지표이며 페인트 완료가 아니다. FCP도 본문 전체의 표시 완료를 보장하지 않는다. LCP는 `load`와 글꼴 준비를 기다린 뒤 1초까지 관찰한 값이다.

코드 글과 수식 글의 본문 도착 중앙값은 JS 대비 WASM에서 각각 약 247ms와 352ms 줄었다. 함수 호출 밖의 세부 비용은 분해하지 않았으므로 이를 전부 import 제거의 효과로 돌리지 않는다. 수식 글에는 KaTeX의 CSS와 글꼴을 MathML과 로컬 글꼴로 교체한 차이도 포함된다. 두 글과 한 로컬 환경의 결과이며 실서비스의 서버리스 콜드 스타트나 모든 글의 개선율은 아니다.

### 재실행

저장소가 지정한 Node와 pnpm으로 의존성을 설치하고, Playwright의 Chromium을 설치한다. 빌드 도구의 CPU와 RSS 수집은 macOS의 `/usr/bin/time -l`을 사용한다. 기준 커밋 `cb40957f`와 `f27162bd`가 로컬 Git 이력에 있어야 한다. WASM 재빌드는 필요하지 않다.

```sh
corepack pnpm install --frozen-lockfile
corepack pnpm --filter blog exec playwright install chromium
node packages/markdown-rs/scripts/experience/run.mjs measure
```

첫 실행은 `.cache/markdown-experience`에 입력을 고정하고 세 구성을 준비한다. 이미 입력이 준비되어 있으면 그 복사본을 재사용한다. 소스나 의존성을 바꾼 뒤 새 측정을 하려면 해당 벤치 전용 디렉터리를 먼저 다른 이름으로 옮기거나 삭제해야 한다. 개발 서버와 다른 빌드, 검증 명령은 측정 전에 종료한다.

`measure`는 빌드 18회와 방문 36회를 모두 실행한다. `pilot`은 예비 빌드 3회와 방문 6회다. `builds`는 빌드만, `browser`는 준비된 빌드로 방문만 반복한다. 원시 결과와 로그, 스크린샷은 `.cache/markdown-experience/{mode}`에 저장되며 `manifest.json`에 입력 파일 해시와 복원 기준을 남긴다.

이번 기록은 예비 빌드 세 개로 방문 36회를 먼저 실행하고, 별도 단계에서 빌드 18회를 실행했다. 예비 빌드는 빌드 시간 요약에서 제외했다. 브라우저에 사용한 빌드 ID와 각 측정 단계의 스크립트 해시는 원시 기록에 함께 남겼다. 이후 본문과 재실행 스크립트를 정리했으므로 재실행 시 파일 해시가 달라질 수 있다.

### 초기 혼합 구성 (역사적 기록)

아래는 파싱과 HAST 생성만 WASM으로 옮기고 KaTeX와 Prism을 JS에 남겼을 때의 측정이다. 현재 스크립트는 전체 WASM 구성을 측정하므로 아래 결과를 그대로 재현하지 않는다.

실행별 시간, 순서, 환경, 코드와 입력의 SHA-256은 [bench-results.json](bench-results.json)에 저장했다. 측정 대상은 `feat/blog-performance`의 `f27162bd`에 이번 벤치 변경을 적용한 작업 트리다.

#### 측정 범위

양쪽 모두 frontmatter를 제거한 마크다운 문자열에서 시작해 KaTeX와 Prism 후처리를 포함한 HAST에서 끝난다. 제목 id, 목차, 제목 링크와 코드 파일명 처리도 포함한다. Rust 쪽 시간에는 Node 바인딩의 UTF-8/JSON 변환과 WASM 호출이 포함된다.

파일 읽기, frontmatter 파싱, 모듈 import, 출력 검증은 타이머 밖에서 실행한다. JS 코드 생성, React/JSX 변환, `imageMetadata`, StyleX의 `parseCodeSnippet`은 두 구현 모두 측정 범위에서 제외한다. 이 수치는 파서 단독 성능이나 전체 페이지 렌더 시간, 빌드 시간으로 해석할 수 없다.

기존 `bench.mjs`는 JS 쪽에서 파리티 검사용 AST 전체 복사 네 번과 MDX의 JS 코드 생성까지 실행했다. Rust 쪽은 HAST 후처리에서 끝났으므로 두 시간의 비율을 같은 작업의 속도 차이로 해석할 수 없었다.

새 [JS 벤치 경로](scripts/js-hast-pipeline.mjs)는 `unified`의 `parse`와 `run`으로 HAST까지만 처리한다. JSX 문단 처리에는 설치된 `@mdx-js/mdx` 3.1.1의 `remarkMarkAndUnravel`을 그대로 사용한다. 이 함수는 내부 경로로 가져오므로 MDX 버전을 갱신할 때 해당 경로와 출력 대조를 함께 확인해야 한다.

#### 출력 검증과 실행 조건

측정 전에 모든 입력의 출력부터 검증한다. 새 JS 경로는 위치 정보만 제거하고 원본 `createProcessor`의 HAST와 대조한다. Rust 경로는 기존 파리티 규칙에 따라 위치 정보와 MDX 메타데이터를 제외하고, MDX 리터럴 속성과 빈 표현식을 정규화한 뒤 대조한다. 이 과정의 복사와 정규화는 측정 시간에 포함되지 않는다. 파싱 오류나 불일치는 실행을 중단시킨다.

- Node 24.20.0, Apple M1, macOS arm64(Darwin 25.6.0).
- 한국어와 영어, 초안을 포함한 현재 포스트 453개를 경로순으로 처리했다. 시리즈 소개는 벤치 입력에 포함하지 않았다.
- 단일 프로세스에서 양쪽 프로세서와 WASM 인스턴스를 재사용했다. 출력 검증 뒤 전체 입력을 양쪽에서 한 번씩 추가로 예열했다.
- JS 먼저와 Rust 먼저를 번갈아 6쌍 측정했다. 각 구현을 먼저 실행한 횟수는 3회씩이다.
- 측정 구간은 UTC 06:51:23.928부터 06:52:03.254까지다. 이 구간에 별도의 빌드나 검증 명령을 실행하지 않았다.
- 가장 느렸던 Rust 첫 실행 2,581.7ms를 포함해 모든 실행을 결과에 남겼다. 기존 글에서 발생하는 KaTeX 경고도 양쪽에 동일하게 유지했다.

이 결과는 예열된 로컬 변환 성능이다. WASM 최초 로딩과 모듈 초기화, 실서비스의 요청 지연은 포함하지 않는다. 이전 글의 Codespaces 수치와는 입력 개수, 환경, 측정 범위가 달라 절대 시간을 직접 비교할 수 없다.

#### 당시 검증 범위

초기 벤치의 기본 출력은 `bench-results.json`이었다. 당시 포스트와 시리즈 461개의 파리티 검사와 JS 벤치 경로의 원본 HAST 대조가 통과했고, 실제 측정 대상 453개에서 양쪽 출력 검증을 다시 통과했다. 이 기록은 현재의 토큰과 수식 마크업을 검증한 결과가 아니다.
